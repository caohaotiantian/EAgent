## 1. Background and Purpose

EAgent already makes deterministic offline runs cheap. `MockProvider`
(`src/providers/mock.ts:38`) is a scriptable, deterministic LLM, and the
`cassette` provider (`src/providers/cassette.ts:47`) replays a recorded event
stream with no network. The `trace` extension
(`src/extensions/trace.ts:55`) folds the lifecycle bus into an ordered list of
spans (tool order, counts, finish reason, errors) and lifetime metrics — but it
only **records and renders** them (`/trace`, `/usage`). Nothing in the codebase
**asserts** over a trajectory, and nothing **grades** an output's quality.

That gap matters. A single green `npm test` run reports pass@1, which overstates
reliability: it proves a scripted path *can* succeed once, not that the agent's
*behavior* — which tools it reaches for, in what order, how many spans it burns,
whether it errors, whether its final answer is actually good — is what we
intend, and stays what we intend as the code changes underneath it. Behavior
should be a rerunnable regression surface: a spec you can assert and a scorecard
you can re-run, the same way `trace` made behavior *observable*.

This task adds a `evals` extension: a **pure event-bus consumer** (mirroring
`trace`'s span model) that builds an in-memory trajectory for the current/last
run, plus the three thin tools that turn that trajectory into a regression
surface:

1. `/expect <spec>` — a declarative, mechanizable assertion over the last run's
   trajectory (tool order/exact, span count, finish reason, no tool errors, max
   tokens), returning pass/fail + the failing reasons.
2. `/eval <dir>` — a headless runner that drives `agent.run`
   (`src/kernel/agent.ts:146`) over `*.eval.json` scenarios — each carrying an
   input, a `MockProvider` script, and an `/expect` spec — and prints a pass@k
   scorecard.
3. a `judge` **tool** — given a rubric + a candidate, it returns
   `{score, verdict, reason}` via a recursion-safe, tool-less provider sub-call,
   reusing the exact pattern `risk-guard` uses for its classifier
   (`src/extensions/risk-guard.ts:95`).

It also ships a small `test/security/` regression set that asserts the existing
safety guards still fire on known attacks, using only the offline harness — no
new primitive.

If we do not do this, EAgent keeps shipping behavior that is observable but never
*checked*: `trace` shows you the spans, but a regression that reorders tools,
doubles the span count, or degrades the final answer sails past `npm test` as
long as the one scripted happy path still returns. The lesson several eval
findings converge on — that a thin assertion+scorecard+judge slice is the
highest-leverage reliability surface an agent can add — goes unlearned.

## 3. Scope Boundary (NOT in scope — Simplicity First)

The risk this design is built against is **scope balloon into a full eval
framework**. The explicit non-goals:

- **No statistical machinery.** No pass@k *confidence intervals*, variance
  analysis, bootstrapping, or significance testing. `/eval` prints a flat
  `passed/total` scorecard (count + the failing scenarios), nothing inferential.
- **No eval-awareness / sandbagging measurement.** No gap measurement between
  "model knows it is being evaluated" and not. No probe rotation, no held-out
  probe banks.
- **No external dataset formats.** No SWE-bench/HELM/lm-eval adapters, no
  HuggingFace loaders, no remote fetch. The only scenario format is the local
  `*.eval.json` defined in §4 D4.
- **No fuzzy / semantic trajectory matching in `/expect`.** `/expect` is a set
  of exact, mechanizable predicates (§4 D2). Semantic "did the trajectory
  *roughly* do the right thing" judgments are the `judge` tool's job over the
  final *output*, not the assertion engine's job over the *trajectory*.
- **No kernel change.** The trajectory is built purely from existing bus events;
  no new event, filter, or signature is added (§4 D1).
- **No new capability vocabulary.** The `judge` tool needs only the provider
  sub-call the kernel already exposes (§4 D3, §5); the consumer and `/expect`
  have no side effects and so are not capability-gated.
- **No live grading by default-on.** `judge` is a tool the model (or a scenario)
  *invokes*; nothing auto-grades every run. The whole extension is
  `EAGENT_EVALS=off`-able.

These are deferred *with intent*, not forgotten: the thin slice (assertions +
scorecard + one judge) is shippable and useful on its own, and each deferred
item can return as its own additive extension later.

## 4. Key Design Decisions

### D1 — Build the trajectory as a pure event-bus consumer, not by threading instrumentation

**Problem.** `/expect` needs an ordered record of the last run's tools, span
count, finish reason, error flags, and token usage. Where does that record come
from?

**Options.**
- (a) **Pure consumer.** Subscribe to the lifecycle bus
  (`agent_start`, `tool_start`/`tool_end`, `usage`, `agent_end`) and fold it into
  an in-memory `Trajectory`, exactly as `trace` already folds the same events
  into spans (`src/extensions/trace.ts:98-173`). No kernel change.
- (b) **Thread instrumentation through `agent.run`.** Add a hook/return field or
  a new event so the loop hands the trajectory out directly.

**Choice: (a) pure consumer.** The bus already narrates every moment `/expect`
cares about, with the exact payloads needed: `tool_start`/`tool_end` carry
`{ call }` and `{ call, result }` (`src/kernel/events.ts:31-32`), `result.isError`
gives the error flag (`src/kernel/agent.ts:304`), `agent_end` carries the
`StopReason` (`src/kernel/events.ts:20`), and `usage` carries `{ cumulative }`
(`src/kernel/events.ts:35`). The handler is wrapped so a throw never escapes the
bus and out-of-order events degrade gracefully — the same defensive `safe()`
discipline `trace` uses (`src/extensions/trace.ts:88-96`). On `agent_start` the
collector resets to keep only the last run, bounding memory exactly as `trace`
does (`src/extensions/trace.ts:99-108`).

**Why (b) is rejected.** It changes the kernel — a new event or return field —
to obtain data the bus already emits, violating the house rule that new behavior
is an extension, not a core fork, and the "minimum code" bar. It would also
duplicate the span-collection logic `trace` already proves correct. A pure
consumer is strictly less code and strictly more faithful to the architecture.

### D2 — The `/expect` assertion set: five exact, mechanizable predicates

**Problem.** Which checks does `/expect` support? Too few and it cannot express
real regressions; too many (or fuzzy ones) and it becomes the full eval
framework §3 forbids.

**Options.**
- (a) **A minimal exact set:** `tools` (an expected name sequence, matched
  `in_order` as a subsequence or `exact` as the full list), `maxSpans` (a ceiling
  on the **tool-span count only** — see "Span set" below), `finishReason` (the
  `StopReason`), `noToolErrors` (every tool span ok), `maxTokens` (cumulative
  token ceiling).
- (b) **Add fuzzy / semantic trajectory matching** — "the trajectory roughly
  resembles this template", regex-over-args, timing thresholds.
- (c) **A single check** (e.g. only `tools in_order`).

**Span set (what a `span` IS for evals).** `trace` builds three span kinds —
`agent`, `turn`, and `tool` (`src/extensions/trace.ts:28`). For evals' purposes a
`Trajectory` records **only the `tool` spans**: one span per dispatched tool
call, carrying the tool name, an `ok` flag (`result.isError === false`), and the
call order. The `agent`/`turn` spans are deliberately *not* part of the
trajectory's span set, because a count that included `turn` spans would make the
ceiling depend on how many turns the model happened to take — a noisier, less
stable regression signal than the tool count, which is the behavior `/expect`
exists to pin. Consequently `traj.tools` (the ordered tool-name list) and
`traj.spans` are the *same* sequence viewed two ways, and `maxSpans` counts
exactly `traj.spans.length === traj.tools.length` — the number of **tool spans**,
never agent or turn spans.

**Choice: (a) the five exact predicates.** Each maps one-to-one onto a field the
trajectory already holds and is decided by a pure, deterministic comparison —
`checkExpect(traj, spec)` returns `{ pass, reasons }` with one human-readable
reason per failed predicate, and is unit-testable with zero I/O. Specifically:
`tools` checks the ordered tool-name list (subsequence for `in_order`, deep
equality for `exact`); `maxSpans` compares the tool-span count (defined above);
`finishReason` compares the captured `StopReason`; `noToolErrors` asserts every
tool span's `ok`; `maxTokens` compares cumulative `totalTokens`
(`src/kernel/types.ts`, imported as `trace` does at `src/extensions/trace.ts:24`).
These five are exactly the dimensions `trace` already surfaces, which is the proof
they are mechanizable from the bus.

**Why the others are rejected.** (b) is non-deterministic or requires a model
call, which makes `/expect` itself unrepeatable — defeating the entire point of a
*regression* surface — and is the scope balloon §3 names; semantic judgment is
delegated to the `judge` tool over the *output*, where non-determinism is
mockable (D3). (c) is too thin: tool *order* alone misses the most common real
regressions (an extra error, a finish-reason flip from `end_turn` to `stop`/`max
turns`, a token blowup), all of which are cheap exact checks. The five-predicate
set is the minimal *mechanizable* set that covers the regressions `trace` can
already see.

### D3 — The `judge` tool via a recursion-safe tool-less sub-call, not a subagent

**Problem.** Grading a candidate against a rubric needs a model call. How is that
call made so it (i) cannot recurse into the tool-dispatch seam and (ii) stays
cheap and offline-mockable?

**Options.**
- (a) **A recursion-safe tool-less provider sub-call** — call
  `e.agent.providers.get().stream({ ..., tools: [] })` directly with a fixed
  rubric system prompt, parse the one-line reply, exactly as `risk-guard.classify`
  does (`src/extensions/risk-guard.ts:95-121`). Default to cheap effort
  (`thinking` omitted/`"off"`).
- (b) **Spawn a subagent** (`subagents` extension) to grade.

**Choice: (a) tool-less sub-call.** Passing `tools: []` runs the completion
outside the agent loop, so it cannot emit a tool call and re-enter
`beforeToolCall`/dispatch — the same recursion guard `risk-guard` documents
(`src/extensions/risk-guard.ts:88-94`).

**`judge` is declared `executionMode: "sequential"`.** Unlike `risk-guard`, whose
sub-call fires from `beforeToolCall` (no concurrent outer-loop stream in flight),
`judge` runs *inside* `dispatch`, and its inner `provider.stream(...)` consumes
from the **same** provider whose `MockTurn[]` queue the outer agent loop is also
consuming (`MockProvider` dequeues one turn per `stream` call,
`src/providers/mock.ts:42-44`). A *parallel* dispatch (`Promise.all`,
`src/kernel/agent.ts:292`) of a batch containing `judge` could therefore race the
shared queue against any sibling call's turn, making the consumption order — and
thus the scripted-classifier test (§7 #6) — nondeterministic. Marking `judge`
`sequential` makes any batch containing it run in requested order through the
`for … of … await runOne` path (`src/kernel/agent.ts:285-290`): the `judge`
sub-call's queue read happens at a single, deterministic point, with no concurrent
outer-loop `stream` in flight. The scripted `MockProvider` queue is thus consumed
in a fixed order — the agent-loop turns up to and including the turn that invokes
`judge`, then the `judge` sub-call's classifier turn — which is precisely the
ordering §7 #6 asserts against. It is a single streamed completion: cheap,
no nested loop, and — critically — **offline-mockable**, because the sub-call is
just `provider.stream(...)` that the `MockProvider` scripts like any other turn
(D acceptance, §7).

The reply parses with `parseJudgeReply`, a sibling of `parseVerdict`
(`src/extensions/risk-guard.ts:57-67`) with the same total, exception-free shape:

```
parseJudgeReply(reply: string): { score: number; verdict: "pass" | "fail"; reason: string } | undefined
```

- **Reply grammar (pinned).** The classifier system prompt instructs the model to
  reply on **one line**: `SCORE <n>/10 <VERDICT> <reason>`, where `<n>` is an
  integer `0`–`10`, `<VERDICT>` is the literal token `PASS` or `FAIL`
  (case-insensitive), and `<reason>` is the free-text remainder (trimmed, possibly
  empty). Concretely: `SCORE 8/10 PASS clear and correct`. Like `parseVerdict`,
  the parser reads the **first non-empty line**, requires a leading `SCORE` token
  followed by an `<n>/10` fraction it clamps to `0..10`, then the `PASS`/`FAIL`
  token; the rest of the line is `reason`.
- **Failure sentinel (pinned).** A reply missing the `SCORE`/`<n>/10`/verdict
  shape, or an empty reply, returns **`undefined`** — exactly mirroring
  `parseVerdict`'s `Verdict | undefined`. `parseJudgeReply` never throws and never
  fabricates a score; the *tool* wrapper (not the parser) maps that `undefined`
  into an error `ToolResult` (`isError: true`) rather than a silent pass (§7 #5,
  #7). This keeps the pure helper's contract (`… | undefined`) distinct from the
  tool-level contract (an error `ToolResult`).

**Why (b) is rejected.** A subagent spins up a whole nested agent loop — more
code, more latency, and it *can* recurse (it has tools), which is the failure mode
`risk-guard` was specifically designed to avoid. For a one-shot rubric grade,
that machinery is pure overhead. The tool-less sub-call is the cheaper, strictly
safer, and already-proven path.

### D4 — `*.eval.json` scenario format: minimal, offline, self-contained

**Problem.** `/eval <dir>` must drive headless runs deterministically. What does
one scenario file look like?

**Options.**
- (a) **`{ input, mockScript, expect }`** — `input` is the user string passed to
  `agent.run`; `mockScript` is a `MockTurn[]` (the exact shape `MockProvider`
  already consumes, `src/providers/mock.ts:26`) used to script a fresh provider;
  `expect` is a D2 spec object. JSON only, no code.
- (b) A richer format: embedded JS responders, cassette file references,
  per-scenario extension lists, setup/teardown hooks.

**Choice: (a) the three-field JSON object.** Each field reuses a type the kernel
already has — `mockScript` is literally `MockTurn[]`, `expect` is the D2 spec —
so the runner is thin: for each `*.eval.json`, `parseEvalScenario` validates the
object, the runner scripts a fresh `MockProvider` with `mockScript`
(`src/providers/mock.ts:53` `script()`), runs `agent.run(input)`
(`src/kernel/agent.ts:146`) with the `evals` consumer attached, then applies
`checkExpect` to the captured trajectory. The scorecard is `passed/total` plus
the failing scenarios' reasons. Pure JSON keeps scenarios declarative, diffable,
and trivially loadable with `readFileSync` + `JSON.parse` — no eval, no jiti, no
network.

**Why (b) is rejected.** Embedded JS, cassette wiring, and per-scenario extension
graphs are the eval-framework scope §3 defers. A JSON object whose fields are
already-existing kernel types is the minimum that runs an offline scenario
end-to-end; richer needs (a live cassette instead of a mock script) are an
additive extension later. `MockProvider` and `cassette` share the
`request → StreamEvent[]` contract, so swapping in `ReplayProvider`
(`src/providers/cassette.ts:47`) later is a one-line provider substitution, not a
format change.

### D5 — Defer the statistical/eval-awareness machinery (Scope Boundary decision)

**Problem.** A "real" eval framework wants pass@k confidence intervals,
eval-awareness gap measurement, probe rotation, and dataset adapters. Ship them?

**Options.** (a) Ship the thin slice (assertions + scorecard + one judge) and
*document* the rest as deferred. (b) Build toward the full framework now.

**Choice: (a) the thin slice.** The problem statement is "behavior is
observable but never checked" — solved completely by trajectory assertions + a
scorecard runner + one judge. Everything in (b) is a separate, larger problem
(statistical confidence, sandbagging) with its own design, and each piece is
additive on top of this slice.

**Why (b) is rejected.** It is precisely the scope balloon this design's primary
risk (§8) names. Building inferential statistics and eval-awareness probes before
the basic assertion surface exists inverts the priority and multiplies the code
for no near-term win. Deferring them — explicitly, in §3 — keeps the slice
shippable and reviewable.

### D6 — The security regression set is plain tests, not a new primitive

**Problem.** The spec asks for coverage that the safety guards still fire on
known attacks. Where does that live?

**Options.** (a) A `test/security/` directory of `node:test` files using the
existing offline harness. (b) A new runtime "security suite" extension/primitive
that self-checks the guards.

**Choice: (a) tests.** Each guard already ships its own unit tests; what is
missing is an *attack-shaped regression* per guard — e.g. a `flow-guard`
read-secret-then-fetch chain, a `bash-policy` `rm -rf` deny, a `write-guard`
blind overwrite — wired through `makeHarness` + `host.use`, asserting the call is
blocked/asked. That is exactly what `node:test` is for; it needs no runtime
machinery.

**Why (b) is rejected.** A runtime self-checking primitive is new core surface to
do what a test file does, and it would itself need testing. Tests are the
lighter, conventional, zero-new-code answer. (This decision is "tests vs. a new
primitive" — a behavioral choice between two real mechanisms, not a single
foregone option.)

## 5. Dependencies and Assumptions

- **Bus payloads (existing, unchanged):** `agent_start`, `tool_start`,
  `tool_end`, `usage`, `agent_end` with the shapes in
  `src/kernel/events.ts:11-38`. The trajectory builder reads only these.
- **`MockProvider` / `cassette` for determinism.** Scenarios script
  `MockProvider` (`src/providers/mock.ts`); the same `request → StreamEvent[]`
  contract means `ReplayProvider` (`src/providers/cassette.ts`) is a drop-in for a
  later cassette-backed scenario without a format change.
- **Provider sub-call for `judge`.** `e.agent.providers.get()` returns the
  default provider; `provider.stream({ tools: [], ... })` is the recursion-safe
  grading call (`src/extensions/risk-guard.ts:96-117`). Assumes a provider is
  registered; if none is, `judge` returns an explicit error result (fails closed
  on grading, never throws into the loop).
- **`judge` runs `sequential` for deterministic queue consumption.** Because the
  `judge` sub-call (running inside `dispatch`) and the outer agent loop draw turns
  from the *same* provider — the `MockProvider` queue under test
  (`src/providers/mock.ts:42-44`) — `judge` is registered with
  `executionMode: "sequential"` (`src/kernel/define.ts:15`,
  `src/kernel/types.ts:147`). This forces any batch containing it through the
  in-order `for … of … await` dispatch path (`src/kernel/agent.ts:285-290`) rather
  than the parallel `Promise.all` path (`src/kernel/agent.ts:292`), so the queue is
  consumed in a single, fixed order with no concurrent outer-loop `stream`. The
  §7 #6 test depends on exactly this ordering (D3).
- **`ExtensionAPI` surface:** `e.on`, `e.registerCommand`, `e.registerTool`,
  `e.store`, `e.agent.{providers,model}`, `e.log`
  (`src/kernel/extension.ts:41-78`). No new API is required.
- **House rules:** ESM with `.js` specifiers even for `.ts`; strict TS
  (`noUncheckedIndexedAccess`, no `any`); zero runtime deps beyond `jiti` (pure
  Node — `readFileSync`/`readdirSync` for the runner); offline `node:test` via
  `makeHarness`; `EAGENT_EVALS=off` kill switch; dispose loop that never throws.
- **Assumption — no capability needed.** The consumer and `/expect` have no side
  effects (in-memory reads of the bus). The `judge` tool's only effect is a
  provider sub-call, which the kernel already exposes to extensions without a new
  capability (as `risk-guard`/`memory` do). The `/eval` runner reads files from a
  caller-named directory under the workspace; reading a path the user explicitly
  passes is not a privileged side effect (cf. `trace-save` writing under
  `~/.eagent` with no capability, `src/extensions/trace.ts:235`). So no
  `grantCapability` call is made.

## 6. Relationship with Existing Designs

This is **not** a first-of-its-kind design; it sits deliberately atop three
existing pieces and de-duplicates against each:

- **`trace` (`src/extensions/trace.ts`) — closest relative.** `evals` mirrors
  trace's pure-consumer span model (`src/extensions/trace.ts:26-50, 98-173`):
  same events, same `safe()` wrapping, same reset-on-`agent_start`. **Dedup:**
  `trace` *records and renders* spans (`/trace`, `/usage`); it has no notion of a
  *checked expectation*. `evals` *asserts* over the same data. They are
  complementary consumers of one bus — the canonical "add a consumer, get a view"
  pattern trace's own header describes (`src/extensions/trace.ts:13-16`). No
  conflict: both can be loaded together; neither shadows the other's commands
  (`/trace`/`/usage` vs `/expect`/`/eval`).

- **`cassette` (`src/providers/cassette.ts`) — determinism substrate.** `evals`
  runs scenarios against `MockProvider` (and, later, `ReplayProvider`). **Dedup:**
  cassette is *order-based record/replay* of an event stream
  (`src/providers/cassette.ts:64-70`); it has no assertions and no scorecard.
  `evals` is the assertion/scorecard layer *over* deterministic runs cassette/mock
  make possible. No conflict.

- **`risk-guard` (`src/extensions/risk-guard.ts`) — the judge sub-call pattern.**
  `judge` reuses risk-guard's recursion-safe tool-less `provider.stream({ tools:
  [] })` classifier (`src/extensions/risk-guard.ts:95-121`) and a `parseVerdict`-
  shaped reply parser (`src/extensions/risk-guard.ts:57-67`). **Dedup:**
  risk-guard *gates a tool call* on a SAFE/RISKY verdict via `beforeToolCall`;
  `judge` *grades an arbitrary candidate* against a rubric and returns a score —
  same mechanism, different purpose. No conflict; the patterns coexist.

- **`npm test` / `makeHarness` (`test/helpers.ts`).** Unit-tests primitives in
  isolation. **Dedup:** it asserts a *unit*'s behavior, not *end-to-end trajectory
  + output grading*. `evals` is the behavior-grading layer on top, and its own
  tests run *through* `makeHarness`.

Conflicts: **none.** `evals` adds two commands (`/expect`, `/eval`) and one tool
(`judge`); none collide with existing command/tool names (verified against the
extension list — `trace`/`usage`/`trace-save`, `risk-guard`, `flow-guard`,
`bash-policy`, etc.). It merges several scattered eval findings into one tight
harness rather than spreading them.

## 7. Acceptance Criteria

All criteria are runnable assertions in `test/evals.test.ts` (and `test/security/`)
under `makeHarness`, offline, with the extension loaded via `host.use`.

1. **Trajectory build.** Given a scripted `MockProvider` run that issues, in
   order, tool calls `[A, B]` then a final text turn, the trajectory's ordered
   tool-name list equals `["A","B"]`, its tool-span count is exactly `2`
   (`traj.spans.length === traj.tools.length === 2` — tool spans only, per D2's
   "Span set"; the agent/turn spans are not counted), and its captured
   `finishReason` equals the run's `RunResult.reason` (`src/kernel/agent.ts:238`).
   *Assertion: `assert.deepEqual(traj.tools, ["A","B"])`;
   `assert.equal(traj.spans.length, 2)`.*
2. **`/expect tools in_order` passes and fails correctly.** For the run in (1),
   `checkExpect(traj, { tools: ["A","B"], order: "in_order" }).pass === true`;
   `checkExpect(traj, { tools: ["B","A"], order: "in_order" }).pass === false`
   and `.reasons` names the order mismatch.
3. **`/expect exact / maxSpans / finishReason / noToolErrors / maxTokens` each
   gate.** A passing spec returns `{pass:true, reasons:[]}`; flipping each single
   predicate to a violated value returns `pass:false` with exactly that
   predicate's reason — five independent assertions.
4. **`noToolErrors` catches a real error.** A scripted run whose tool result has
   `isError:true` (a genuine failed call through the loop, as
   `test/recovery.test.ts:108` does) yields a trajectory with that span `ok:false`
   and `checkExpect(traj,{noToolErrors:true}).pass === false`.
5. **`parseJudgeReply` is pure and total.**
   `parseJudgeReply("SCORE 8/10 PASS clear and correct")` (the pinned grammar,
   §4 D3) yields exactly `{ score: 8, verdict: "pass", reason: "clear and correct" }`;
   an empty reply and a garbled reply (e.g. `"hello world"`, missing the
   `SCORE`/`<n>/10`/verdict shape) each yield **`undefined`** (the pinned failure
   sentinel — never a throw, never a fabricated score). Table-driven, no I/O.
   *Assertion: `assert.deepEqual(parseJudgeReply("SCORE 8/10 PASS clear and
   correct"), { score: 8, verdict: "pass", reason: "clear and correct" })`;
   `assert.equal(parseJudgeReply(""), undefined)`.*
6. **`judge` tool against a scripted classifier.** With the `MockProvider` queue
   scripted so that the turn invoking `judge` is followed by a judge-shaped reply
   turn (`SCORE 8/10 PASS …`) — the deterministic consumption order guaranteed by
   `judge` being `sequential` (§4 D3, §5), so the sub-call reads the next queued
   turn with no concurrent outer-loop `stream` racing it — invoking the `judge`
   tool (rubric + candidate) returns a `ToolResult` whose parsed `details`/`content`
   carry the expected `{score, verdict, reason}`. *Assertion: on the tool result.*
7. **`judge` fails closed without a provider verdict.** When the scripted reply
   is unrecognizable (or no usable reply) — i.e. `parseJudgeReply` returns
   `undefined` (§4 D3) — the `judge` *tool* wrapper maps that sentinel into an
   error `ToolResult` (`isError:true`) rather than throwing or silently passing.
8. **`/eval` runner over an inline fixture.** Given a directory holding one tiny
   `*.eval.json` (`{input, mockScript, expect}`) whose `expect` matches the
   `mockScript`'s trajectory, `/eval <dir>` prints a `1/1` scorecard; given a
   second fixture whose `expect` is violated, the scorecard is `1/2` and names the
   failing scenario. *Assertion: on the printed lines via the command's `print`.*
9. **Kill switch.** With `EAGENT_EVALS=off`, loading the extension registers no
   live consumer/commands/tool effects: the trajectory stays empty after a run and
   `/expect` reports the disabled state (or is a no-op) — asserted exactly as
   `test/recovery.test.ts:149` asserts `EAGENT_RECOVERY=off`.
10. **Clean dispose.** After `host.unload("evals")`, a subsequent `agent.run`
    leaves no `evals` consumer attached (trajectory not updated) and the `/expect`
    / `/eval` commands and `judge` tool are gone — no leak, mirroring
    `test/recovery.test.ts:173`.
11. **Security regression set fires.** In `test/security/`, each of `flow-guard`,
    `content-guard`, `secret-guard`, `bash-policy`, `write-guard` is driven through
    `makeHarness` with a known attack and asserted to still take its defining
    action — one runnable assertion per guard, all offline. The four gating guards
    (`flow-guard`, `secret-guard`, `bash-policy`, `write-guard`) are asserted to
    **block or ask** (per that guard's mode) on `beforeToolCall`; `content-guard`,
    which rides `afterToolCall` and never blocks or asks, is instead asserted to
    **sanitize and label** the foreign payload (invisible-Unicode strip +
    provenance envelope).

## 8. Risks and Rollback

- **Risk — scope balloon into a full eval framework.** *Mitigation:* ship only
  the thin slice (trajectory assertions + scorecard runner + one judge tool); the
  statistical/eval-awareness/dataset machinery is deferred and *documented* as
  such (§3, §4 D5). The acceptance criteria (§7) bound exactly what is built.
- **Risk — judge non-determinism makes tests flaky.** *Mitigation:* the judge is
  a single `provider.stream` sub-call (D3) that `MockProvider` scripts
  deterministically, so every judge test is offline and repeatable (§7 #6, #7).
  Against a live provider the judge is `thinking:"off"`/cheap by default; it never
  runs in `npm test`.
- **Risk — out-of-order or missing bus events corrupt the trajectory.**
  *Mitigation:* the consumer wraps each handler in `safe()` (a throw is logged,
  never escapes) and folds defensively, exactly as `trace` does
  (`src/extensions/trace.ts:88-96, 149-163`); a mismatched event degrades the
  trajectory, never the run.
- **Risk — `/eval` reading a bad/huge directory.** *Mitigation:* the runner only
  reads `*.eval.json` files the user names, parses each with `parseEvalScenario`
  (a malformed file is reported as a failed scenario, not a thrown runner), and
  does pure JSON parsing — no code execution, no network.
- **Rollback.** The extension is purely additive (no kernel change, no new
  capability, no built-in registration in this task). The kill switch is
  `EAGENT_EVALS=off`; full removal is `host.unload("evals")` or deleting
  `src/extensions/evals.ts` — nothing else depends on it. The `test/security/`
  files are independent regression tests and can stay or go on their own.
