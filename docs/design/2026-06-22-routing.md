# Design: `routing` — difficulty-aware per-turn model tiering

Slug: `2026-06-22-routing`
Status: closed
Closing-commit: e20db1a
Closed-on: 2026-06-23
Deferred: none

## 1. Background and Purpose

EAgent runs **one configured model per provider per run**. `Agent.model` is a
public, mutable string field (`src/kernel/agent.ts:72`, defaulted at `:98`), and
the agent loop re-reads `this.model` on **every** turn — once when assembling the
`transformContext` payload (`agent.ts:262`) and again when building the provider
request (`agent.ts:269`, the request's `model` field). So a turn's model is
whatever `this.model` holds at the top of that turn; nothing in the kernel pins
it for the lifetime of a run.

Two adjacent extensions touch model/cost but neither picks a tier per turn:

- **`cost`** (`src/extensions/cost.ts`) *measures* spend — it maps the provider's
  reported `usage` into USD via a date-pinned price card (`cost.ts:52-69`,
  `:206-231`) and flags anomalies. It is observability only and, by its own
  charter, "never changes which model runs" — it reads `e.agent.model`, it does
  not write it.
- **`subagents-least-privilege`** lets a `spawn_agent` caller override a *child's*
  `provider`/`model` (validated against the registry, `subagents.ts:77-88`), but
  it overrides a child per *spawn*, statically supplied by the caller. It does
  **not** auto-classify difficulty to choose a tier per turn.

The gap: a trivial turn ("rename this variable", "what's 2+2", a one-line
acknowledgement) burns flagship-model tokens at flagship prices, while a hard
turn ("design the migration", "debug this race") needs the flagship. Tools like
PilotDeck route trivial work to a cheap model and reserve the flagship for the
hard turns, cutting cost with no kernel surgery.

This design adds a **new `routing` extension** that, per turn, classifies
difficulty with a **cheap deterministic heuristic** (default) and assigns
`Agent.model` to the matching tier from a store-configurable tier map, then
**restores** the user's configured model when routing is disabled or at
`agent_end`. It reuses the existing mutable `Agent.model` seam — **zero kernel
change** — and, because `subagents-least-privilege` already lets a spawned child
carry its own model, a routed parent and a routed child compose. Off by default,
`EAGENT_ROUTING=off`, no capability beyond the optional sub-call.

What happens if we do not build it: every turn pays the flagship rate regardless
of difficulty; the only lever today is to globally downgrade the model (losing
the flagship on hard turns) or to hand-route via `spawn_agent` (manual,
per-spawn, not per-turn).

## 3. Scope Boundary (NON-goals — Simplicity First)

- **No kernel change.** Everything rides the *existing* public mutable
  `Agent.model` (`agent.ts:72`) that the loop already re-reads each turn
  (`agent.ts:262`, `:269`). No new hook, no new field, no new "model selector"
  seam (D1).
- **No new capability for the default path.** The heuristic classifier reads only
  the transcript the extension is already handed (message text, tool-result
  sizes); it performs no side effect, so it declares no capability — the same
  posture as `cost` and the heuristic guards. The **optional** sub-call reuses the
  capability-free, recursion-safe provider call (risk-guard / `memory`'s pattern),
  which also declares no capability (D2, §4).
- **Not a privilege/auto-mode classifier.** This routes by **cost/difficulty** and
  changes the **model**. It does **not** read, set, or gate capabilities; it is
  orthogonal to the capability layer (D5). The rejected "tiered auto-mode
  privilege classifier" that competed with the capability layer is explicitly
  *not* this.
- **Not a cost meter.** `routing` changes the model; `cost` prices the tokens.
  This extension declares no price card and emits no USD figure — it pairs with
  `cost`, it does not duplicate it (§6).
- **No per-tool or per-message-content rewriting.** It only assigns `Agent.model`;
  it never touches `transformContext`, tool arguments, or the system prompt.
- **No learned/adaptive classifier, no feedback loop, no per-model accuracy
  tuning.** The default heuristic is a small, fixed, deterministic function;
  there is no online learning, no telemetry, no auto-tuning of thresholds.
- **No more than two tiers required.** The default tier map is `{cheap, flagship}`
  (D3). The store may hold more entries, but the default heuristic resolves to one
  of those two; a richer N-tier policy is out of scope for v1.
- **No permanent session-model change.** The override is **per turn**; the
  configured model is always restored on disable / `agent_end` (D4). Routing must
  never leave the session pinned to a tier after a run ends.
- **No routing of the optional classifier sub-call itself.** When the optional
  sub-call is used, it runs on the *currently configured* model
  (`e.agent.model` at call time), exactly as risk-guard's classifier does
  (`risk-guard.ts:128`) — we do not recursively route the router.

## 4. Key Design Decisions

### D1 — Per-turn model override: reuse the existing mutable `Agent.model` vs. a new kernel seam

- **Problem.** To run a turn on a chosen tier, that turn's model must be settable
  from an extension, per turn, without forking the kernel.
- **Options.**
  1. **Reuse `Agent.model`** — assign `e.agent.model = tierModel` on `turn_start`;
     the loop reads `this.model` on the very next provider request
     (`agent.ts:269`) and `transformContext` (`agent.ts:262`).
  2. **Add a new kernel seam** — e.g. a `selectModel` filter on the loop, or a
     `modelFor(turn)` hook the loop consults before each request.
- **Choice: option 1 (reuse `Agent.model`).** `Agent.model` is already `public`
  and mutable (`agent.ts:72`), and the loop re-reads `this.model` **every turn**
  at request-build time (`agent.ts:269`) — assigning it on `turn_start` (emitted
  at `agent.ts:180`, *before* `streamTurn`) is read by that same turn's request.
  `cost` already proves an extension may *read* `e.agent.model` live
  (`cost.ts:163`/`:203`, where it stamps its lookup model); writing it is the
  symmetric, already-supported move.
  Zero kernel change, which is the EAgent thesis ("new behavior is always an
  extension, never a fork", CLAUDE.md).
- **Why a new kernel seam was rejected.** A `selectModel` filter would add a hook
  the kernel must define, document, and maintain forever — to do what assigning an
  *already-public, already-per-turn-read* field does for free. It would also be a
  second source of truth for "what model is this turn?" alongside `this.model`,
  inviting drift (e.g. `cost` reads `this.model`, the new hook sets something
  else). The field already *is* the per-turn seam; adding a parallel one violates
  Simplicity First and the seven-primitives charter. The only thing the field
  lacks is auto-restore, which this extension supplies in userland (D4), not the
  kernel.
- **Ordering note (load-bearing).** `turn_start` fires at `agent.ts:180`, which is
  *before* `streamTurn(turn)` at `agent.ts:182`; `streamTurn` reads `this.model`
  at `:262`/`:269`. So a `turn_start` handler that sets `e.agent.model` is
  guaranteed to be observed by the turn it fires for. This is asserted directly
  (AC-1).

### D2 — Classifier: deterministic heuristic (default) vs. an LLM sub-call

- **Problem.** Difficulty must be judged cheaply enough that the judging itself
  does not erase the savings, and offline-testably.
- **Options.**
  1. **Deterministic heuristic** — a pure function of signals already in hand
     (latest user-message length, presence of difficulty keyword cues, recent
     tool-result byte size), returning a tier. Zero cost, deterministic, offline.
  2. **LLM sub-call** — a recursion-safe, tool-less provider call (the risk-guard
     pattern, `risk-guard.ts:96-137`) that asks the model to rate the turn.
  3. **Hybrid** — heuristic by default, with the sub-call available when
     explicitly configured (`mode: "llm"` in the store).
- **Choice: option 3 — heuristic default, optional sub-call.** The **default** is
  the deterministic heuristic (option 1): it is free (no round-trip), deterministic
  (a property the test suite requires — `MockProvider` aside, the classifier must
  not need a model), and offline by construction. The heuristic is intentionally
  small: a turn is `flagship` if any of {latest user text length ≥ `HARD_CHAR_LEN`,
  any cue in `HARD_KEYWORD_CUES` is present (whole-word, case-insensitive, matching
  the `microagents` trigger-match shape), the most recent tool-result content
  exceeds `HARD_TOOL_RESULT_BYTES`}; otherwise `cheap`. These three thresholds are
  **pinned named constants with concrete defaults**, mirroring how `cost.ts` pins
  `ANOMALY_K`/`WINDOW_SIZE` (`cost.ts:114-118`):
  - `HARD_CHAR_LEN = 280` — a turn whose latest user text is ≥ 280 chars
    (≈ a long paragraph, the "design the migration"/"debug this race" shape)
    routes flagship; a one-liner ("rename this variable", "what's 2+2") stays cheap.
  - `HARD_KEYWORD_CUES = ["debug", "design", "architect", "refactor", "migrate",
    "optimize", "race", "deadlock", "security", "vulnerability", "proof", "prove",
    "algorithm", "concurrent", "concurrency"]` — a fixed, lowercase default cue set,
    matched whole-word and case-insensitively. Operator-overridable via the store
    (same surface as the tier map).
  - `HARD_TOOL_RESULT_BYTES = 8192` — a most-recent `tool_result` whose content
    exceeds 8 KiB signals a large, dense context worth the flagship.
  All three are store-overridable (re-read each turn, like the tier map, D3); the
  constants are the **defaults**, so the default heuristic — which *is* the default
  path — is fully specified without operator configuration.
  When the operator opts in (`/routing mode llm` or a store flag), difficulty is
  instead judged by a **recursion-safe tool-less sub-call** that reuses
  risk-guard's exact shape (`provider.stream({ systemPrompt, messages, tools: [],
  model: e.agent.model, signal })`, `risk-guard.ts:124-132`), parsing a short
  `CHEAP`/`HARD` verdict the way `parseVerdict` parses `SAFE`/`RISKY`
  (`risk-guard.ts:58-68`). The sub-call **fails open to the heuristic** (or, if
  even that is unavailable, to flagship — D-conservative below), never to a throw.
- **Why heuristic-only was rejected.** A heuristic alone cannot read intent it has
  no signal for (a short prompt that is genuinely hard); leaving *no* escape hatch
  would force such users to disable routing entirely. The optional sub-call is the
  escape hatch, paid for only when explicitly turned on.
- **Why LLM-only (no heuristic) was rejected.** Putting a model round-trip in
  front of *every* turn to decide difficulty is the exact cost/latency
  anti-pattern risk-guard calls out (`risk-guard.ts:78-95` / its design §4.1) — and
  worse here, because the whole point is to *save* cost. It would also make the
  default path non-deterministic and require a provider to test the common case.
  The heuristic must be the default; the LLM is the opt-in.
- **Conservative-on-unsure rule.** When the classifier cannot decide (heuristic
  signals absent *and* no opt-in sub-call, or the sub-call failed open and the
  heuristic is also indeterminate), it returns **flagship**, never cheap — a wrong
  call should over-spend, not under-serve (Risk §8). This is a behavioral choice
  (default-to-flagship vs. default-to-cheap), justified by "a hard turn on a cheap
  model fails the user; a trivial turn on the flagship merely costs a little
  more."

### D3 — The tier map: store-configurable `{cheap, flagship}` with date-pinned defaults

- **Problem.** A tier name (`cheap`/`flagship`) must resolve to a concrete model
  id, and that mapping must be operator-overridable without code change.
- **Options.**
  1. **A two-key store map** `{ cheap: <modelId>, flagship: <modelId> }`, seeded
     with date-pinned defaults, overridable live via `/routing tier …`.
  2. **A small ordered list** of model ids (index 0 = cheapest) with the heuristic
     returning an index.
  3. **Hardcoded model ids** in the extension source.
- **Choice: option 1 (named two-key store map).** A named map reads clearly at the
  call site (`tierMap.cheap`), survives an operator override of *just one* tier,
  and maps one-to-one onto the heuristic's binary `cheap`/`flagship` output. It
  mirrors `cost`'s store-override-merged-over-defaults pattern exactly
  (`cost.ts:186-194`, `activeCard()`): re-read on every turn so a mid-session
  `/routing tier …` takes effect on the next turn.
- **Date-pinned defaults (and why these).** The default flagship is a date-pinned
  **flagship Claude** model id and the default cheap is a date-pinned **cheap
  Claude** model id, chosen to match the families `cost.ts` already prices
  (`cost.ts:52-62`: `claude-opus-*` flagship rates, `claude-sonnet-*`/`-fable-*`
  cheaper) so a routed run is priced coherently by the sibling extension. The
  exact ids are pinned with a `// as of 2026-06-22` comment (the same staleness
  mitigation `cost.ts:43` uses) and are fully store-overridable, so a deployment on
  a different vendor (`gpt-4o`, `gemini-2.0-flash`, both in `cost`'s card) sets its
  own pair. **In the offline test suite both tiers are registered `MockProvider`
  model ids** (e.g. `mock-cheap`, `mock-flagship`) so the default Claude ids never
  need a network — the test overrides the map (AC-1).
- **Why an ordered list was rejected.** An index-into-a-list is less legible
  (`tiers[0]` vs. `cheap`), makes a single-tier override clumsy (you must re-supply
  the whole list to change one), and offers an N-tier generality this v1 heuristic
  (binary cheap/flagship — §3) does not use — speculative, against Simplicity
  First. If a future design needs graded tiers, it can widen the map; the binary
  default needs only two names.
- **Why hardcoded ids were rejected.** Hardcoding strands every non-Claude
  deployment and makes the model-id staleness un-fixable without a code edit — the
  exact problem `cost`'s overridable price card was built to avoid.
- **Validate-and-fall-back (the unresolvable-tier guard).** The validation
  surface is **the configured tier map itself**, *not* the provider registry. This
  is a deliberate correction of an earlier draft: `ProviderRegistry`
  (`registry.ts:73-83`) keys by **provider name**, not model id (`get(name)` ⇒
  `this.#providers.get(name ?? this.#default ?? "")`), so there is *no* "is this
  model id registered?" query to make — the registry cannot validate a model id,
  and `subagents-least-privilege` is **not** a precedent for one (its
  `resolveChildProvider` validates the *provider name* via
  `parent.providers.get(args.provider)` and accepts **any** non-empty string as
  the model with zero registry check, `subagents.ts:354`/`:362`). So "validate"
  here is concrete and self-contained: when the heuristic returns a tier name, the
  extension looks that name up in the live tier map (`tierMap[tier]`); a tier whose
  entry is **missing or not a non-empty string** (e.g. an operator typo'd
  `/routing tier cheap` to empty, or a tier name the map has no key for) falls back
  to the captured configured baseline (logged via `e.log.warn`), never a throw.
  The conservative guarantee is "never assign a tier we cannot resolve to a
  concrete model id from our own map; fall back to the configured baseline." This
  guards what we can actually observe — the map is ours, the registry's model space
  is not — and it is fully automatable against a known surface (AC-7). What we do
  **not** and **cannot** check is whether a *well-formed, present* tier id is one
  the downstream provider will accept: that is the provider's job (an unknown id is
  surfaced by the provider call as a normal turn error), exactly as it is today for
  the operator-configured `Agent.model` and for a `spawn_agent` `model` override.

*(Pure string/format sub-choices that self-justify as non-behavioral: the env var
name `EAGENT_ROUTING`, the tier key names `cheap`/`flagship`, the verdict tokens
`CHEAP`/`HARD`, and the classifier system-prompt wording are fixed constants with
no behavioral fork. The three heuristic threshold **defaults** —
`HARD_CHAR_LEN = 280`, `HARD_TOOL_RESULT_BYTES = 8192`, and the
`HARD_KEYWORD_CUES` default cue set — are **behavioral** and so are pinned as named
constants in D2 above, not left to the implementer; they are store-overridable, but
the pinned defaults make the default heuristic path fully specified, exactly as
`cost.ts` pins `ANOMALY_K`/`WINDOW_SIZE` (`cost.ts:114-118`).)*

### D4 — Restore the configured model on disable / `agent_end` (the override is per-turn, never permanent)

- **Problem.** Mutating `Agent.model` is global to the agent; other consumers read
  it live (`cost`'s `agent_start` re-stamp `cost.ts:203`, the `/cost` status line).
  Routing must not leave the session pinned to a tier after a run, nor when it is
  turned off mid-session.
- **Options.**
  1. **Capture-and-restore** — on `agent_start`, capture `e.agent.model` as the
     restore baseline; on `agent_end`, assign it back. On `/routing off` (or
     `EAGENT_ROUTING=off`), immediately restore the captured baseline and stop
     assigning.
  2. **Set-and-leave** — assign the tier and let the next run / next router pass
     fix it; never restore.
- **Choice: option 1 (capture-and-restore).** The capture mirrors how `cost`
  re-stamps `activeModel = e.agent.model` on `agent_start` (`cost.ts:203`) — the
  configured model at run start is the ground truth. Restoring on `agent_end`
  (emitted at `agent.ts:247`, inside the loop's `finally`, so it runs even on
  error/abort) guarantees the session model is exactly what the user configured
  the moment a run ends. On disable, the same baseline is restored so a
  mid-session toggle does not strand the session on a cheap tier. This makes the
  override observably *per-turn-scoped*, the property AC-3/AC-4 assert.
- **Why set-and-leave was rejected.** It would leak a tier into the next run and
  into every other live reader of `e.agent.model` (e.g. a `/cost` status query
  between runs would report the cheap tier as "the model", confusingly), and a
  run that ends mid-route would leave the session pinned to whatever the last turn
  picked. Per-turn means per-turn; not restoring breaks that contract and the
  rollback story (§8).

### D5 — This is cost/difficulty routing of the MODEL, not the rejected privilege/auto-mode classifier

- **Problem.** A prior rejected idea — a "tiered auto-mode classifier" — proposed
  auto-selecting a *privilege/capability* tier per turn. This design must be
  clearly distinct so it does not re-introduce that rejected coupling.
- **Options.**
  1. **Route the model only** — the classifier's output selects a *model id*;
     capabilities are untouched.
  2. **Route privilege too** — the classifier also sets a capability profile
     (the rejected auto-mode shape).
- **Choice: option 1 (model only).** The classifier returns a tier name that
  resolves to a *model id* assigned to `Agent.model`. It never reads
  `e.agent.capabilities`, never grants/denies, never gates a tool. It is
  **orthogonal** to the capability layer: a routed turn has exactly the same
  permissions as an un-routed one.
- **Why routing privilege was rejected.** Coupling difficulty to privilege is the
  exact design that was rejected for competing with the capability layer —
  capabilities are EAgent's single security vocabulary (CLAUDE.md, "Capabilities
  are the security vocabulary"), enforced by the dispatcher (`agent.ts:343-345`),
  and a second, difficulty-driven privilege selector would be a parallel authority
  with no audit trail and a confusing security model (a "trivial" turn silently
  losing or gaining permissions). Routing the **model** is a pure
  cost/quality lever with no security semantics; keeping the two orthogonal is the
  whole point of calling this `routing` and not `auto-mode`.

### D6 — Off by default + `EAGENT_ROUTING=off` (it changes behavior; opt-in)

- **Problem.** Should routing run by default?
- **Options.**
  1. **Off by default**, enabled via `/routing on` (store flag) /
     `EAGENT_ROUTING` env, hard-disabled by `EAGENT_ROUTING=off`.
  2. **On by default.**
- **Choice: option 1 (off by default).** Routing *changes which model runs* — a
  behavior change with a quality/cost trade-off the operator must opt into, not a
  silent default. This mirrors `risk-guard` (off by default because it changes
  behavior and adds a paid call — its design §4.2) and `bash-policy` (no-op by
  default). `EAGENT_ROUTING=off` is the absolute kill switch regardless of the
  store flag (the `cost.ts:150` pattern: env `off` short-circuits activation to a
  no-op `() => {}`).
- **Why on-by-default was rejected.** Silently downgrading some turns to a cheaper
  model changes output quality for every existing user with no opt-in — a
  surprising default. A user who has tuned their run to a specific flagship model
  would see unexplained quality variance. Off-by-default keeps least-surprise and
  Simplicity First; the always-on baseline stays "the configured model, every
  turn."

## 5. Dependencies and Assumptions

- **Depends on** `Agent.model` being a public, mutable field (`agent.ts:72`,
  defaulted `:98`) that the loop re-reads each turn at request-build time
  (`agent.ts:269`) and for `transformContext` (`agent.ts:262`). The whole design
  is a no-op if this stops being true — it is the single load-bearing kernel fact
  (asserted indirectly by AC-1/AC-2).
- **Depends on** the hook ordering `turn_start` (`agent.ts:180`) firing **before**
  `streamTurn` (`agent.ts:182`), and `agent_start` (`agent.ts:162`) /
  `agent_end` (`agent.ts:247`, in `finally`) for capture/restore.
- **Depends on** `ExtensionAPI`: `e.on("agent_start"|"turn_start"|"agent_end")`,
  `e.agent.model` (read + write), `e.store` get/set (the tier map — the **sole
  tier-resolution surface**, since the registry keys by provider name not model id,
  D3 — plus the enabled flag + mode), `e.registerCommand`, `e.log`. The optional
  LLM sub-call additionally reads `e.agent.providers` to obtain a provider to
  `stream` against (`registry.ts:73-83`); the **default heuristic path touches the
  registry not at all**. All on the current public surface (`extension.ts:41-78`).
- **Depends on**, for the optional sub-call only, the recursion-safe tool-less
  provider call (`provider.stream({ tools: [], model: e.agent.model, signal })`,
  the risk-guard/`memory` pattern, `risk-guard.ts:124-132`) and a lenient
  `CHEAP`/`HARD` verdict parser modeled on `parseVerdict` (`risk-guard.ts:58-68`).
- **Assumes** the default heuristic's signals are all already in hand on
  `turn_start`: the latest user message text and the most recent tool-result
  content are both readable from `e.agent.messages` (the transcript handle,
  `agent.ts:104-106`), so the heuristic needs no new data source and no
  capability.
- **Offline-test assumption.** `MockProvider` is deterministic and scriptable
  (`src/providers/mock.ts`); the test registers two model tiers as plain string
  ids in the overridden tier map (e.g. `mock-cheap`/`mock-flagship`) and asserts
  per-turn which id reached the request via a `MockProvider` responder that reads
  `req.model` (`mock.ts:63`, the request carries `model` from `agent.ts:269`), and
  via a `turn_start` spy reading `e.agent.model`. No network, no API key.
- **Zero new runtime dependencies** (jiti-only house rule). Pure Node + existing
  kernel modules.

## 6. Relationship with Existing Designs

Closest existing **code** (all read in full to ground this design):

- **`src/kernel/agent.ts`** — the seam this design reuses: `Agent.model` public
  mutable field (`:72`, `:98`), read each turn at `:262` (`transformContext`
  payload) and `:269` (the provider request's `model`); `turn_start` emitted at
  `:180` before `streamTurn` (`:182`); `agent_start` `:162`; `agent_end` `:247`
  (in `finally`). The `handle.model` accessor (`:120`) shows model is already a
  live-read value extensions consume.
- **`src/extensions/cost.ts`** — the **pairing** sibling: it *measures* spend
  (price card `:52-69`, `usage` consumer `:206-231`) by stamping its lookup model
  `activeModel = e.agent.model` **once at `agent_start`** (`:203`); it explicitly
  never writes the model. `routing` *writes* the model to *reduce* the spend `cost`
  measures, and the savings appear in `cost`'s **aggregate** (a routed run's total
  is genuinely lower). **They compose only at the aggregate level, not per tier:**
  because `cost` prices the whole run against its run-start `activeModel` and does
  *not* re-read `e.agent.model` per usage event, a run with mixed-tier turns is
  attributed entirely to the run-start model in the per-model breakdown
  (`:273-283`) — so that breakdown does **not** split a single run's spend across
  cheap/flagship (see §8 "Known limitation"). This design copies `cost`'s
  store-override-over-defaults pattern (`activeCard()`, `:186-194`) for its tier
  map and its kill-switch no-op (`:149-152`).
- **`src/extensions/subagents-least-privilege.ts`** (design closed,
  `2026-06-22-subagents-least-privilege.md`) — the per-spawn provider/model
  override (`subagents.ts:77-88`) that lets a **spawned child** carry its own
  model. `routing` reuses *that already-supported child model override* so a routed
  parent's children are independently routable; `routing` itself routes the
  **parent's per-turn** model, which subagents-lp does not. **Note (not a
  validation precedent):** `resolveChildProvider` (`subagents.ts:354`, `:362`)
  validates only the *provider name* against the registry and accepts **any**
  non-empty string as the model with no registry check — so it is *not* a model-id
  validation precedent; `routing`'s tier guard validates against its own tier map
  instead (D3).
- **`src/extensions/risk-guard.ts`** — the source of the **optional** classifier
  shape: the recursion-safe tool-less sub-call (`:96-137`, `tools: []`,
  `model: e.agent.model`), the lenient single-line verdict parser (`parseVerdict`,
  `:58-68`), off-by-default gating + `/risk-guard` command + env kill switch
  (`:78-84`, `:157-184`). `routing` copies this shape for its `mode: "llm"` path
  and its command/kill-switch ergonomics.
- **`src/kernel/registry.ts`** — `ProviderRegistry.get`/`list` (`:73-83`) keys by
  **provider name**, not model id, so it cannot validate a tier *model id* — read
  to establish the negative that grounds D3's "validate against the tier map, not
  the registry" choice. Used only by the optional LLM sub-call (to fetch a
  provider to `stream`), never by the default tier guard.

**De-duplication (why this is not an existing extension).**

- **Not `cost`.** `cost` only *measures* (reads `e.agent.model`, prices tokens);
  it never changes which model runs. `routing` *changes* the model to reduce
  spend. They are complementary (measure vs. act), not overlapping.
- **Not `subagents-least-privilege`.** That overrides a **child's** provider/model
  per **spawn**, statically supplied by the caller; it does **not** auto-classify
  difficulty to pick a **per-turn parent** tier. `routing` does exactly the thing
  it does not.
- **Not the rejected privilege/auto-mode classifier.** That competed with the
  capability layer by auto-selecting a *privilege* tier; `routing` routes by
  *cost/difficulty* and changes the *model*, orthogonal to capabilities (D5). No
  overlap.

**Conflict note.** A `grep` of `docs/design/` for `routing` matches only this file
plus incidental uses in `2026-06-20-dynamic-workflow.md` ("in-graph routing" — a
DAG-edge feature, unrelated to model tiering) and a `risk-guard` implementation
note ("routing sentinel", unrelated). **No existing design routes the model by
difficulty.** This is the **first design** to do per-turn difficulty-aware model
tiering; no prior design is superseded and there is no conflict.

## 7. Acceptance Criteria

All verified offline by `npm test` against a scripted `MockProvider` (no network,
no API key), in `test/routing.test.ts`, loaded via `host.use("routing", activate)`
(per `test/recovery.test.ts:118-120`), **not** via `BUILTIN_EXTENSIONS`. The tier
map is overridden in-test to two registered mock model ids (`mock-cheap`,
`mock-flagship`).

- **AC-1 (trivial turn → cheap tier; per-turn `Agent.model` set).** With routing
  enabled (heuristic mode) and a turn whose latest user text is below `HARD_CHAR_LEN`
  (280) with no `HARD_KEYWORD_CUES` cue and no large prior tool result, assert that
  **during that turn**
  `e.agent.model === "mock-cheap"`. Measured two independent ways: (a) a
  `turn_start` spy that records `e.agent.model` *after* the routing handler runs,
  and (b) a `MockProvider` responder that records `req.model` (`mock.ts:63`) for
  that turn's request. Both must equal `mock-cheap`.
- **AC-2 (hard turn → flagship tier).** A turn whose latest user text is ≥
  `HARD_CHAR_LEN` (280) (or contains a `HARD_KEYWORD_CUES` cue, or follows a
  tool result above `HARD_TOOL_RESULT_BYTES` (8192)) sets `e.agent.model ===
  "mock-flagship"` — asserted by the same `turn_start` spy and `req.model`
  recorder. A two-turn script (trivial then hard) asserts the model *changed
  between turns* (cheap on turn 1, flagship on turn 2), proving the override is
  re-evaluated per turn, not pinned.
- **AC-3 (restore on `agent_end`).** After a run that routed at least one turn to
  the cheap tier, assert `e.agent.model` equals the **configured** model (the
  baseline captured at `agent_start`) once `run()` resolves — i.e. routing left no
  residue. Verified by reading `e.agent.model` after `await agent.run(...)`.
- **AC-4 (restore + stop on disable).** Enable routing, run a trivial turn
  (model becomes cheap), then `/routing off` (or set the store flag false)
  mid-session via a queued `turn_start`; assert that from the next turn onward
  `e.agent.model` is the configured baseline and stays there (no further tier
  assignment). Equivalently, a unit-level assertion: with `enabled === false` the
  handler restores and returns without assigning a tier.
- **AC-5 (`EAGENT_ROUTING=off` never changes the model).** With the env var set
  to `off` (saved/restored in `finally`), load the extension and run a turn that
  *would* classify trivial; assert `e.agent.model` equals the configured model on
  every turn and at end — the kill switch makes activation a no-op (`return
  () => {}`), so no `turn_start` handler is registered. Assert by a `turn_start`
  spy observing the model is unchanged for the whole run.
- **AC-6 (conservative-on-unsure → flagship).** With routing enabled and a turn
  the heuristic cannot classify as trivial against the pinned defaults — e.g. an
  empty/absent latest user message, so none of the `HARD_CHAR_LEN`,
  `HARD_KEYWORD_CUES`, or `HARD_TOOL_RESULT_BYTES` signals can be evaluated — *and*
  no LLM mode configured (the indeterminate case), assert `e.agent.model ===
  "mock-flagship"` (never the cheap tier) — the default-to-flagship safety rule (D2).
- **AC-7 (unresolvable tier entry → fall back + warn).** The trigger is a
  concrete, automatable map-resolution miss (the registry has no model-id concept
  to test against, D3): override the tier map so the cheap tier's entry is **absent
  or an empty string** (e.g. `{ cheap: "", flagship: "mock-flagship" }`); run a
  trivial turn; assert `e.agent.model` falls back to the configured baseline (not
  the empty/missing value) and an `e.log.warn` was emitted (captured via the
  harness logger). No throw. (A well-formed-but-provider-unknown id is *not* this
  AC — that is the provider's error to raise on the turn, exactly as for a typo'd
  `Agent.model` today; `routing` only guarantees it never assigns a tier it cannot
  resolve to a non-empty model id from its own map.)
- **AC-8 (optional LLM mode classifies via a tool-less sub-call).** With
  `mode: "llm"`, script the `MockProvider`'s classifier response to a `HARD`
  verdict; assert the turn routes to flagship and that the classification call
  passed **no tools** (assert the sub-call request's `tools` is empty, mirroring
  risk-guard's recursion-safety assertion). A `CHEAP` verdict routes to cheap. A
  garbled verdict fails open (to the heuristic, then to flagship) and does not
  throw.
- **AC-9 (registration deltas).** Activating the extension via the harness adds
  exactly the expected `agent_start` / `turn_start` / `agent_end` listeners and
  **one** command, and **zero** tools (delta assertions, per
  `risk-guard.test.ts` AC-8 style). `host.unload("routing")` removes them all and
  restores the configured model; a subsequent run never changes the model.
- **AC-10 (offline + typecheck).** `npm test` and `npm run typecheck` pass with no
  network and no API key (house rule); the new suite is fully offline against
  `MockProvider`.

## 8. Risks and Rollback

- **Risk: a wrong difficulty call routes a hard turn to a cheap model** (quality
  regression). *Mitigation*: the classifier is **conservative — default to
  flagship when unsure** (D2, AC-6); it is off by default and the user can disable
  it at any time; the cheap tier is only chosen when a positive trivial signal is
  present. A misroute costs quality on one turn, recoverable by the user, never a
  silent permanent downgrade.
- **Risk: changing `Agent.model` mid-session confuses other live readers** (e.g.
  `cost`'s `/cost` status reading `e.agent.model` between turns). *Mitigation*:
  the override is **restored on disable / `agent_end`** (D4), so between runs the
  field is always the configured model. **Known limitation — `cost` mis-attributes
  per-turn-routed spend within a run (corrected claim):** `cost` stamps
  `activeModel = e.agent.model` **only at `agent_start`** (`cost.ts:163` init,
  `:203` re-stamp) and prices **every** `usage` event of the run against that
  single run-start `activeModel` (`cost.ts:211` `priceRow(activeModel, …)`,
  `:218`/`:229` `perModel.get/set(activeModel)`) — it does **not** re-read
  `e.agent.model` per usage event (`cost.ts:216` is `sessionUsd =
  costOf(p.cumulative, row)`, a cost computation, not a live model read). So a run
  that routes some turns to cheap and some to flagship is attributed **entirely to
  the run-start model** in `cost`'s per-model breakdown; the per-turn USD split is
  *not* reflected there. This does not corrupt the total (every event is still
  priced against one real card row) and does not affect `routing`'s correctness
  (the model genuinely changed per turn — AC-1/AC-2), but it weakens the
  `routing`+`cost` composition: the savings show up as a lower aggregate, not as a
  clean per-tier line. Tightening `cost` to re-stamp `activeModel` per turn (e.g.
  on `turn_start`/`usage`) is a **separate `cost` change**, out of scope here and
  noted as follow-up. The per-turn *model* scoping is documented and asserted
  (AC-1/AC-2/AC-3/AC-4); the per-turn *cost attribution* is not claimed.
- **Risk: a tier resolves to no usable model id** (an operator emptied/omitted a
  tier entry). *Mitigation*: the tier guard resolves against the **configured tier
  map** (not the registry, which keys by provider name — D3) and falls back to the
  configured baseline with an `e.log.warn` when a tier's entry is missing or empty
  (D3, AC-7) — the run continues on the known-good configured model. A
  *well-formed-but-provider-unknown* tier id is **not** caught here (the registry
  exposes no model-id check to catch it): it is surfaced as a normal turn error by
  the provider call, identical to how a typo'd `Agent.model` or a `spawn_agent`
  `model` override behaves today — an accepted, pre-existing limitation, not a
  regression `routing` introduces.
- **Risk: the optional LLM classifier adds cost/latency or recurses.**
  *Mitigation*: it is **opt-in** (`mode: "llm"`, off by default within an
  already-off-by-default extension); it is recursion-safe (`tools: []`, runs
  outside the loop, `risk-guard.ts:124-132`); and it **fails open to the
  heuristic** (then to flagship), never to a throw (AC-8).
- **Risk: routing leaks into a child or grandchild.** *Mitigation*: `routing`
  operates on `e.agent` (the parent). A spawned child is a *separate* `Agent`
  built by `subagents` with its own model (`subagents.ts:77-88`); the parent's
  `turn_start` handler does not fire on the child's loop. A child is routed only
  if `routing` is loaded in the child's host — out of scope here, and explicitly a
  non-goal (§3 "No routing of the classifier sub-call itself" / per-spawn override
  is subagents-lp's job).

**Kill switch.** `EAGENT_ROUTING=off` makes `activate` an immediate no-op
(`return () => {}`, the `cost.ts:150-152` pattern): no listeners registered, no
command, `Agent.model` never touched, so the system behaves exactly as before this
extension existed (AC-5). The in-session `/routing off` is the soft switch: it
restores the configured model and stops assigning (AC-4).

**Rollback.** A single self-contained extension plus (deferred) one
`BUILTIN_EXTENSIONS` line. `EAGENT_ROUTING=off`, `/routing off`, or
`host.unload("routing")` restores the configured model and removes the extension
with zero effect on other extensions (AC-9). No schema, storage, or protocol
change to undo; the configured model is always the baseline.
