# Design: token-gated structured conversation compaction with a pinned block (`compact` extension)

Status: open
Slug: `2026-06-22-compact`

## 1. Background and Purpose

Five extensions register on the `transformContext` seam (applied at
`src/kernel/agent.ts:247-251`, over a *copy* of the transcript
`[...this.#messages]` with context `{turn, model}`): `prune` (`prune.ts:85`),
`memory` (`memory.ts:131`), `microagents` (`microagents.ts:197`), `context-files`
(`context-files.ts:71`), and `skills` (`skills.ts:43`). But only **two** *bound*
context size — `prune` and `memory`; the other three are additive injectors of
notes/system content, not folders/truncators — and neither of those does
token-gated structured conversation summarization:

- **`prune`** (`src/extensions/prune.ts`) truncates the *bytes* of old, oversized
  `tool_result` blocks beyond a protected recent window
  (`prune.ts:50-82`). Its header is explicit that it is the *size* defense and
  does **not** summarize the conversation (`prune.ts:11-16`). It is provider-free
  and never folds dialogue.
- **`memory`** (`src/extensions/memory.ts`) folds the older prefix into a summary
  — but it triggers on **message count** (`memory.ts:131-133`, defaults 12 / keep
  4 at `memory.ts:27-28`) and summarizes into a **single free-form bullet** via a
  generic "terse bullet summary" prompt (`memory.ts:31-33`). Count is the wrong
  axis (a few huge messages can fill the window without tripping it; many tiny
  ones trip it pointlessly), and a free-form bullet can **silently drop** an
  active plan, a decision, or a load-bearing fact, with nothing pinned to survive
  by construction.

The robust pattern in production agents (codex `compact`, gemini
`chatCompressionService`) is different on every axis: trigger on a **token
budget** at a **user-turn boundary**, summarize the older slice via a
recursion-safe tool-less provider sub-call into a **structured handoff**
(`## Decisions` / `## Files` / `## Open threads`), keep a protected recent
window, and **always re-inject a small byte-capped PINNED block** so designated
evidence survives compaction *by construction* rather than by the summarizer's
discretion.

This task adds a new **`compact`** extension implementing exactly that, on the
same `transformContext` seam, producing the `meta.kind:"summary"` marker that
`prune` already recognizes and stops at (`prune.ts:61`). It is the token-aware,
structured-slot successor to `memory`'s count-based compaction path.

## 3. Scope Boundary (NON-goals — Simplicity First)

- **Not** a tokenizer. Reuse `prune`'s `chars/4` heuristic verbatim
  (`prune.ts:30-32`); do not add a real tokenizer or any dependency.
- **Not** a rewrite of `memory.ts`. We do not delete or restructure `memory`'s
  scratchpad (`remember`/`recall`), its `/memory` command, or its
  `transformContext` hook here. We only **supersede its `/compact` command** by
  registering ours after it (D3). A flag to retire `memory`'s count-based hook is
  raised for a later cleanup task; not done here (BATCH-mode constraint: only the
  new files are touched).
- **Not** mid-tool-call splitting. The split point is *only* a user-turn boundary,
  so an in-flight `tool_call`/`tool_result` pair is never severed (Risk R3).
- **Not** caching/fingerprinting of the summary across turns (the `memory.ts:55-120`
  SummaryCache machinery). compact is gated by a *token budget*, so it fires
  rarely; a per-fire sub-call is acceptable and the cache is needless complexity
  here. (Re-summarization carrying forward prior slots — D8 — replaces the need.)
- **Not** semantic/embedding retrieval, sub-agent handoff, or multi-summary
  hierarchy. One structured summary slot + one pinned block.
- **Not** on by default. It costs a model sub-call; it is opt-in (D7), like
  `risk-guard` (`risk-guard.ts:18-21`, `:80`).
- **No** new capability for the compaction hook itself (it reads/transforms
  context only); the `pin`/`unpin` tool is a private store notebook and needs none
  either, exactly as `memory`'s `remember`/`recall` justify (`memory.ts:186-188`).

## 4. Key Design Decisions

### D1 — Trigger axis: token budget at a user-turn boundary

- **Problem:** when should compaction fire?
- **Options:** (a) message **count** threshold (what `memory.ts:131-133` does);
  (b) estimated **token** budget, evaluated at a user-turn boundary.
- **Choice:** (b) — estimated token budget. Reuse `prune`'s per-string estimator
  `est(s) = Math.max(0, Math.round(s.length / 4))` (`prune.ts:30-32`), but sum over
  **both text and tool_result block content** across the whole transcript — note
  `prune` itself sums **only** `tool_result` content (`prune.ts:64-69` skips
  non-`tool_result` blocks), because it is a tool-output size defense; compact is a
  *conversation*-size gate, so it must also count dialogue text (else a text-heavy
  conversation under-counts and never fires, defeating this decision's rationale).
  Fire only when the running estimate exceeds the budget.
- **Why (a) rejected:** count is lossy and orthogonal to what actually fills the
  window — five whole-file reads overflow the window with ~6 messages (never
  tripping count 12), while a dozen one-word turns trip it for no reason. `prune`'s
  own header (`prune.ts:5-9`) documents precisely this failure of the count axis.
  Tokens are what the model's window is denominated in.

### D2 — Summary shape: structured slots vs one free-form bullet

- **Problem:** what does the summary message contain?
- **Options:** (a) a single free-form bullet (memory's approach, prompt at
  `memory.ts:31-33`); (b) fixed structured sections — `## Decisions`, `## Files`,
  `## Open threads`.
- **Choice:** (b) — a system prompt that instructs the sub-call to emit exactly
  those three markdown sections. (The exact section *strings* are a pure
  format choice and self-justify as non-behavioral: any three-slot scheme works;
  these mirror the codex/gemini handoff shape.)
- **Why (a) rejected:** a single free-form bullet has no slot that *must* hold the
  active plan or the touched files, so the summarizer can omit them silently —
  the exact lossy behavior this task exists to fix. Structured slots give the model
  a named place for decisions, files, and open threads, so a dropped plan is a
  visibly empty `## Open threads`, not invisible loss.

### D3 — Relationship to `memory.ts`: supersede its count-based `/compact`, do not run two compactors

- **Problem:** `memory` *already* registers a `/compact` command (`memory.ts:148`)
  and *already* emits `meta:{source:"memory",kind:"summary"}` (`memory.ts:125`)
  from its own count-based `transformContext` hook (`memory.ts:131-143`). Shipping
  a second token-based compactor risks **two competing compactors** double-folding
  the same prefix and a **command-name collision** on `/compact`.
- **Options:** (a) run `compact` *alongside* `memory`'s hook (both fire); (b) make
  `compact` the token-aware structured **successor** and have it take over the
  `/compact` verb, documenting that it supersedes `memory`'s count-based path.
- **Choice:** (b). `CommandRegistry.register` is last-wins (`commands.ts:27-44`,
  `get()` returns `.at(-1)`), and in `BUILTIN_EXTENSIONS` `memory` loads before any
  appended extension (`host.ts:72`), so registering `compact`'s `/compact` command
  *after* `memory` cleanly shadows it; disposing `compact` restores `memory`'s
  (`commands.ts:31-39`). Per house rules we pick the more-tested/**newer**
  compactor and do **not** run two. We **flag** `memory`'s count-based
  `transformContext` hook for later retirement but **do not modify `memory.ts`** in
  this task (BATCH-mode constraint).
- **Why (a) rejected:** two `transformContext` handlers both folding the older
  prefix would summarize a summary (or fold a slice the other just folded),
  burning two sub-calls and degrading fidelity. The whole point of the seam is one
  compaction *strategy* at a time (`memory.ts:13-19`).
- **Coexistence note (why this task is safe as scoped, and why the retirement is
  load-bearing, not cosmetic):** the interim story is *not* "a shared marker guard
  keeps the two hooks from double-folding." It is the opposite: `memory`'s
  `transformContext` hook has **no** `meta.kind:"summary"` guard — it
  *unconditionally* folds everything before its last `keepRecent` (4) messages
  whenever `messages.length > threshold` (12) (`memory.ts:131-143`). Only `prune`
  breaks on the marker (`prune.ts:61`); `memory` does not. So once both are
  registered, registration order decides everything: filters run in registration
  order, each receiving the previous one's output (`hooks.ts:64-76,102`), and in
  `BUILTIN_EXTENSIONS` `memory` loads *before* any appended extension
  (`host.ts:72`). `memory`'s hook would therefore fire **first**, collapse the
  prefix to ~5 messages, and hand `compact` a transcript already under the 60k
  budget — making `compact` a **silent no-op** (and, on a later turn, leaving
  `memory` free to re-fold an array that already contains a `compact` summary).
  That is exactly why **this task does not register `compact` in
  `BUILTIN_EXTENSIONS`** (Deliverables: host wiring deferred) and why every test in
  §7 loads extensions in isolation via `host.use` (AC-10 loads `memory`+`compact`
  explicitly and asserts only command shadowing, not co-running hooks). Within this
  task's scope the two hooks never run together against a real transcript, so there
  is no interim double-fold to bound. The **durable** fix — `compact` taking the
  `/compact` verb *and* `memory`'s count-based hook being retired at batch
  integration — is therefore not optional polish: it is the prerequisite for
  enabling `compact` at all, because `memory`'s un-guarded first-firing hook would
  otherwise neuter it. Sequencing is spelled out in R1.

### D4 — Token budget default + protected recent-window size (THRESHOLD decision)

- **Problem:** pick the default budget (when to fire) and the protected recent
  window (how much to keep verbatim). Both are behavioral.
- **Options considered for the budget:** a small fraction of a typical context
  window, vs a large one. For the window: last N **messages** (memory's `keepRecent`
  axis, `memory.ts:28`) vs last N **user turns**.
- **Choice — budget:** default **`60_000`** estimated tokens, overridable via
  `e.store.get<number>("budget", …)`. Rationale: this sits comfortably above
  `prune`'s `PRUNE_PROTECT=40_000` verbatim-protection floor (`prune.ts:23`), so
  `prune`'s cheap byte-trim gets the first crack at oversized tool outputs and
  `compact`'s paid sub-call only fires once the *conversation itself* (not just one
  fat tool result) is genuinely large — a sane fraction of a 128k–200k window that
  leaves headroom for the system prompt, tools, and the next response.
- **Choice — window:** protect the last **K = 3 user turns** (a user turn plus the
  assistant/tool messages that follow it), overridable via
  `e.store.get<number>("keepTurns", 3)`. Rationale: turns (not messages) are the
  unit that keeps a `tool_call`/`tool_result` pair together (D1/R3); three recent
  user turns preserve the immediate working context (current request + the two
  before it) while still leaving a foldable older slice in any conversation long
  enough to exceed a 60k budget.
- **Why the rejected ends:** a *small* budget (e.g. 12k) would fire compaction —
  and its sub-call cost — on routine sessions that fit the window fine; a *huge*
  budget (e.g. 180k) would fire only at the brink, too late to leave response
  headroom. Counting *messages* for the window (rejected) is exactly D1's lossy
  axis and risks splitting a tool pair (R3).

### D5 — Recursion-safe summarization: tool-less provider sub-call vs sub-agent

- **Problem:** the summary must be produced by the model without re-entering the
  agent loop (and thus `transformContext`/this very hook) recursively.
- **Options:** (a) the `risk-guard`/`memory` pattern — call `provider.stream({…,
  tools: [], …})` directly with a re-entrancy guard flag; (b) spawn a sub-agent.
- **Choice:** (a). Copy the exact pattern: a module-level/closure re-entrancy
  boolean set before and cleared after the sub-call, plus
  `provider.stream({systemPrompt: COMPACT_SYSTEM_PROMPT, messages: older, tools:
  [], model: e.agent.model, signal: new AbortController().signal})`, reading
  `ev.type==="done"` → `textOf(ev.message)` (verbatim from `risk-guard.ts:95-121`
  and `memory.ts:78-93`). `tools: []` means the completion cannot emit a tool call,
  so it cannot re-enter the loop; the guard flag additionally makes the hook a
  no-op if re-entered. Fails **open**: no provider / throw / empty reply →
  fall back to a deterministic provider-free digest of the slice (mirroring
  `memory.ts:78-93,252-268`) so the prefix is never dropped.
- **Why (b) rejected:** a sub-agent is heavier (its own loop, tools, hooks) and —
  critically — would itself have `transformContext` and could **itself trigger
  compaction**, the recursion this design must avoid. The tool-less sub-call is the
  established, minimal, proven-safe primitive here.

### D6 — Pinned-block source: a `pin`/`unpin` tool over `e.store` vs a `pin:` text convention

- **Problem:** where do the always-surviving pinned facts come from?
- **Options:** (a) a `pin`/`unpin` tool that writes notes to `e.store` under a
  `pin:` key prefix (like `memory`'s `remember`/`recall`, `memory.ts:190-236`,
  `NOTE_PREFIX` at `:38`); (b) a `pin:` **text convention** — scan the transcript
  for user/assistant lines beginning `pin:` and lift them.
- **Choice:** (a) — a `pin`/`unpin` tool over `e.store`. The pinned block is built
  by concatenating all `pin:`-prefixed store entries, **byte-capped** to a fixed
  budget (`PIN_MAX_BYTES`, default 2_000, a pure constant), and is **always**
  prepended immediately before the recent window on every compaction — so pinned
  evidence survives by construction.
- **Why (b) rejected:** a text convention is implicit and fragile — it re-scans the
  full transcript every hook call, mis-fires on incidental `pin:` text (URLs,
  prose), and offers no way to *unpin*. An explicit tool is a clear, testable,
  durable contract that the model (or user, via the tool) controls, and reuses the
  exact store-notebook pattern `memory` already validates (no capability needed,
  `memory.ts:186-188`). The byte cap (vs the slot strings) is a behavioral bound:
  it guarantees the pinned block can never itself blow the budget it is meant to
  protect.

### D7 — Posture: off by default with `EAGENT_COMPACT=off`, vs on with a high budget

- **Problem:** should compaction be enabled by default?
- **Options:** (a) **off** by default (an explicit enable), `EAGENT_COMPACT=off`
  hard kill; (b) **on** by default with a high budget.
- **Choice:** (a) — off by default; enabled via `e.store.set("enabled", true)` (or
  a `/compact on`), with `EAGENT_COMPACT=off` as the hard env kill read inside the
  hook. Exactly `risk-guard`'s posture (`risk-guard.ts:18-21,80`): because it makes
  a **paid, latency-adding model sub-call** and **changes the context the model
  sees**, it is opt-in.
- **Why (b) rejected:** even with a high budget, "on by default" means a long
  session silently incurs a summarization sub-call and a context rewrite the user
  never asked for — a surprising cost and a surprising behavior change for a
  defense most short sessions never need. `prune` can default-on because it is
  provider-free (`prune.ts:11-16`); `compact`, like `risk-guard`, cannot.

### D8 — Re-summarization on a second fold: carry forward the prior summary slot

- **Problem:** when `compact` fires a *second* time (the transcript has grown past
  budget again and there is already one `meta.kind:"summary"` message in the
  prefix), what does the second sub-call summarize, and what happens to the first
  summary's slots?
- **How the seam actually behaves (load-bearing):** `transformContext` runs over a
  *fresh* `[...this.#messages]` copy every turn and the folded result is used only
  for the provider request — it is **never written back** to the durable transcript
  (`agent.ts:247-251`). So the raw older messages are **not** gone after a fold: on
  the next over-budget turn the hook re-receives the *raw originals* and re-folds
  them from scratch. A `compact` summary therefore never sits at the head of `older`
  in production — the live transcript never contains one.
- **Options:** (a) **carry the prior summary forward defensively** — when building
  `older`, split on (do not exclude) any `summary` marker, with a prompt instruction
  to merge/preserve its `## Decisions` / `## Files` / `## Open threads`; (b)
  **strip any prior summary** from `older` before the sub-call; (c) **drop the prior
  summary** and summarize only the new raw messages since the last fold.
- **Choice:** (a) — carry forward, as a belt-and-suspenders merge. Because the live
  transcript re-presents the raw originals each turn (above), this is not the
  load-bearing mechanism the way it would be if folds were persisted — re-folding
  raw never loses anything. But splitting *on* (not excluding) the marker costs no
  extra machinery, and if a summary ever does reach `older` (e.g. an upstream filter
  that persists, or a hand-built transcript), the D2 merge prompt preserves its
  slots rather than dropping them. It is the strictly safer default at zero cost.
- **Why (b) rejected:** stripping the marker would discard a prior summary's slots
  in the one case where it *does* reach `older` (a persisting upstream transform),
  for no benefit — splitting on it is simpler and never loses items.
- **Why (c) rejected:** dropping the prior summary throws away exactly the earlier
  decisions/files/threads this task exists to preserve. It would only matter if folds
  were persisted (they are not), but the merge-forward default keeps decisions durable
  across an arbitrary number of compactions for free, and it is what the rejected
  SummaryCache (Scope §3) tried to buy with fingerprinting machinery we do not need.
  AC-7 is the runnable guard (it hand-builds the prior-summary-at-head case the live
  loop does not itself generate, validating the merge prompt directly).

## 5. Dependencies and Assumptions

- **Hook surface:** `transformContext` exists and is applied at
  `agent.ts:247-251` over a copied array `[...this.#messages]` with `{turn, model}`
  context; returning a new array never mutates the durable transcript. Assumed
  stable (it is a kernel filter type).
- **`ExtensionAPI`:** `e.hook`, `e.registerTool`, `e.registerCommand`, `e.store`
  (namespaced per `extension.ts:224,234`), `e.log`, `e.agent.providers.get()`,
  `e.agent.model`, `e.agent.messages` — all present (`extension.ts:41-78`).
- **Provider sub-call:** `provider.stream` yields a terminal `{type:"done",
  message, …}` (`types.ts:197-201`); MockProvider satisfies this per scripted turn
  (`mock.ts:63-101`), so the sub-call is just one more scripted turn offline.
- **Estimator parity:** reuse `prune`'s `chars/4` (`prune.ts:30-32`); MockProvider's
  usage estimate is also ~4 chars/token (`mock.ts:121-123`), so test math is
  consistent.
- **House rules:** ESM with `.js` specifiers even for `.ts`; strict TS
  (`noUncheckedIndexedAccess`, no `any`); zero runtime deps beyond `jiti`; offline
  `node:test` against MockProvider; a `dispose` loop that never throws (the
  `risk-guard.ts:170-178` shape).
- **Assumption:** a conversation that exceeds a 60k-token budget contains at least
  one user-turn boundary older than the last 3 turns to split at; if not (one
  giant turn), compact is a no-op and `prune` handles the size — acceptable.

## 6. Relationship with Existing Designs

Closest existing extensions/files (all read and grounded):

- **`src/extensions/prune.ts`** — same `transformContext` seam; `compact`
  **reuses** its `est` estimator (`:30-32`) and **produces** the
  `meta.kind:"summary"` marker that `prune` stops at (`:61`). No conflict: prune
  trims tool-output *bytes*; compact summarizes *dialogue*. Design doc:
  `docs/design/2026-06-20-prune.md`.
- **`src/extensions/memory.ts`** — the count-based compactor this **supersedes**
  (D3). **CONFLICT:** `memory` already owns the `/compact` command (`:148`) and
  emits a `summary`-marked message (`:125`); compact shadows the command
  (last-wins, `commands.ts`) and is the structured token-aware successor; memory's
  count hook is flagged for later retirement, **not** modified here.
- **`src/extensions/risk-guard.ts`** — the **recursion-safe tool-less
  provider sub-call** pattern copied verbatim (`:95-121`), including the off-by-
  default + `EAGENT_*=off` posture (`:80`) and the never-throw dispose loop
  (`:170-178`). No conflict (different hook: `beforeToolCall`).

DEDUP statement: `prune` truncates tool-output **bytes** by recency and refuses to
summarize; `memory` compacts on message **count** into one **free-form** bullet.
`compact` is **token-gated, user-turn-boundary, structured-slot** conversation
summarization with a **guaranteed-surviving byte-capped PINNED block** — the gap
neither covers. This is not a first design (it is the structured successor to the
`memory`/`prune` compaction lineage).

## 7. Acceptance Criteria (measurable / automatable)

All via `makeHarness` + `host.use("compact", activate)`, offline, scripting the
MockProvider so one scripted turn serves the compaction sub-call.

1. **No-op below budget:** with a short transcript under the 60k budget, the array
   returned by `transformContext` is reference-equal-by-content to the input
   (same length, no `meta.kind:"summary"` message inserted). Assert
   `messages.filter(m => m.meta?.kind === "summary").length === 0`.
2. **Fires over budget → one summary message:** feed a transcript whose `est` sum
   exceeds the budget with ≥1 user-turn boundary older than `keepTurns`; assert the
   transformed array contains **exactly one** `system` message with
   `meta.kind === "summary"`, placed before the recent window, and that the last
   `keepTurns` user turns survive verbatim.
3. **Structured slots present:** the summary message text contains the literal
   headings `## Decisions`, `## Files`, and `## Open threads` (the MockProvider is
   scripted to return text including them; assert all three substrings present).
4. **Split only at a user-turn boundary:** construct a transcript ending in an
   assistant `tool_call` followed by a `tool` `tool_result`; assert no transformed
   message ever separates that `tool_call` from its `tool_result` (no `summary`
   marker is inserted between them) — i.e. the recent window contains the whole
   pair.
5. **Pinned block always survives:** call the `pin` tool with a value, then trigger
   compaction; assert the transformed array contains a message whose text includes
   the pinned value, positioned immediately before the recent window. Then exceed
   the pin budget: assert the pinned block's byte length ≤ `PIN_MAX_BYTES`.
6. **`unpin` removes it:** `pin` then `unpin` a key; trigger compaction; assert the
   pinned value no longer appears in the transformed array.
7. **Re-summarization carries prior slots forward (D8):** trigger compaction twice
   (second time with more messages); assert the second summary message's text
   still contains content from the first summary (the prior slots are fed into the
   second sub-call's `older` slice / carried forward), i.e. earlier decisions are
   not lost across a second fold.
8. **Off by default:** with no `enabled` set in the store and `EAGENT_COMPACT`
   unset, a transcript over budget yields **no** `summary` message (assert count
   === 0). After `e.store.set("enabled", true)`, the same transcript yields one.
9. **`EAGENT_COMPACT=off` kill switch:** with `enabled` true but
   `EAGENT_COMPACT=off`, an over-budget transcript yields **no** `summary` message
   (assert count === 0). Restore the env var in `finally`.
10. **`/compact` command supersedes memory's:** load `memory` then `compact` via
    `host.use`; assert `commands.get("compact")` resolves to compact's command
    (the description/effect differs — e.g. running it forces a token-based fold and
    prints a compact-specific line). Dispose `compact`; assert
    `commands.get("compact")` resolves back to memory's.
11. **Recursion safety:** assert the compaction sub-call is invoked with `tools`
    empty (script the MockProvider responder as a function asserting
    `req.tools.length === 0` on the sub-call turn) and that triggering compaction
    does not re-enter the hook (a re-entrancy counter stays ≤ 1).
12. **Fails open:** with no provider returning summary text (script the sub-call
    turn to `{text:""}`), assert a deterministic non-empty fallback summary message
    is still produced (the older slice is never silently dropped).
13. **Dispose is clean:** `host.unload("compact")` removes the hook, the
    `/compact` command, and the `pin`/`unpin` tools (assert `commands.get`,
    `agent.tools.get("pin")` are gone) and never throws.

## 8. Risks and Rollback

- **R1 — two competing compactors (overlap with `memory`).** The danger is real
  and **not** mitigated by a shared marker guard: `memory`'s `transformContext`
  hook has no `meta.kind:"summary"` guard (`memory.ts:131-143`) — only `prune`
  breaks on the marker (`prune.ts:61`). Because filters run in registration order
  (`hooks.ts:64-76,102`) and `memory` loads before any appended extension
  (`host.ts:72`), if both were registered `memory`'s hook would fire first,
  collapse the prefix under the 60k budget, and silently no-op `compact` (and could
  later re-fold an array already holding a `compact` summary). The mitigation is
  therefore **sequencing, not coexistence**: (1) within *this* task `compact` is
  **not** in `BUILTIN_EXTENSIONS` (host wiring deferred per Deliverables) and the §7
  tests load extensions in isolation via `host.use`, so the two hooks never run
  together — there is no interim window to bound; (2) at batch integration `compact`
  must be wired in **and** `memory`'s count-based hook retired in the *same* change,
  so a single token-aware compactor owns the seam from the first moment `compact` is
  enabled. `compact` taking the `/compact` verb (last-wins) handles the command
  collision independently. AC-2/AC-10 guard the isolated behavior; the batch-
  integration change must add a co-load regression test once `memory`'s hook is
  removed. Ordering note (injectors): once wired into `BUILTIN_EXTENSIONS` after
  `skills`/`microagents`/`context-files`, `compact` also runs *after* their
  `transformContext` injections, so a freshly-injected note/system block could fall
  into the older slice and be summarized. This is benign — those injections are
  small and re-injected each turn, and `compact` splits at user-turn boundaries — but
  the batch-integration co-load test should include an injector to confirm it.
- **R2 — the summarization sub-call adds latency/cost per fire.** Mitigated by D7
  (off by default), D4 (a 60k budget so it fires rarely, after `prune`), and full
  offline testability (the sub-call is just a scripted MockProvider turn).
- **R3 — a bad split drops an in-flight `tool_call`/`tool_result` pair.** Mitigated
  by splitting **only** at a user-turn boundary, never mid-pair (D1/D4); AC-4 is the
  runnable guard.
- **R4 — pinned block grows unbounded and itself blows the budget.** Mitigated by
  the byte cap `PIN_MAX_BYTES` (D6); AC-5 asserts the cap.
- **R5 — provider failure mid-summary.** Mitigated by fail-open to a deterministic
  fallback digest (D5, mirroring `memory.ts:252-268`); AC-12 guards it.
- **Rollback (graduated):**
  1. `EAGENT_COMPACT=off` — env hard kill read inside the hook (AC-9); compaction
     never fires, transcript untouched, `prune`/`memory` still apply.
  2. `/compact off` (or `e.store.set("enabled", false)`) — runtime disable; the
     `/compact` verb falls back to memory's when compact is unloaded.
  3. `host.unload("compact")` / remove from `BUILTIN_EXTENSIONS` — full teardown via
     the never-throw dispose loop (AC-13); restores memory's `/compact`.
