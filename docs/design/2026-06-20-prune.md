# Design: token-budget tool-output pruning (`prune` extension)

Slug: `2026-06-20-prune`

## 1. Background and Purpose

EAgent already has `memory` — a `transformContext` filter that folds the older
*prefix* of the transcript into a cached summary once the **message count**
crosses a threshold (`src/extensions/memory.ts:131`, default 12 messages,
keep 4 recent). That defends against a long *conversation*, but not against a
*heavy* one: an agentic run can blow the model's context window with only a
handful of messages when those messages carry enormous tool outputs — five
whole-file `read`s, a giant `grep`, a verbose `bash` dump. Such a run never
trips `memory`'s count threshold yet still overflows.

The opencode project handles exactly this with a second, complementary
mechanism (`packages/opencode/src/session/compaction.ts`, the `prune` path,
MIT): walk the transcript backward, keep the most recent tool outputs verbatim,
and **truncate the older, oversized tool outputs in place** — a cheap, provider-
free trim that targets the single biggest space consumer in agentic context
(tool results) without summarizing or calling the model.

EAgent lacks this. This task ports it as a small `prune` extension on the same
`transformContext` seam `memory` uses, so the two compose: `memory` bounds by
*message count* (summarizing the old prefix), `prune` bounds by *token size*
(trimming old tool outputs in whatever context survives). If we do not, the only
context defense is count-based and silently inadequate for output-heavy runs.

## 2. Deliverables

- [ ] `src/extensions/prune.ts` — a `transformContext` filter that truncates old,
      oversized `tool_result` content beyond a protected recent window, returning
      a **new** message array; no tool, no command, no capability; honors an
      `EAGENT_PRUNE=off` runtime kill switch.
- [ ] `test/prune.test.ts` — offline tests covering AC 2–9 (no-op below budget,
      prune over budget, recency protection, summary boundary, below-minimum
      no-op, transcript purity, provider-free, metadata).
- [ ] `src/host.ts` — register `prune` in `BUILTIN_EXTENSIONS` (after `memory`,
      so it trims whatever context survives summarization).
- [ ] `CLAUDE.md` — one-line inventory entry for `prune`.

## 3. Scope Boundary (NOT in scope)

- **No summarization.** Folding old messages into an LLM summary is `memory`'s
  job; `prune` never calls a provider.
- **No transcript mutation / persistence.** `prune` is a pure `transformContext`
  transform: it returns a new array for the model to see and never alters
  `agent.messages` (the durable transcript) — identical to the contract `memory`
  and `test/agent.test.ts:164` already enforce.
- **No protected-tool-name set.** opencode protects `skill` tool *outputs*
  because skills there arrive as tool results. In EAgent skills are injected via
  `transformContext` (`src/extensions/skills.ts:43`), not as tool results, so no
  EAgent tool output carries must-keep instructions; the recency window and
  summary boundary already protect any live instructional content. Porting the
  protected-name set (and the `toolCallId → tool_call.name` correlation it needs)
  would be unrequested machinery for an empty set.
- **No configurable thresholds beyond the kill switch.** Thresholds are module
  constants; no `e.store` override surface (that is unrequested flexibility —
  `memory`'s store-config pattern is not a mandate).
- **Only `tool_result` text is pruned.** `text`, `thinking`, and `image` blocks
  are untouched.
- **No new command or tool.** `prune` adds only a hook.

## 4. Key Design Decisions

**D1 — New extension vs. extending `memory`.** Problem: where does token-based
trimming live? Options: (a) fold it into `memory.ts`; (b) a new `prune`
extension. Choice: **(b)**. Rationale: `memory` summarizes by *message count*
and depends on a provider round-trip; `prune` trims by *token size* and is
provider-free. Different trigger, different cost, different mechanism — co-housing
them would entangle two independent strategies and violate the kernel's
"strategy stays swappable" thesis (`memory.ts:12-15`). Rejected (a): it couples
a cheap synchronous trim to an expensive async summarization and forces one
on/off switch for two concerns.

**D2 — The `transformContext` filter seam.** Problem: where to intervene?
Options: (a) a new kernel hook; (b) mutate `agent.messages` from an event
handler; (c) the existing `transformContext` filter (`agent.ts:247`). Choice:
**(c)**. Rationale: it is the documented seam for reshaping the message list
*just before the provider call* without touching the transcript (`memory`,
`skills`, `context-files` all use it). Rejected (a): no kernel change is needed.
Rejected (b): mutating the durable transcript is destructive and breaks the
purity contract `test/agent.test.ts:164` pins.

**D3 — Backward walk with a recency window + summary stop.** Problem: which tool
outputs are safe to trim? Options: (a) trim everything oldest-first; (b) protect
the most recent N *messages*; (c) protect the most recent N *user turns* and stop
at a summary boundary. Choice: **(c)** — protect the most recent **2 user
turns**, and stop the walk at any message whose `meta.kind === "summary"`. This
is opencode's rule (`compaction.ts:267-282`). Rationale: turns (not raw message
count) are the unit of "what the model is actively working on"; the summary
boundary means we never prune content that has already been folded into a
summary or sits before it. Rejected (a): trims live working context. Rejected
(b): a single tool-heavy turn can be many messages; a *turn* window tracks intent.

**D4 — Token-budget thresholds (keep first `PRUNE_PROTECT`, gate on
`PRUNE_MINIMUM`).** Problem: how aggressive? Choice: faithful port of opencode's
two-gate scheme. Walking backward over eligible (past the recency window)
completed `tool_result` blocks, accumulate an estimated-token `total`; while
`total ≤ PRUNE_PROTECT` keep verbatim; once it exceeds `PRUNE_PROTECT`, the
remaining (older) **oversized** outputs become prune candidates and their tokens
accumulate into `pruned`; **only if `pruned > PRUNE_MINIMUM`** actually truncate.
Constants: `PRUNE_PROTECT = 40_000` tokens, `PRUNE_MINIMUM = 20_000` tokens,
`TOOL_OUTPUT_MAX_CHARS = 2_000` chars (the cap each pruned output is truncated
to). Rationale: the two gates make `prune` a cheap no-op until there is *both* a
large protected head *and* substantial reclaimable tail — so it never churns a
context that is merely medium-sized. Values match opencode so behavior is a known
quantity. Rejected single-gate (prune as soon as over a window): churns small
savings for no benefit.

**D5 — `chars / 4` token estimate.** Problem: EAgent has no tokenizer (zero
deps). Options: (a) add a tokenizer dependency; (b) `Math.ceil(len / 4)`
heuristic. Choice: **(b)**. Rationale: the estimate only governs *when* to prune,
never correctness — over/under-estimating shifts the trigger point within the
wide `PRUNE_PROTECT`/`PRUNE_MINIMUM` margins, and `chars/4` is the standard cheap
approximation. Rejected (a): violates the zero-runtime-deps norm
(`CLAUDE.md` House conventions) for a trigger heuristic.

**D6 — Truncation shape.** A pruned output keeps its first `TOOL_OUTPUT_MAX_CHARS`
characters followed by a single human-legible marker line naming how many
characters were elided (e.g. `\n… [pruned 8123 chars to free context]`). Only
blocks whose `content.length > TOOL_OUTPUT_MAX_CHARS` are rewritten (truncating a
short output would only add a misleading marker and reclaims nothing). Rationale:
keeping the head preserves the most useful part (tool outputs front-load
identifying lines); the marker tells the model the content was elided, not lost.

**D7 — Ordering after `memory`.** Problem: filter order on the shared
`transformContext` point. Choice: register `prune` **after** `memory` in
`BUILTIN_EXTENSIONS`. Rationale: filters run in registration order
(`hooks.ts:64`), so `prune` operates on the *post-summarization* context — the
final shape sent to the model — trimming any large tool outputs `memory` kept
verbatim in its recent window. Both filters return new arrays and mutate nothing,
so the order is safe either way; after-`memory` is chosen so `prune` is the
last-line token defense. (When `memory` has summarized, its summary message sits
at index 0 with `meta.kind==="summary"`; `prune`'s backward walk halts there,
consistent with D3.)

## 5. Dependencies and Assumptions

- **Kernel `transformContext` filter** (`agent.ts:247-251`): signature
  `(messages: Message[], { turn, model }) => Message[] | Promise<…>`; its return
  value becomes `req.messages`; the persistent `#messages` is untouched.
- **Type shapes** (`src/kernel/types.ts`): `Message {role, content:
  ContentBlock[], meta?}`; `ToolResultBlock {type:"tool_result", toolCallId,
  content:string, isError?}`. `tool_result` blocks live in tool-role messages but
  `prune` scans every message's blocks generically.
- **`memory` summary marker**: `memory` tags its summary message
  `meta={source:"memory", kind:"summary"}` (`memory.ts:125`). `prune` keys only on
  `meta?.kind === "summary"`.
- **No network, no provider, no fs, no capability.** Pure in-memory transform;
  tests run offline under `MockProvider`.
- Assumption: a user turn begins at a `role==="user"` message (the agent loop
  appends the user message that opens each turn — `agent.ts:150`).

## 6. Relationship with Existing Designs

No prior `docs/design/*.md` covers context pruning. Closest existing artifacts:

- `src/extensions/memory.ts` — the count-based summarization filter on the same
  seam. `prune` is **complementary, not a conflict**: different trigger (tokens
  vs. message count), different mechanism (truncate vs. summarize), different cost
  (provider-free vs. one provider call). Ordering is specified in D7.
- `docs/design/2026-06-20-tool-output-spill.md` (cycle 2, `limits` extension) —
  spills *full* tool output to disk for the human audit trail. Orthogonal:
  spill preserves output losslessly **out-of-band**; `prune` trims what the
  **model** sees **in-band**. Neither reads the other's state.
- Terminology anchors: `CLAUDE.md` _language-policy_ (House conventions) and the
  kernel barrel `src/kernel/index.ts`.

No conflicts. No warning markers required.

## 7. Acceptance Criteria

Each maps to an offline assertion in `test/prune.test.ts` (invoke the filter via
the harness hook bus — `h.agent.hooks.apply("transformContext", msgs, {turn,
model})` — the idiom `test/memory.test.ts` uses) unless noted.

- **AC-1 (registration):** loading `prune` registers exactly one
  `transformContext` hook and nothing else (no tool, no command); `host.test.ts`
  passes with `prune` in `BUILTIN_EXTENSIONS`.
- **AC-2 (no-op below budget):** a context whose eligible tool outputs total
  `≤ PRUNE_PROTECT` tokens is returned with every `tool_result.content`
  unchanged.
- **AC-3 (prune over budget):** given a protected head ≥ `PRUNE_PROTECT` tokens
  of recent tool output **and** an older tail > `PRUNE_MINIMUM` tokens of
  oversized tool output, every old tail `tool_result.content` is truncated to
  `≤ TOOL_OUTPUT_MAX_CHARS` + the marker, the marker text is present, and the
  protected-head outputs are byte-for-byte verbatim.
- **AC-4 (recency protection):** a huge `tool_result` inside the most recent 2
  user turns is **never** truncated, even when the run is over budget.
- **AC-5 (summary boundary):** with a `meta.kind==="summary"` message present, no
  `tool_result` at or before it is truncated (the backward walk halts there).
- **AC-6 (below-minimum no-op):** a context just over `PRUNE_PROTECT` but whose
  reclaimable tail is `≤ PRUNE_MINIMUM` tokens is returned unchanged.
- **AC-7 (transcript purity):** after the filter runs, `h.agent.messages` and the
  original blocks' `content` are unchanged (the filter returns a new array; the
  original objects are not mutated) — mirrors `test/agent.test.ts:164`.
- **AC-8 (provider-free / no capability):** `prune` produces its result with a
  harness whose provider would throw if streamed (proving no provider round-trip),
  and registers no tool requiring a capability. **Quality budget** (hot path: runs
  every turn): a single linear pass, no `await` on any provider/network call —
  realized as this provider-free assertion.
- **AC-9 (kill switch):** with `EAGENT_PRUNE=off`, the filter is a pass-through
  (returns the input unchanged even when over budget).
- **AC-10 (suite):** `npm run typecheck` exit 0 and `npm test` `# fail 0`
  (≥ 307 prior + new subtests).

## 8. Risks and Rollback

- **Risk: pruning content the model still needs.** Mitigation: only *old* outputs
  (past the 2-turn recency window), only when *far* over budget (both gates), and
  the truncation keeps the head + an explicit marker so the model knows content
  was elided. Worst case is a re-read, not a silent loss (the full output also
  survives on disk when `limits` spill is active).
- **Risk: marker confuses the model.** Mitigation: the marker is a single plain-
  English line; tool outputs are already free-form text.
- **Risk: `chars/4` mis-estimates and prunes too eagerly / too late.**
  Mitigation: the estimate only moves the trigger within wide margins; it never
  affects which specific blocks are head vs. tail beyond the threshold crossing.
- **Risk: ordering interaction with `memory`.** Mitigation: both filters are pure
  (new array, no mutation); order is specified (D7) and either order is safe.
- **Rollback:** runtime — set `EAGENT_PRUNE=off` (the hook becomes a
  pass-through). Permanent — remove the one `["prune", prune]` line from
  `BUILTIN_EXTENSIONS`. No kernel change to revert; no persisted state to migrate.
