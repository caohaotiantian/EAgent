# Design: token-budget tool-output pruning (`prune` extension)

Slug: `2026-06-20-prune`

## 1. Background and Purpose

EAgent already has `memory` — a `transformContext` filter that folds the older
*prefix* of the transcript into a cached summary once the **message count**
crosses a threshold (`src/extensions/memory.ts:131-133`; defaults at
`memory.ts:27-28`: 12 messages, keep 4 recent). That defends against a long *conversation*, but not against a
*heavy* one: an agentic run can blow the model's context window with only a
handful of messages when those messages carry enormous tool outputs — five
whole-file `read`s, a giant `grep`, a verbose `bash` dump. Such a run never
trips `memory`'s count threshold yet still overflows.

The opencode project handles exactly this with a second, complementary
mechanism (`packages/opencode/src/session/compaction.ts`, the `prune` path,
MIT): walk the transcript backward, keep the most recent tool outputs verbatim,
and **truncate the older, oversized tool outputs in place** — a cheap, provider-
free trim that targets the single biggest space consumer in agentic context
(tool results) without summarizing or calling the model.

EAgent lacks this. This task ports it as a small `prune` extension on the same
`transformContext` seam `memory` uses, so the two compose: `memory` bounds by
*message count* (summarizing the old prefix), `prune` bounds by *token size*
(trimming old tool outputs in whatever context survives). If we do not, the only
context defense is count-based and silently inadequate for output-heavy runs.

## 2. Deliverables

- [ ] `src/extensions/prune.ts` — a `transformContext` filter that truncates old,
      oversized `tool_result` content beyond a protected recent window, returning
      a **new** message array; no tool, no command, no capability; honors an
      `EAGENT_PRUNE=off` runtime kill switch.
- [ ] `test/prune.test.ts` — offline tests covering AC 2–9 (no-op below budget,
      prune over budget, recency protection, summary boundary, below-minimum
      no-op, transcript purity, provider-free, metadata).
- [ ] `src/host.ts` — register `prune` in `BUILTIN_EXTENSIONS` (after `memory`,
      so it trims whatever context survives summarization).
- [ ] `CLAUDE.md` — one-line inventory entry for `prune`.

## 3. Scope Boundary (NOT in scope)

- **No summarization.** Folding old messages into an LLM summary is `memory`'s
  job; `prune` never calls a provider.
- **No transcript mutation / persistence.** `prune` is a pure `transformContext`
  transform: it returns a new array for the model to see and never alters
  `agent.messages` (the durable transcript) — identical to the contract `memory`
  and `test/agent.test.ts:164` already enforce.
- **No protected-tool-name set.** opencode protects `skill` tool *outputs*
  because skills there arrive as tool results. In EAgent skills are injected via
  `transformContext` (`src/extensions/skills.ts:43`), not as tool results, so no
  EAgent tool output carries must-keep instructions; the recency window and
  summary boundary already protect any live instructional content. Porting the
  protected-name set (and the `toolCallId → tool_call.name` correlation it needs)
  would be unrequested machinery for an empty set. (If a future EAgent tool ever
  emits must-keep instructions *as a tool result*, this exclusion must be
  revisited and the protected-name set reintroduced.)
- **No configurable thresholds beyond the kill switch.** Thresholds are module
  constants; no `e.store` override surface (that is unrequested flexibility —
  `memory`'s store-config pattern is not a mandate).
- **Only `tool_result` text is pruned.** `text`, `thinking`, and `image` blocks
  are untouched.
- **No new command or tool.** `prune` adds only a hook.

## 4. Key Design Decisions

**D1 — New extension vs. extending `memory`.** Problem: where does token-based
trimming live? Options: (a) fold it into `memory.ts`; (b) a new `prune`
extension. Choice: **(b)**. Rationale: `memory` summarizes by *message count*
and depends on a provider round-trip; `prune` trims by *token size* and is
provider-free. Different trigger, different cost, different mechanism — co-housing
them would entangle two independent strategies and violate the kernel's
"strategy stays swappable" thesis (`memory.ts:12-15`). Rejected (a): it couples
a cheap synchronous trim to an expensive async summarization and forces one
on/off switch for two concerns.

**D2 — The `transformContext` filter seam.** Problem: where to intervene?
Options: (a) a new kernel hook; (b) mutate `agent.messages` from an event
handler; (c) the existing `transformContext` filter (`agent.ts:247`). Choice:
**(c)**. Rationale: it is the documented seam for reshaping the message list
*just before the provider call* without touching the transcript (`memory`,
`skills`, `context-files` all use it). Rejected (a): no kernel change is needed.
Rejected (b): mutating the durable transcript is destructive and breaks the
purity contract `test/agent.test.ts:164` pins.

**D3 — Backward walk with a recency window + summary stop.** Problem: which tool
outputs are safe to trim? Options: (a) trim everything oldest-first; (b) protect
the most recent N *messages*; (c) protect a recent *user-turn* window and stop at
a summary boundary. Choice: **(c)**, ported mechanically from opencode's loop
(`compaction.ts:268-272`). Precise rule, walking the message list **from last to
first** with a counter `turns = 0`:

1. For each message: if `role === "user"`, increment `turns` **first**.
2. If `turns < 2`, the message is **protected** — skip it (do not prune its
   `tool_result` blocks) and continue.
3. Otherwise the message is **eligible** for pruning.
4. If a message has `meta?.kind === "summary"`, **stop** the walk entirely (it and
   everything older is left untouched).

Because the increment precedes the guard, eligibility begins **at the
second-most-recent `user` message itself**: protected = every message strictly
after the 2nd-most-recent `user` message (i.e. the most-recent user message and
all content following it). This is exactly opencode's fence-post, not "2 whole
turns" — the doc states the loop, not an approximation. Rationale: user messages
delimit "what the model is actively working on", and a tool-heavy single turn can
be many messages, so a *turn-counted* window tracks intent better than a raw
message count. The summary stop means we never prune content already folded into
(or sitting before) a summary. Rejected (a): trims live working context.
Rejected (b): message count ignores turn structure.

opencode has a *second* `break loop` — `if (part.state.time.compacted) break loop`
(`compaction.ts:278`) — that **halts the entire backward walk** the moment it
reaches a part a prior prune already truncated (the persisted `compacted` flag).
EAgent's filter is **stateless per call** (it re-derives the trim from scratch
each turn and never persists a `compacted` flag), so that break has no analogue
and is intentionally not ported; idempotence is instead guaranteed by D6 (a block
already at/under the cap is never rewritten).

**D4 — Token-budget thresholds (keep within `PRUNE_PROTECT`, gate on
`PRUNE_MINIMUM`).** Problem: how aggressive? Choice: faithful port of opencode's
two-gate scheme (`compaction.ts:279-283,288`). Walking backward over eligible
(past the recency window) completed `tool_result` blocks, accumulate an
estimated-token `total` **that includes each candidate as it is examined**. The
exact opencode rule, per block: `total += est(block)`; **if** `total <=
PRUNE_PROTECT`, keep this block verbatim (`continue`); **else** this block — the
one whose inclusion pushed `total` past `PRUNE_PROTECT` — and every older eligible
block is a prune candidate: add its tokens to `pruned` and mark it. So the
*crossing* block is itself pruned, **not** kept. Then, **only if `pruned >
PRUNE_MINIMUM`**, actually truncate the marked blocks (D6). Constants:
`PRUNE_PROTECT = 40_000` tokens, `PRUNE_MINIMUM = 20_000` tokens,
`TOOL_OUTPUT_MAX_CHARS = 2_000` chars (the cap each pruned output is truncated
to). Rationale: the two gates make `prune` a cheap no-op until there is *both* a
protected head whose cumulative size stays within `PRUNE_PROTECT` *and* a
reclaimable tail (everything from the crossing block onward) exceeding
`PRUNE_MINIMUM` — so it never churns a context that is merely medium-sized.
Values and comparisons (`<=`, `>`) match opencode so behavior is a known
quantity. Rejected single-gate (prune as soon as over a window): churns small
savings for no benefit.

**D5 — `chars / 4` token estimate.** Problem: EAgent has no tokenizer (zero
deps). Options: (a) add a tokenizer dependency; (b) a `chars / 4` heuristic.
Choice: **(b)**, matching opencode's own estimator exactly —
`Math.max(0, Math.round(input.length / 4))` (`packages/core/src/util/token.ts`).
Rationale: the estimate only governs *when* to prune, never correctness —
over/under-estimating shifts the trigger point within the wide
`PRUNE_PROTECT`/`PRUNE_MINIMUM` margins; using opencode's exact rounding keeps the
"behavior is a known quantity" fidelity claim honest. Rejected (a): violates the
zero-runtime-deps norm (`CLAUDE.md` House conventions) for a trigger heuristic.

**D6 — Truncation shape.** A pruned output keeps its first `TOOL_OUTPUT_MAX_CHARS`
characters followed by a single human-legible marker line naming how many
characters were elided (e.g. `\n… [pruned 8123 chars to free context]`). Only
blocks whose `content.length > TOOL_OUTPUT_MAX_CHARS` are rewritten (truncating a
short output would only add a misleading marker and reclaims nothing). Rationale:
keeping the head preserves the most useful part (tool outputs front-load
identifying lines); the marker tells the model the content was elided, not lost.

**D7 — Ordering after `memory`.** Problem: filter order on the shared
`transformContext` point. Choice: register `prune` **after** `memory` in
`BUILTIN_EXTENSIONS`. Rationale: filters run in registration order
(`hooks.ts:64`), so `prune` operates on the *post-summarization* context — the
final shape sent to the model — trimming any large tool outputs `memory` kept
verbatim in its recent window. Both filters return new arrays and mutate nothing,
so the order is safe either way; after-`memory` is chosen so `prune` is the
last-line token defense. Two honest caveats: (i) when `memory` has summarized, its
summary message sits at **index 0** (`memory.ts:142`), so `prune`'s backward walk
reaches it only as the very last element — the summary stop (D3 step 4) is
therefore a **belt-and-suspenders** guard here, load-bearing only if a summary
ever appears mid-transcript (e.g. a future persisted-summary design), not in
today's prepend-each-turn `memory`; AC-5 tests the rule, not a claim that it
fires in normal `memory` operation. (ii) `memory`'s summary is a **`system`**
message (`memory.ts:124`) whereas opencode's boundary is an `assistant` message
with `summary:true`; `prune` keys only on `meta?.kind === "summary"` and is
role-agnostic, so the role difference is immaterial.

## 5. Dependencies and Assumptions

- **Kernel `transformContext` filter** (`agent.ts:247-251`): signature
  `(messages: Message[], { turn, model }) => Message[] | Promise<…>`; its return
  value becomes `req.messages`; the persistent `#messages` is untouched.
- **Type shapes** (`src/kernel/types.ts`): `Message {role, content:
  ContentBlock[], meta?}`; `ToolResultBlock {type:"tool_result", toolCallId,
  content:string, isError?}`. `tool_result` blocks live in tool-role messages but
  `prune` scans every message's blocks generically.
- **`memory` summary marker**: `memory` tags its summary message
  `meta={source:"memory", kind:"summary"}` (`memory.ts:125`). `prune` keys only on
  `meta?.kind === "summary"`.
- **No network, no provider, no fs, no capability.** Pure in-memory transform;
  tests run offline under `MockProvider`.
- Assumption: a user turn begins at a `role==="user"` message (the agent loop
  appends the user message that opens each turn — `agent.ts:150`).

## 6. Relationship with Existing Designs

No prior `docs/design/*.md` covers context pruning. Closest existing artifacts:

- `src/extensions/memory.ts` — the count-based summarization filter on the same
  seam. `prune` is **complementary, not a conflict**: different trigger (tokens
  vs. message count), different mechanism (truncate vs. summarize), different cost
  (provider-free vs. one provider call). Ordering is specified in D7.
- `docs/design/2026-06-20-tool-output-spill.md` (cycle 2, `limits` extension) —
  spills *full* tool output to disk for the human audit trail. Orthogonal:
  spill preserves output losslessly **out-of-band** (it operates on tool-output
  bytes at dispatch, on the durable transcript), while `prune` trims what the
  **model** sees **in-band** (a `transformContext` copy). Neither reads the
  other's state and `prune` does **not depend on** spill being enabled — the
  on-disk copy is an independent convenience, not a correctness prerequisite.
- Terminology anchors: `CLAUDE.md` _language-policy_ (House conventions) and the
  kernel barrel `src/kernel/index.ts`.

No conflicts. No warning markers required.

## 7. Acceptance Criteria

Each maps to an offline assertion in `test/prune.test.ts`. Unless noted, invoke
the filter the way `test/memory.test.ts` does — capture the registered handler and
call it, or apply it through the harness hook bus
(`h.agent.hooks.apply("transformContext", msgs, {turn, model})`).

**Fixture-token convention (pins the boundary tests).** A test controls only
`content.length`; the estimate is `est(s) = Math.max(0, Math.round(s.length/4))`.
So an output of exactly `4 * N` characters estimates to `N` tokens. The gates use
opencode's comparisons: a block is kept verbatim while the running `total`
of eligible-output tokens is `total <= PRUNE_PROTECT`; pruning is committed only
when reclaimable `pruned > PRUNE_MINIMUM` (both strict per `compaction.ts:281,288`).
Fixtures state exact char counts so each boundary is deterministic.

- **AC-1 (registration, measured):** snapshot `agent.tools.list().length` and the
  command-registry size before and after `host.use("prune", prune)`; both are
  **unchanged** (no tool, no command), and the `transformContext` listener count
  increases by exactly one. `host.test.ts` also passes with `prune` in
  `BUILTIN_EXTENSIONS`.
- **AC-2 (no-op below budget):** an eligible region whose tool outputs total
  `<= PRUNE_PROTECT` tokens (e.g. one eligible `tool_result` of `4*40000` chars →
  40000 tokens, exactly at the boundary, plus the protected recent window) is
  returned with **every** `tool_result.content` unchanged.
- **AC-3 (prune over budget):** in the eligible region (the older part of a
  ≥3-user-turn transcript, before the recency window), place these oversized
  `tool_result`s **newest→oldest**: A=`4*30000` chars (30000 tok), B=`4*8000`
  (8000 tok), C=`4*8000` (8000 tok), D=`4*8000` (8000 tok), E=`4*8000` (8000 tok).
  Cumulative `total`: A→30000 (`<=40000`, **kept**), B→38000 (**kept**), C→46000
  (`>40000`, **crossing — pruned**), D→54000 (**pruned**), E→62000 (**pruned**);
  `pruned = 8000*3 = 24000 > PRUNE_MINIMUM`, so C, D, E are truncated. Assert: C,
  D, E each have `content.length <= TOOL_OUTPUT_MAX_CHARS + markerLen` and contain
  the marker substring; A and B (both oversized, so a wrong implementation that
  pruned them would be detectable) remain **byte-for-byte verbatim**.
- **AC-4 (recency protection):** a `tool_result` of `4*60000` chars located
  **after the second-most-recent `user` message** (inside the protected window per
  D3) is **never** truncated, even when the eligible region is independently over
  budget.
- **AC-5 (summary boundary):** with a `meta.kind==="summary"` message placed
  mid-list and over-budget oversized tool outputs **at and before** it, none of
  those at-or-before-the-summary outputs is truncated (the backward walk halts at
  step 4 of D3).
- **AC-6 (below-minimum no-op):** an eligible region that crosses the first gate
  but whose reclaimable tail is `<= PRUNE_MINIMUM` tokens is returned unchanged.
  Fixture (newest→oldest eligible): a kept block of `4*38000` chars (38000 tok,
  `total=38000 <= 40000`, kept) then one oversized crossing block of `4*5000`
  chars (5000 tok, `total=43000 > 40000` → crossing, `pruned=5000`). Since
  `pruned = 5000` is **not** `> PRUNE_MINIMUM`, nothing is truncated — every
  `content` is byte-for-byte unchanged.
- **AC-7 (transcript purity):** after the filter runs over an over-budget input,
  the original message array, every original `Message` object, and every original
  `tool_result.content` string are unchanged (the filter returns a **new** array
  with new block objects; inputs are not mutated) — mirrors `test/agent.test.ts`
  ("transformContext must not mutate the persistent transcript").
- **AC-8 (hot-path budget — two measured parts):**
  - *(a) provider-free under a real turn:* run a full `h.agent.run(...)` (one
    scripted assistant `{text}` turn) under a `MockProvider` wrapped to **count**
    `stream` invocations, over an over-budget transcript with `prune` loaded;
    assert the count equals exactly the number of agent turns (one) — i.e. `prune`
    adds **zero** provider round-trips (contrast `memory`, which would add one).
  - *(b) synchronous single pass:* the registered `prune` handler, captured and
    invoked directly, returns a plain array **synchronously** — its return value is
    not a `Promise`/thenable (`typeof ret.then !== "function"`), proving the hot
    path does not `await` any provider/network call.
  - It also registers no tool requiring a capability (subsumed by AC-1).
- **AC-9 (kill switch):** with `process.env.EAGENT_PRUNE="off"`, the filter is a
  pass-through — an over-budget input is returned with every `content` unchanged
  (restore the env var in `finally`).
- **AC-10 (suite):** `npm run typecheck` exit 0 and `npm test` `# fail 0`
  (≥ 307 prior + new subtests).

## 8. Risks and Rollback

- **Risk: pruning content the model still needs.** Mitigation: only *old* outputs
  (before the recency window — at/older than the 2nd-most-recent `user` message
  per D3), only when *far* over budget (both gates), and
  the truncation keeps the head + an explicit marker so the model knows content
  was elided. Worst case is a re-read, not a silent loss (and if the `limits`
  spill is enabled, the full output is independently retained on disk — though
  `prune` does not rely on that).
- **Risk: marker confuses the model.** Mitigation: the marker is a single plain-
  English line; tool outputs are already free-form text.
- **Risk: `chars/4` mis-estimates and prunes too eagerly / too late.**
  Mitigation: the estimate only moves the trigger within wide margins; it never
  affects which specific blocks are head vs. tail beyond the threshold crossing.
- **Risk: ordering interaction with `memory`.** Mitigation: both filters are pure
  (new array, no mutation); order is specified (D7) and either order is safe.
- **Rollback:** runtime — set `EAGENT_PRUNE=off` (the hook becomes a
  pass-through). Permanent — remove the one `["prune", prune]` line from
  `BUILTIN_EXTENSIONS`. No kernel change to revert; no persisted state to migrate.
