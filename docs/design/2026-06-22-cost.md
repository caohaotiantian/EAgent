# cost — token→USD accounting + rolling-mean run-cost anomaly flag

Status: closed
Closing-commit: c8ae864
Closed-on: 2026-06-22
Deferred: none

Design author: EAgent design team · Date: 2026-06-22

## 1. Background and Purpose

EAgent can already *count* tokens but cannot *price* them.

- `trace` (`src/extensions/trace.ts`) is a pure event-bus consumer: it folds
  `on("usage")` into a lifetime `Usage` aggregate and exposes `/usage`
  (`trace.ts:165-172`, `:203-216`). It reports `in=…  out=…  total=…` token
  counts — **no dollars, no per-model split, no baseline**.
- `limits` (`src/extensions/limits.ts`) enforces a **static** per-run token
  **count** cap via `agent_start` + `beforeToolCall` (`limits.ts:200-234`). It
  blocks at a fixed number — **no dollars, no learned baseline**.

So a run on an expensive model that burns a large but *legal* token count
produces no signal at all, and nobody can answer "what did this session cost?"
or "is this run abnormally expensive?". You cannot optimize what you cannot
measure.

**Purpose.** Add a new `cost` extension — a *sibling* of `trace`, in the exact
same pure-consumer shape — that (1) maps tokens to USD via a static, date-pinned
price card; (2) accumulates per-run and cumulative-session cost, split per
model; (3) learns a rolling baseline of recent run costs and emits a **warn-only**
anomaly flag when a finished run's cost is a statistical outlier; (4) exposes
`/cost`. It is **observability only** — it never blocks (that is `limits`' job)
and requires **zero kernel change** (it reads the existing `usage` payload and
`e.agent.model`).

## 3. Scope Boundary (NON-goals — Simplicity First)

Explicitly **out of scope**; do not build:

1. **No new token categories.** Cost is computed from `Usage.inputTokens` and
   `Usage.outputTokens` **only** (`types.ts:182-185`). Cache-read, cache-write,
   and reasoning-token pricing are **deferred** — accounting for them would
   require widening the kernel `Usage` type and every provider, a
   kernel-boundary change that violates "no kernel change" (see D2). Documented
   here as a follow-up, not a gap.
2. **No enforcement / blocking.** `cost` never returns a blocking `ToolDecision`
   and registers **no** `beforeToolCall` hook. A dollar budget that *blocks*
   would duplicate `limits`' per-run cap (see D6). Anomaly detection is
   **warn-only** and never alters control flow.
3. **No live price fetching.** No network call, ever (house rule: zero runtime
   deps, providers-only `fetch`). The price card is a static constant; staleness
   is mitigated by a pinned date comment + store override (see D1).
4. **No persisted per-model history / cost database / CSV export.** The only
   persisted state is the `priceCard` override and the small fixed-size rolling
   window. Per-model breakdown is computed in-memory for the live session only.
   (`trace` keeps detail for the last run only for the same reason.)
5. **No per-task / per-label cost attribution.** A single global rolling window;
   no task-label buckets (see D3).
6. **No new capability.** `cost` has no side effects beyond reading the event
   bus and writing its own namespaced store; like `trace`/`limits` it declares
   no capability.

## 4. Key Design Decisions

### D1 — Price source: static date-pinned card vs live rate fetch

- **Problem.** Tokens must be multiplied by a USD rate per model; rates change
  over time.
- **Options.** (a) Static, date-pinned price-card constant compiled into the
  extension. (b) Fetch live rates from a pricing endpoint at runtime.
- **Choice.** (a) Static date-pinned card, overridable via the `priceCard`
  store key, with that override **settable at runtime through a `/cost
  pricecard <model> <inputPerMTok> <outputPerMTok>` sub-command** (the `/cost`
  command is therefore *read + a price-card setter sub-command*, not read-only).
- **Rationale.** House rules forbid runtime deps and non-provider network I/O
  ("providers use the global `fetch`; nothing else"). A static constant is
  zero-dep and offline-testable. Staleness is mitigated three ways: a pinned
  `// rates as of 2026-06-22` comment, an operator override of the `priceCard`
  store key, and a clearly-marked fallback rate for unknown models. The override
  is exposed through the `/cost pricecard …` setter so an operator can retune a
  rate live without editing code — the idiomatic EAgent self-configuration
  pattern (`limits` writes its own store config via `/limits key=value`,
  `test/limits.test.ts:83`). Making the override command-settable also gives the
  test suite a reachable seam to seed `priceCard` before a run (the store
  backend is private and not exposed by the harness), which is what makes AC-6
  testable. The non-`priceCard` config (`enabled`, threshold/mode) stays
  store-backed; only `priceCard` needs the command setter for runtime tuning and
  testability.
- **Why (b) rejected.** A live fetch adds a network dependency, breaks the
  offline test guarantee (`npm test` must run with no network / no API key), and
  introduces a failure mode (endpoint down → no cost) for a pure-observability
  feature. Rejected.

### D2 — Token categories: input+output only vs adding cache/reasoning

- **Problem.** Real bills include cache-read/write and reasoning tokens at
  different rates.
- **Options.** (a) Price `inputTokens` + `outputTokens` only — the two fields
  the kernel `Usage` type actually carries. (b) Add cache/reasoning categories.
- **Choice.** (a) input + output only.
- **Rationale.** The `usage` event payload is exactly `{ usage, cumulative }`
  where `usage: Usage = { inputTokens, outputTokens }` (`types.ts:182-185`,
  emitted at `agent.ts:278`). Pricing only these keeps `cost` a *pure*
  no-kernel-change consumer.
- **Why (b) rejected.** Adding categories requires widening the kernel `Usage`
  type (`types.ts:182`) **and** updating every provider that fills it — a
  kernel-boundary change. That contradicts the whole premise ("new behavior is
  always an extension, never a fork"). Deferred to a follow-up and recorded in
  §3.1. Rejected for this iteration.

### D3 — Anomaly baseline: per-task-label buckets vs single global rolling window

- **Problem.** "Abnormally high" needs a baseline to compare against.
- **Options.** (a) Per-task-label buckets (a separate rolling window per task
  type). (b) A bucket keyed by a hash of the first user message. (c) A single
  global rolling window of the last N run costs.
- **Choice.** (c) A single global rolling window (fixed size, e.g. last 20 run
  costs, stored under `e.store`).
- **Rationale.** There is no reliable host-supplied task label on the bus — the
  `agent_start` payload is just `{ input: userMessage }` (`agent.ts:156`); the
  loop has no notion of "task type". A global window catches *gross* spikes
  (a run that costs 10× the recent norm) with trivial, observable math, and is
  explicitly documented as **coarse** and **warn-only**.
- **Why (a) rejected.** No trustworthy label exists to bucket on. **Why (b)
  rejected.** A first-message hash is crude and noisy — paraphrases land in
  different buckets, so each bucket stays tiny and the min-sample guard (D4)
  never lets it fire. A global window is simpler and actually triggers. Rejected.

### D4 — Anomaly threshold k and min-sample guard (THRESHOLD DECISION)

- **Problem.** When does a finished run's cost count as an outlier?
- **Options.** (a) `k = 2σ` above the rolling mean. (b) `k = 3σ`. (c) A flat
  percentage over the mean (e.g. > 150%). Plus: a minimum prior-sample count
  `N` before any warning may fire.
- **Choice.** Warn when `cost > mean + k·stddev` with **`k = 3`** and a guard of
  **`N ≥ 5`** prior samples in the window. Both surfaced as named constants
  (`ANOMALY_K = 3`, `ANOMALY_MIN_SAMPLES = 5`).
- **Rationale.** `3σ` is the conventional gross-outlier threshold and is
  deliberately conservative: a *false* cost alarm is worse than a missed one,
  because it trains users to ignore the warning. The `N ≥ 5` guard prevents a
  tiny sample (where stddev is meaningless / near-zero) from firing a spurious
  warning on the 2nd or 3rd run of a session.
- **Why (a) rejected.** `2σ` fires on ~5% of normal runs — too chatty for a
  warn-only signal meant to flag the *gross* spike. **Why (c) rejected.** A flat
  percentage ignores variance: a session with naturally bursty costs would warn
  constantly, while a low-variance session would miss a real regression that a
  σ-based test catches. Rejected.

### D5 — Posture: on-by-default observability vs opt-in

- **Problem.** Should `cost` run by default?
- **Options.** (a) On by default (pure observability, like `trace`). (b) Off by
  default / opt-in (like `risk-guard`).
- **Choice.** (a) On by default, with an `EAGENT_COST=off` env kill switch and
  an `e.store` `enabled` flag.
- **Rationale.** `cost` is *non-intervening* — it never blocks, only listens and
  prints, exactly the `trace` profile (which is on by default with no capability
  and no env gate of its own). Cost visibility is broadly useful and has no
  control-flow risk, so it should be present without configuration.
- **Why (b) rejected.** Opt-in posture belongs to extensions that *intervene*
  (`risk-guard` asks/blocks, so it is off by default — `README.md:219`). `cost`
  intervenes in nothing, so gating it behind opt-in would just hide a useful,
  harmless view. The env kill switch + store flag already give the off-ramp.
  Rejected.

### D6 — Measurement only vs cost enforcement

- **Problem.** Once you know the dollar cost, should you also *cap* it?
- **Options.** (a) `cost` measures only; enforcement stays in `limits`. (b) Add
  a `beforeToolCall` dollar-budget block to `cost`.
- **Choice.** (a) Measurement only.
- **Rationale.** Single responsibility: `limits` already owns per-run budget
  enforcement via `beforeToolCall` (`limits.ts:210-234`). `cost` adds the
  *dollar view* and the *learned baseline* that `limits` lacks. Two extensions,
  two distinct jobs.
- **Why (b) rejected.** A dollar-budget `beforeToolCall` would duplicate
  `limits`' mechanism and create two places that block a run — confusing and
  redundant. If dollar-enforcement is ever wanted, the right move is to extend
  `limits` to read a cost figure, not to grow a second gate in `cost`. Rejected.

## 5. Dependencies and Assumptions

- **Kernel surface used (all existing, no change):**
  - `e.on("usage", …)` payload `{ usage: Usage, cumulative: Usage }` — emitted at
    `agent.ts:278`; `Usage = { inputTokens, outputTokens }` (`types.ts:182-185`).
  - `e.on("agent_start", …)` payload `{ input: Message }` — emitted at
    `agent.ts:156` (used only as a reset trigger; the model is read separately).
  - `e.on("agent_end", …)` payload `{ reason: StopReason }` — emitted at
    `agent.ts:235`.
  - `e.agent.model: string` — the active model id (`types.ts:241-242`,
    `AgentHandle.model`); the price-card lookup key.
  - `e.store.get/set` — namespaced, persistent (`store.ts:12-17`); holds
    `priceCard`, `enabled`, and the rolling window. Note: `get<T>(key, fallback)`
    returns `fallback` when absent.
  - `e.registerCommand`, `e.log.warn` — `extension.ts:230`, `extension.ts:235`.
- **Model ids that exist** (host defaulting, `host.ts:145-153`): `claude-fable-5`
  (Anthropic default), `gpt-4o` (OpenAI), `gemini-2.0-flash` (Gemini), `mock`
  (tests). The price card pins rows for these plus a documented fallback. Also
  acknowledged: `claude-opus-*` / `claude-sonnet-*` model families may appear via
  `ANTHROPIC_MODEL`.
- **Assumptions.**
  - The `usage` event's `cumulative` is the agent's running total (the agent sums
    deltas at `agent.ts:277`); `cost` mirrors `cumulative` for the session figure
    and uses the per-event `usage` delta for the per-run figure, matching how
    `trace` mirrors `cumulative` (`trace.ts:167-171`).
  - `e.agent.model` is stable for the duration of a single run (it is read once
    per run, stamped on `agent_start`).
  - `mock` and any unknown model price at the documented fallback (D1) so tests
    and unfamiliar endpoints never silently report a misleading dollar figure.
- **House rules honored:** ESM `.js` specifiers, strict TS (no `any`,
  `noUncheckedIndexedAccess`), zero runtime deps, offline `node:test`, kill
  switch, never-throwing dispose loop.

## 6. Relationship with Existing Designs

- **`src/extensions/trace.ts` (closest — the pattern this mirrors).** `cost` is a
  *sibling observability consumer*: same `on("usage")` + `on("agent_*")` +
  `registerCommand("/cost")` shape (`trace.ts:98-173`, `:218-250`), same
  `safe()`-wrapped handlers that never throw, same never-throwing dispose loop
  (`trace.ts:252-260`). **Dedup:** `trace` counts tokens and exposes `/usage`;
  `cost` adds the USD layer, the per-model split, and the learned baseline —
  distinct, non-overlapping views. No conflict.
- **`src/extensions/limits.ts`.** `limits` enforces a *static per-run token
  count* cap (`limits.ts:210-234`). **Dedup:** `cost` adds the *dollar* figure
  and the *rolling baseline* that `limits` has no notion of, and it **does not
  block** (D6). No conflict — complementary.
- **`src/host.ts` model defaulting (`host.ts:145-153`).** The source of truth for
  which model ids exist; the price card's pinned rows are derived from it. No
  change to `host.ts` beyond adding the `cost` entry to `BUILTIN_EXTENSIONS`.
- **First-design note.** This is the **first** extension to introduce USD/price
  accounting and a *learned* (statistical) cost baseline in EAgent. No prior
  design covers price cards or anomaly detection over run cost.

## 7. Acceptance Criteria

All measurable via `makeHarness` (`test/helpers.ts:27`) + a `MockProvider`.
The mock reports `usage` on its `done` event (`mock.ts:96-100`), so usage flows
through `agent.run()` → `agent.ts:278`. **Note on driving usage:** `MockProvider`
usage is *not* a scriptable field — `MockTurn` carries only `{text, reasoning,
toolCalls}` (`mock.ts:26-31`) and `usage` is **computed** deterministically as
`estimateTokens = ceil(len/4)` over `systemPrompt + messages + output text`
(`mock.ts:96-99`, `:121-122`). The suite therefore drives **known** token counts
by crafting input/output **text lengths** (e.g. a `turn.text` of exactly `4·M`
characters yields `outputTokens = M`) and reads the *actual* emitted `usage` off
the `usage` event, asserting cost as a **derived/relative** figure (the mock's
own counts × the price card), never a hard-coded round-number bill. No mock
change is required — the offline mock stays "that way" per CLAUDE.md. Each
criterion is a runnable assertion in `test/cost.test.ts`.

1. **Cost is computed from priced tokens.** With a known price card pricing model
   `mock` at `{inputPerMTok: 2, outputPerMTok: 6}`, after one `agent.run("hi")` the
   reported session cumulative USD equals the *derived* figure computed from the
   mock's **own emitted** `usage` — captured off the `usage` event — i.e.
   `inputTokens/1e6·$2 + outputTokens/1e6·$6`. *Assertion:* capture
   `{inputTokens, outputTokens}` from the `usage` event, compute `expected`, and
   `assert.match(out, …)` / compare the `/cost` USD to `expected` rounded to the
   chosen format (no hard-coded round-number bill — the mock cannot emit one).
2. **`/cost` prints the required four blocks.** Output contains (a) session
   cumulative USD + token totals, (b) a per-model breakdown line naming the model
   (`mock`), (c) the active price-card row(s), (d) an anomaly-status line naming
   the rolling mean and last-run cost. *Assertion:* four `assert.match` checks for
   labelled lines (`/cumulative/i`, `/per-model/i` or model id, `/price/i`,
   `/anomaly|baseline|mean/i`).
3. **Per-run reset on `agent_start`.** After two runs, the *per-run* (last-run)
   cost reflects only the second run's tokens, not the sum. *Assertion:* drive two
   runs whose mock outputs are crafted to differ in length (e.g. run 2's `turn.text`
   ≈ 2× run 1's, so its `outputTokens` ≈ 2×); capture each run's emitted `usage`
   off the `usage` event and assert the last-run figure equals run 2's *derived*
   price, while cumulative equals run1+run2 — a relative check, not a fixed bill.
4. **Anomaly warning fires on a gross spike, only past the min-sample guard.**
   Script ≥ 5 cheap runs (establishing a low-variance window) then one run whose
   cost ≫ mean + 3σ; capture `e.log.warn` via a custom `logger` passed to
   `makeHarness`. *Assertion:* `warn` is called exactly **once**, on the spike
   run, and the message names the run cost vs the rolling mean. Also assert **no**
   warning fires before `ANOMALY_MIN_SAMPLES` (5) prior samples exist.
5. **Anomaly never blocks.** Even when the warning fires, the spike run's
   `agent.run()` resolves normally and no tool call is vetoed. *Assertion:* the
   run's returned stop reason is unchanged and `lastText(agent)` is non-empty;
   `cost` registers no `beforeToolCall` hook (assert via absence of any decision
   block on a tool-using run).
6. **Price-card override via the `/cost pricecard` setter takes effect.**
   Invoking `/cost pricecard mock <10×in> <10×out>` before a run (the
   command writes the validated row to `e.store`, mirroring `/limits key=value`
   at `test/limits.test.ts:83`) changes the reported USD. *Assertion:* seed a
   10× row through `runCommand(h, "cost", "pricecard mock …")`, run, then assert
   the session USD in `/cost` output is 10× the default-card figure for the same
   token count. (This is the reachable seam: the harness does not expose the
   store backend, so the override must be set through the command.)
7. **Unknown / `mock` model uses the marked fallback, never crashes.** A run on a
   model id absent from the card produces a finite USD figure at the documented
   fallback rate (or `$0.00` with a clear marker) and the per-model line is marked
   as a fallback. *Assertion:* `assert.ok(Number.isFinite(usd))` and
   `assert.match(out, /fallback|unknown/i)`.
8. **Kill switch disables the extension.** With `EAGENT_COST=off`, activation is a
   no-op: `/cost` is **not** registered and no `usage` handler accumulates.
   *Assertion:* `assert.equal(h.commands.get("cost"), undefined)` after activating
   with the env var set; restore env in a `finally`.
9. **Dispose is clean and never throws.** After `host.unload("cost")` (or the
   returned deactivate), `/cost` is gone and a subsequent `agent.run()` triggers
   no `cost` handler. *Assertion:* command lookup returns `undefined`; the dispose
   loop swallows a thrown disposer (mirrors `trace.ts:252-260`).
10. **`npm test` and `npm run typecheck` both pass** with the new suite included
    (strict TS, no `any`). *Assertion:* CI/local gate — recorded as commit
    trailers per convention.

## 8. Risks and Rollback

- **Risk: price cards go stale.** Rates drift; a pinned card eventually
  misprices. *Mitigation:* date-pinned `// rates as of 2026-06-22` comment, the
  `priceCard` store override (operators retune without a code change), and a
  clearly-marked fallback so `mock`/unknown models report `$0.00` or an explicitly
  "(fallback rate)"-labelled figure rather than a confident wrong number. The
  figure is advisory observability, never a billing source of truth.
- **Risk: the global rolling baseline is coarse.** It can miss a per-task cost
  regression (a specific task type getting more expensive while the global mean
  stays flat) or warn on a single legitimately-large run. *Mitigation:*
  warn-only (never blocks), conservative `k = 3σ`, the `N ≥ 5` min-sample guard,
  and the `/cost` line stating the math so a human can judge it. Documented as
  coarse in §4 D3.
- **Risk: a thrown handler corrupts the run.** *Mitigation:* every `on(…)`
  handler is `safe()`-wrapped (trace pattern, `trace.ts:88-96`); the dispose loop
  swallows errors (`trace.ts:252-260`). A `cost` failure can at worst drop a cost
  number, never a turn.
- **Risk: a malformed `priceCard` store override.** *Mitigation:* the card reader
  validates each row's shape (numeric `inputPerMTok`/`outputPerMTok`) and falls
  back to the built-in row / fallback rate on anything malformed — the same
  defensive-read posture `limits` uses for its store config (`limits.ts:88-122`).
- **Rollback.**
  - **Kill switch:** `EAGENT_COST=off` (env) disables activation entirely; the
    `enabled` store flag does the same at runtime. `/cost` only reads or writes
    `cost`'s own namespaced store (the `pricecard` setter writes a price row;
    the status form is read-only) and never blocks or mutates a run, so leaving
    it active is harmless.
  - **Unload:** `host.unload("cost")` / hot reload tears down every registration
    cleanly (tracked disposables, `extension.ts:218-255`).
  - **Persisted state:** the only persisted keys are `priceCard` (operator
    override) and the rolling-window samples in `e.store`; deleting them, or
    removing the `cost` entry from `BUILTIN_EXTENSIONS` in `host.ts`, fully
    reverts the feature with no kernel residue.
