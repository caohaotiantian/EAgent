# Design: `ask` — agent→host elicitation (`ask_user_question`) with a `ui:ask` capability

Slug: `2026-06-22-ask`
Date: 2026-06-22
Status: closed
Closing-commit: 065efbe
Closed-on: 2026-06-23
Deferred: **delivered** — the durable async server-side ask/resume channel (HTTP
elicitation) is now built (see §9, B1): the server pauses the turn, emits an
`action_required` event on the open `/run` stream, and resumes when the client
answers via `POST /answer`, with a bounded-timeout + disconnect fallback. Residual
(still deferred): concurrent multi-question elicitation within a single turn (one
pending ask at a time per turn is the supported shape) and cross-process/queued
durability (the pending-ask registry is in-memory and single-flight, so a server
restart drops an in-flight question).

## 1. Background and Purpose

EAgent already has a host→agent injection path: `steer(message)` and
`followUp(message)` on the `AgentHandle` (`src/kernel/types.ts:245-248`,
implemented `src/kernel/agent.ts:128-135`, exposed to tools via
`ctx.agent.handle` at `agent.ts:118-125`). The *human* can interrupt or nudge the
running agent at will.

There is no inverse — no **agent→host elicitation**. The model cannot pause,
surface a concrete "which of these did you mean?" question to the human, and
block on the answer before committing to a direction. The only human-facing UI
primitive the kernel exposes is a yes/no `confirm` plus a fire-and-forget
`notify`:

```ts
// src/kernel/types.ts:227-231
export interface UI {
  /** Ask the human a yes/no question. Resolves to the decision. */
  confirm(question: string): Promise<boolean>;
  notify(message: string): void;
}
```

`confirm` can only ratify a decision the model has *already* made ("Allow X?").
It cannot collect a free-form or multiple-choice answer *before* the model
chooses. So on an ambiguous instruction ("update the config" — which config?
"deploy it" — which environment?) the model **guesses**. A wrong guess is the
single most expensive failure mode in agentic work: it spends a whole run going
the wrong direction, and the human only discovers it at the end.

This extension closes that gap with the minimum surface:

1. Add **one optional method** to the `UI` interface:
   `ask?(question: string, options?: string[]): Promise<string | null>`.
   Optional so every existing `UI` implementer keeps compiling and running
   unchanged (`defaultUI` in `agent.ts:392-396`, the CLI `ui` in `cli.ts:117-125`,
   the server's reliance on `defaultUI`, and the test `autoUI` in
   `helpers.ts:31-33`).
2. Implement `ask` on the **CLI host** (`src/cli.ts`) as a readline prompt that
   lists the options and resolves with the chosen/typed answer — mirroring the
   existing `confirm` impl. The **server** (`src/server.ts`) gets no interactive
   `ask` in v1 (it uses `defaultUI`, where `ask` is absent → the non-interactive
   fallback); the durable-async server variant is explicitly deferred.
3. A new **`ask` extension** registering an `ask_user_question` tool
   (input `{question, options?: string[]}`) gated behind a trivial **`ui:ask`**
   capability. The tool calls `ctx.ui.ask(...)` when present; when absent — or
   when `ui:ask` is denied (batch / `--yolo`-deny / non-interactive) — it returns
   a clear "cannot ask in non-interactive mode — proceed with a stated
   assumption" result so the model continues sensibly instead of dead-ending.

This is the agent→host mirror of `steer`/`followUp`, living exactly where
`confirm` lives: in the host's `UI` implementation, with **zero agent-loop
change**.

## 3. Scope Boundary (NON-goals — Simplicity First)

- **No agent-loop change.** The `Agent` class, the turn/dispatch machinery, and
  the hook surface are untouched. The only kernel edit is one optional method on
  the `UI` interface (a type addition, not a behavioral change). Elicitation
  lives in the host's `UI` impl exactly as `confirm` does.
- **No durable / async server elicitation.** A real server `ask` needs an
  `action_required` surface plus a resume channel (the turn pauses, the client
  polls/streams the question, answers out-of-band, the turn resumes). That is a
  protocol-level feature an order of magnitude larger than this. v1 server uses
  `defaultUI` → `ask` absent → fallback. The durable variant is **deferred** and
  named here so it is a known gap, not an accident.
- **No slash command.** `/ask` (human types a question *to* the agent) is the
  inverse of this extension's purpose and is already covered by just talking to
  the agent. No command is added.
- **No rate-limiting / over-ask throttle in v1.** Over-asking is a real
  behavioral concern (§8), but the `ui:ask` capability gate plus a host-side
  prompt already bound it. A per-run ask budget is a speculative feature; not
  built.
- **No structured / typed answer schema.** The tool returns the chosen option
  string (or the free-typed string). No JSON, no validation of the answer
  against a schema — that overlaps `output-contract`'s job and is not needed to
  resolve ambiguity.
- **No multi-question / form batching.** One question, optional flat list of
  string options. No nested questions, no follow-on conditional fields.
- **No persistence of answers.** Each call is independent; nothing is stored
  across turns or sessions. (The transcript already records the Q and A as the
  tool call + result.)
- **No change to `confirm` or `notify`.** Capability prompts keep using
  `confirm` (`capabilities.ts:116`). `ask` is purely additive.

## 4. Key Design Decisions

### D1 — Add `ask` to the `UI` interface as OPTIONAL vs REQUIRED

**Problem.** The model needs a host-implemented elicitation primitive, so it must
live on the `UI` interface alongside `confirm`/`notify`. But four
implementations already satisfy `UI`: `defaultUI` (`agent.ts:392-396`), the CLI
`ui` (`cli.ts:117-125`), the server (which passes no `ui` and so inherits
`defaultUI` via `agent.ts:94`), and the test `autoUI` (`helpers.ts:31-33`). The
kernel's stated discipline is that the `UI`/types surface "changes rarely and
never breaks" (`types.ts:4-7`).

**Options.**
- (a) **Required** method: `ask(question, options?): Promise<string | null>` on
  every `UI`.
- (b) **Optional** method: `ask?(...)`, with every caller handling its absence
  gracefully.

**Choice: (b) optional.** A pure type addition of an optional member; existing
implementers keep compiling and behaving identically. The `ask` extension's tool
narrows `ctx.ui.ask` before calling and falls back when it is `undefined`.

**Why (a) rejected.** A required method is a breaking change to a deliberately
stable kernel interface: it would force an immediate edit to *all four*
implementers (and any out-of-tree `UI`), and a headless embedder that only wants
`confirm`/`notify` would be compelled to stub `ask`. Optional + graceful-absence
gives the same capability with none of the breakage — and the absence itself is
load-bearing: "no `ask` available" is exactly the signal the fallback keys off
(D5). This is a *behavioral* decision (it determines what happens to every
existing `UI`), not a cosmetic one.

### D2 — Gate the tool behind a `ui:ask` capability vs always-available

**Problem.** In a non-interactive run (CI batch via piped stdin, `--eval`, the
server) there is no human at a terminal. If the tool blindly called a blocking
`ask`, it could hang forever waiting on stdin. We need a clean *auto-decline*
that does not hang and does not require the tool to sniff "am I interactive?".

**Options.**
- (a) **Capability-gated**: tool declares `capabilities: ["ui:ask"]`; a run that
  denies it gets the kernel's standard capability rejection.
- (b) **Always-available**, tool inspects the environment (TTY checks, env vars)
  to decide whether to ask.

**Choice: (a) capability-gated on `ui:ask`, with a CONDITIONAL grant.** The
capability layer already *is* the clean auto-decline path. In `executeGuarded`,
after `beforeToolCall`, the kernel calls `this.capabilities.require(cap, ...)`
for each declared capability (`agent.ts:343-345`); a denied capability throws
`CapabilityError` (`capabilities.ts:85-120`), which `runOne` catches and turns
into `{ content: errorText(err), isError: true }` (`agent.ts:307-314`).

The grant, however, is **not unconditional** — and that is load-bearing. The
decision order in `CapabilityManager.require` is deny-patterns first
(`capabilities.ts:86`), then **grant-patterns return ALLOW**
(`capabilities.ts:90`), and only *then* the fallback (`capabilities.ts:102-109`).
`matchPattern("ui:ask","ui:ask")` is an exact match (`capabilities.ts:146`). So a
grant of `ui:ask` short-circuits `require` to ALLOW *before* the `fallback:
"deny"` branch is ever reached: an unconditional grant would make `fallback:
"deny"` un-deniable. The only thing that beats a grant is an explicit `deny`
pattern (checked first), and `makeHarness` exposes only `fallback`, no `deny`
passthrough (`helpers.ts:42-47`) — so a grant cannot be overridden under the
prescribed harness either. Therefore the extension grants `ui:ask` **only when
the host UI can actually answer**: at activation it checks `typeof
api.agent.ui.ask === "function"` (the agent's UI is reachable as
`api.agent.ui`, `agent.ts:68`) and grants only then. Under an interactive run
(CLI `ui` implements `ask`) the grant fires, so the human is not double-prompted
(capability prompt *then* the question). Under a non-interactive run (headless /
server / batch, where `ask` is absent) the grant does **not** fire, so `ui:ask`
falls through to the policy: a `fallback: "deny"` run hits the deny branch
(`capabilities.ts:106`), the tool never executes, and the model gets a legible
"capability denied" result — no hang, no stdin block. (And because a
non-interactive UI also lacks `ask`, this is the *only* reachable
non-interactive outcome: the capability denial runs *before* `execute`, so it
precedes the absence-fallback of D5; the fallback is the path taken when the
policy *allows* `ui:ask` but the UI still cannot ask.)

**Why (b) rejected.** Environment-sniffing duplicates policy the capability layer
already owns, is the anti-pattern the project avoids (capabilities are "the
security vocabulary"), and is brittle: TTY detection is wrong under pipes,
sub-processes, and the server. Gating also composes — a locked-down run denies
`ui:ask` the same way it denies `shell:exec`, with one uniform mechanism and the
existing audit log (`capabilities.ts:130-136`). This is behavioral: it decides
what a batch run does when the model tries to ask. (Note: the conditional grant
above is *not* this anti-pattern — it is a one-time, activation-time check of
whether the host `UI` even implements `ask`, used only to decide whether to
pre-grant; it does not sniff TTY/env at call time, and the *enforcement* of
whether asking is allowed still flows entirely through the capability layer.)

### D3 — CLI `ask` impl: readline listing options, accept index or free text

**Problem.** The CLI host must render a question + options to a terminal human
and collect one answer, reusing the host's single readline interface (`rl`)
without a second input channel.

**Options.**
- (a) **Reuse the existing `rl`** (`cli.ts:115,157`) with one `rl.question`
  call, printing the numbered options first and accepting either a 1-based index
  or free-typed text; `if (!rl)` (non-interactive) returns `null`, exactly like
  `confirm`'s `if (!rl) return args.yolo` branch (`cli.ts:120`).
- (b) Spin up a **separate prompt library / second readline** for rich
  selection.

**Choice: (a).** Symmetry with the proven `confirm` impl (`cli.ts:117-125`):
same `rl`, same late-binding `if (!rl)` guard, same `notify`-to-stderr discipline
so stdout stays clean for `--json` mode. An index keeps selection unambiguous
when options are long; free text lets the human answer "none of these, do Z".

**Why (b) rejected.** Violates the zero-runtime-deps rule (only `jiti` allowed) —
no prompt library may be added. A second readline on the same stdin fights the
existing one for input and the SIGINT handler (`cli.ts:166-187`). Reusing `rl` is
both simpler and the only dependency-clean option. The index-vs-free-text parsing
is a behavioral choice (it determines how an answer is resolved), so it is
surfaced, not assumed.

### D4 — Server v1: minimal (non-interactive fallback) vs durable async

**Problem.** The HTTP server (`src/server.ts`) runs one turn per request and
streams JSONL back; it has no interactive channel to a human mid-turn. How should
`ask` behave there?

**Options.**
- (a) **Minimal v1**: the server passes no custom `ui`, so it inherits
  `defaultUI` (`agent.ts:94`), where `ask` is absent → the tool's fallback fires
  (proceed-with-assumption). No server code change.
- (b) **Durable `action_required` + resume**: the turn pauses, the server emits
  an `action_required` event carrying the question/options, the client answers
  via a new route, the turn resumes.

**Choice: (a) minimal v1.** It is *zero* server code (the absence of `ask` on
`defaultUI` already routes to the fallback), it never hangs the single-flight
request loop (`server.ts:159-168`), and it degrades exactly like any other
non-interactive run. (b) is documented as the deferred durable variant (§3).

**Why (b) rejected for v1.** It is a protocol feature: a new pause/resume state
machine, a new route, session-state for the pending question, and a client
contract — disproportionate to "let the model ask a question" and orthogonal to
the core value (which the CLI already delivers). Shipping (a) first means the
feature works end-to-end on the CLI today without blocking on a server protocol
design. This is a behavioral decision about what the server does on an
agent-initiated question.

**Update (B1, delivered).** Option (b) — the durable `action_required` + resume
channel — has since been built; see §9. The minimal v1 fallback (a) remains the
behavior when no client is streaming or an ask goes unanswered, so it is now the
*degraded* path under (b) rather than the only path. No agent-loop change was
needed: the `UI.ask` seam (D6) was the only hook required.

### D5 — Absence-fallback returns "proceed with a stated assumption" vs an error

**Problem.** When `ctx.ui.ask` is `undefined` (headless / server / a `UI`
predating this change), what should the tool return to the model?

**Options.**
- (a) **A non-error, instructive result**: a normal `ToolResult` (not
  `isError`) telling the model it cannot ask here and should proceed by *stating
  an explicit assumption and continuing*.
- (b) **An `isError` result** ("ask unavailable").

**Choice: (a) instructive non-error.** The whole point is to keep the run making
*forward* progress under ambiguity. A non-error result that says "no human is
available — pick the most reasonable interpretation, state it, and proceed"
turns the dead-end into a graceful degrade: the model continues with a *declared*
assumption (visible in the transcript) rather than silently guessing or
spinning. The text is a fixed string constant (a non-behavioral format choice,
self-justified: it is the model-legible contract for "no human here").

**Why (b) rejected.** An `isError` result invites the `recovery` extension and
the model's own retry reflex to treat it as a *failure to fix* — the model may
re-issue `ask_user_question`, burning turns (`recovery.ts` exists precisely
because models re-issue failed calls). Worse, in batch this could loop. A clear
non-error "proceed" instruction is the difference between graceful degradation
and a stuck run. (This mirrors `recovery`'s philosophy of turning a stuck state
into a forward nudge — here we never enter the stuck state at all.)

### D6 — Where the elicitation lives: host `UI` impl vs an agent-loop hook

**Problem.** Something must block the tool's `execute` on a human answer. Where
does that blocking live?

**Options.**
- (a) **In the host's `UI` implementation**, reached via `ctx.ui` — the tool
  `await`s `ctx.ui.ask(...)` and the host decides how to source the answer
  (readline, fallback, etc.).
- (b) **In the agent loop**, e.g. a new kernel hook/event the loop awaits.

**Choice: (a) host `UI` impl.** `confirm` already establishes this exact pattern:
a tool/capability check `await`s `ctx.ui.confirm(...)` (`capabilities.ts:116`)
and the *host* supplies the human channel; the kernel stays UI-agnostic. `ask` is
the same shape — the loop neither knows nor cares how the answer arrives.

**Why (b) rejected.** It would put UI/human-interaction policy into the agent
loop, which the loop's contract explicitly forbids: "The loop holds no opinions
about tools, memory, prompts, or UI" (`agent.ts:8-12`). A loop-level hook for one
extension's blocking prompt is exactly the kind of core opinion EAgent pushes out
to extensions/host. Keeping it in `UI` means **no agent-loop change** (the §3
non-goal) and reuses the already-wired `ctx.ui` (`agent.ts:361`).

## 5. Dependencies and Assumptions

- **`ctx.ui` is wired into every tool call.** Confirmed: the loop builds the
  `ToolContext` with `ui: this.ui` (`agent.ts:355-363`); `this.ui` defaults to
  `defaultUI` when no `ui` is passed (`agent.ts:94`).
- **The capability dispatch path is as documented.** Each declared capability is
  enforced via `this.capabilities.require(cap, tool.spec.name)`
  (`agent.ts:343-345`) *before* `execute`; a `CapabilityError` becomes an
  `isError` tool result (`agent.ts:307-314`). `makeHarness({ fallback: "deny" })`
  (`helpers.ts:43-47`) yields a run where `ui:ask` is denied **provided the
  conditional grant did not fire** — i.e. with a UI that lacks `ask` (the harness
  default `autoUI()`, `helpers.ts:31-33`). The harness exposes only `fallback`,
  no `deny` passthrough, so a fired grant cannot be overridden under it; the
  conditional grant (D2) is what keeps the deny path reachable.
- **Optional-method narrowing under strict TS.** With
  `noUncheckedIndexedAccess`/`strict`, the tool checks
  `typeof ctx.ui.ask === "function"` before calling; otherwise it takes the
  fallback. No `any`.
- **`defineTool` / `ok` / `fail` are the tool constructors** (`define.ts:26-49`),
  matching every existing extension (`todo.ts:81-114`).
- **Kill-switch idiom.** `if (process.env.EAGENT_ASK === "off") return () => {}`
  at the top of `activate`, matching `recovery.ts:103`.
- **Test loading.** `host.use(id, activate)` activates an inline extension
  (`extension.ts:120-122`); this is the established offline pattern
  (`recovery.test.ts:118-119`). No dependency on `BUILTIN_EXTENSIONS`.
- **Assumption: a model that calls `ask_user_question` will read the answer in
  the next turn.** This is the normal tool-result loop (`agent.ts:212-224`); no
  new mechanism needed. The answer comes back as the tool result text.
- **Assumption: options, when given, are a flat `string[]`.** The JSON Schema
  declares `options` as an array of strings; the validator (`validate.ts`, via
  `agent.ts:326`) coerces/rejects malformed input before `execute`.

## 6. Relationship with Existing Designs

Closest existing files/extensions, and how `ask` relates:

- **`src/kernel/types.ts` (`UI` interface, lines 227-231)** — the surface being
  extended. `ask` is added as an *optional* sibling of `confirm`/`notify`. No
  conflict: purely additive.
- **`src/cli.ts` (`ui` impl, lines 117-125)** — the readline `confirm` whose
  pattern `ask` copies (same `rl`, same `if (!rl)` guard). No conflict; `ask` is
  a new method on the same object.
- **`src/server.ts`** — inherits `defaultUI`; v1 gets the fallback. No conflict.
- **`src/kernel/agent.ts` (`defaultUI` 392-396; `steer`/`followUp`/`handle`
  118-135)** — `defaultUI` deliberately leaves `ask` undefined (headless →
  fallback). `steer`/`followUp` are the **host→agent** injection this is the
  **inverse** of (agent→host). They coexist; different direction, different
  surface (`AgentHandle` vs `UI`).
- **`planmode` and the capability `ask` fallback (`capabilities.ts:111-119`)** —
  **DEDUP / explicitly distinct.** Those are **host→agent confirmations**: the
  model has *already* chosen a tool/action and the human is asked to *ratify* it
  (`confirm` "Allow X?"). `ask_user_question` is the **inverse**: the model
  *stops to ask* the human a question — possibly multiple-choice, possibly
  free-form — *before* choosing a direction. No existing extension provides
  agent-initiated questions; `confirm`/`planmode` cannot express options or
  collect a non-boolean answer.
- **`recovery` (`recovery.ts`)** — shares the "keep the run moving forward"
  philosophy that motivates D5's non-error fallback, and the kill-switch /
  dispose idiom. No functional overlap (recovery rides `afterToolCall`; `ask`
  registers a tool).
- **`todo` (`todo.ts`)** — the structural template for a small, capability-light
  tool-plus-(no-)command extension with session-clean teardown.

**First-design note:** this is the **first** agent→host elicitation primitive in
EAgent. Every prior human-interaction path is host-initiated (`steer`,
`followUp`) or a yes/no ratification (`confirm`, capability prompts, `planmode`,
`write-guard`).

## 7. Acceptance Criteria

All automatable, offline, via `makeHarness` + `MockProvider` (`helpers.ts`),
loading the extension with `host.use("ask", ask)`. `npm test` exit 0 and
`npm run typecheck` exit 0 are the top-level gate.

1. **Scripted-`ask` UI returns the chosen answer.** With a `UI` whose
   `ask: async () => "Postgres"` is passed to `makeHarness({ ui })`, and a
   `MockProvider` script that calls
   `ask_user_question({ question: "Which DB?", options: ["Postgres","MySQL"] })`,
   the tool's result content equals (or contains) `"Postgres"`. Assert the
   tool_result block in the transcript matches `/Postgres/`.
2. **`ask`-absent UI → proceed-with-assumption fallback (non-error).** With the
   default test `autoUI()` (`helpers.ts:31-33`, no `ask`), the same scripted call
   returns a result whose content matches `/proceed.*assumption/i` (the fixed
   fallback string) and whose `isError` is falsy. Assert
   `block.isError !== true`.
3. **`ui:ask`-denied run auto-declines (no hang, error result).** With
   `makeHarness({ fallback: "deny" })` and a **non-interactive UI** (no `ask`
   method — e.g. the default `autoUI()`, so the conditional grant of D2 does
   **not** fire and the capability falls through to the `deny` fallback), the
   scripted call produces an `isError: true` tool_result whose content matches
   `/capability "ui:ask"/`. Assert the test completes (no timeout) and (since the
   capability check runs *before* `execute`) the tool body never runs. Note: an
   `ask`-capable UI would receive the conditional grant and ALLOW, so the deny
   path is reachable *only* with the non-interactive UI — which is exactly the
   real batch/headless case this protects.
4. **Interactive run does not double-prompt.** With an **`ask`-capable UI**
   (so the conditional grant of D2 fires at activation) and a counting `ui.confirm`
   spy, dispatching `ask_user_question` invokes `confirm` **zero** times (the
   capability is pre-granted, so `require` short-circuits to ALLOW at
   `capabilities.ts:90` and never reaches the `ask`-fallback that would call
   `confirm`) and `ask` **once**. The `fallback` value is irrelevant here — the
   fired grant makes it moot — so the harness default is fine. (Contrast
   Criterion 3, where the UI has no `ask`, the grant does not fire, and
   `fallback: "deny"` therefore bites.)
5. **Kill switch.** With `EAGENT_ASK=off`, `host.use("ask", ask)` registers **no**
   `ask_user_question` tool: assert `agent.tools.get("ask_user_question")` is
   `undefined` (and a scripted call to it returns the kernel's
   `/Unknown tool: ask_user_question/` result).
6. **Clean teardown — with one acknowledged, irreversible grant.** After
   `host.unload("ask")`, `ask_user_question` is no longer registered
   (`agent.tools.get(...) === undefined`) — `registerTool`'s tracked disposable
   removes it — and disposing never throws. **Known limitation, asserted
   explicitly:** the `ui:ask` *grant* is **not** reversed by unload.
   `grantCapability` returns `void` and is **not** wrapped in the host's
   `track(...)` disposal helper (`extension.ts:233`, contrast the tracked
   `registerTool`/`on`/`hook` at `extension.ts:228-232`); `CapabilityManager.grant`
   just pushes the pattern into `#grant` with no `Disposable`
   (`capabilities.ts:77-79`). So after unload, `ui:ask` remains allowed for the
   session. The test asserts this *as the current contract* (no live tool leaks;
   the grant persists), not as a passing-by-omission claim. The teardown defect
   and its consequence are called out in §8 Rollback below; reversing the grant
   needs an `ExtensionAPI`/kernel change (a disposable-returning `grantCapability`)
   that is out of scope here.
7. **Options echoed to the human channel.** When `ask` *is* present, the
   `options` array is passed through to `ui.ask`'s second argument: assert the
   spy received `["Postgres","MySQL"]` (the host renders them; the tool forwards
   them verbatim).

## 8. Risks and Rollback

- **Risk: blocking on stdin in a non-interactive run.** A naive `ask` could hang
  CI/batch/server forever. **Mitigation (two layers):** (1) the `ui:ask` grant is
  **conditional on the UI being able to ask** (D2), so a non-interactive run
  leaves `ui:ask` ungranted and a `fallback: "deny"` / deny pattern auto-declines
  it — the tool never runs; (2) when the policy instead *allows* `ui:ask` but the
  UI still cannot elicit (CLI `ask` returns `null` when `!rl`, or `ask` is absent
  entirely), the absence-fallback returns the proceed-with-assumption result (D5)
  — neither path blocks. Covered by acceptance criteria 2 and 3.
- **Risk: adding a method to a stable kernel interface.** **Mitigation:** the
  method is **optional** (D1); every existing `UI` impl keeps compiling and
  running unchanged. Acceptance criterion 2 confirms a `UI` without `ask` still
  works (it takes the fallback). `npm run typecheck` is the compile-time proof.
- **Risk: over-asking — the model asks too many questions.** **Mitigation /
  note:** the `ui:ask` gate plus a host-side human prompt already bound the rate;
  a per-run ask budget is deferred (§3) as a speculative feature. This is flagged
  as a behavioral concern to watch, not blocked on.
- **Risk: free-typed CLI answer is garbage / empty.** **Mitigation:** the CLI
  returns whatever the human types (or the resolved option for an index); an
  empty answer resolves to `null` and the tool reports it plainly. No parsing
  beyond index-vs-text; no crash path.
- **Kill switch.** `EAGENT_ASK=off` early-returns a no-op deactivate from
  `activate` (matching `recovery.ts:103`), so the tool is never registered
  (acceptance criterion 5). Per-run, set the env var; per-deny, deny `ui:ask`.
- **Risk: the `ui:ask` grant is irreversible via the current `ExtensionAPI`.**
  `grantCapability` is not tracked for disposal and `CapabilityManager.grant`
  returns no `Disposable` (`extension.ts:233`, `capabilities.ts:77-79`), so once
  the conditional grant (D2) fires, `unload("ask")` removes the tool but **not**
  the grant — `ui:ask` stays allowed for the session. **Impact:** a later
  out-of-tree `ui:ask`-gated tool loaded *after* this extension unloads would be
  silently auto-allowed. **Mitigation/scope:** the conditional grant (D2) already
  bounds the blast radius — the grant only ever fires in an *interactive* run
  (where a human is at the terminal anyway), never in batch/headless. A proper
  fix (a disposable-returning `grantCapability`, tracked like the other
  registrations) is a kernel/`ExtensionAPI` change deferred out of this task and
  named here so the residual is a known gap, not an accident. Acceptance
  criterion 6 asserts the grant persists rather than pretending teardown is
  total.
- **Rollback.** Three independent, reversible pieces: (1) remove the optional
  `ask?` line from `types.ts` (it is additive, so removal is clean once the
  extension is gone); (2) remove `src/extensions/ask.ts` + `test/ask.test.ts`
  and the (deferred) `BUILTIN_EXTENSIONS` entry; (3) remove the CLI `ask`
  method. Each is local; none touches the agent loop. Caveat: the `ui:ask`
  *grant* (when it fired in an interactive session) is not rolled back by
  removing the extension — it lives in the running `CapabilityManager` and clears
  only on a fresh session/process (see the irreversible-grant risk above). With
  the extension absent or `ui:ask` denied, the tool simply does not exist /
  auto-declines — no behavior change to any other extension.

## 9. Durable server-side ask/resume channel (B1 — the deferred deliverable, delivered)

The §3 / §4-D4 non-goal — "No durable / async server elicitation" — is now built.
The CLI delivered agent→host elicitation via a synchronous readline; the HTTP
server (`src/server.ts`) had no human channel mid-turn, so `ask_user_question`
always inherited `defaultUI` (no `ask`) and took the proceed-with-assumption
fallback. B1 makes the tool actually reach a human over HTTP, with **zero**
agent-loop and **zero** kernel change — the `UI.ask` seam (D6) and the optional
`UI.ask` type (D1) were the only hooks needed. All changes are confined to
`src/server.ts` (+ its test).

### B1-D1 — Server `UI.ask` delegates to a per-turn elicitation sink

`createHttpServer` constructs a single `serverUI: UI` whose `ask(q, opts)`
delegates to a mutable holder, `Elicitation { ask, pending, nextId }`. `streamRun`
installs `elicit.ask` at turn start and clears it in `finally`; when nothing is
installed (no turn streaming, or a stateless call between turns) `serverUI.ask`
resolves `null` → the ask tool's proceed-with-assumption fallback. This is back-
compatible: a turn whose model never calls `ask_user_question` is byte-identical
to before (no `action_required`, no extra state touched).

The sink is passed to `createAgentHost({ ui: serverUI })`. `AgentHostOptions`
**already** threads `ui` to both the `Agent` and the `CapabilityManager`, so
**no `host.ts` change was required** (the task's "if host can't thread `ui`
cleanly" branch did not apply). Because the server runs under `yolo: true` and
`serverUI.ask` is a function at activation, the `ask` extension's conditional
grant of `ui:ask` fires and the tool calls `ui.ask` rather than auto-declining.

**`serverUI.confirm` stays fail-safe (security).** Supplying a `ui` for the
`ask` channel means the server no longer inherits `defaultUI`, whose `confirm`
returns `false` ("headless default denies prompts", `agent.ts:412`). So
`serverUI.confirm` is set to `async () => false` — the SAME fail-safe deny —
**not** auto-approve. This is load-bearing: every ask-mode guard (write-guard,
secret-guard, flow-guard, risk-guard, bash-policy, circuit-breaker,
skills-hardening, planmode) prompts via `ui.confirm` in `beforeToolCall`, and
`yolo` only sets the *capability* fallback to allow — it does **not** bypass a
guard's own `confirm`. An auto-approving server `confirm` would silently turn all
of those guards fail-**open**. Only `ask` is new; `confirm` must not become
fail-open as a side effect. A regression test (a blind `write` on the server stays
blocked, file untouched) pins this.

### B1-D2 — `action_required` event + `POST /answer` resume route

When the installed sink's `ask` fires it (a) takes a stable id from a per-server
monotonic counter (`elicit.nextId++` — **not** `Math.random`/`Date.now`, which are
non-deterministic and disallowed), (b) writes one NDJSON line
`{ type: "action_required", id, question, options }` to the open `/run` stream,
and (c) returns a Promise whose resolver is parked in `elicit.pending` keyed by id.
A new route `POST /answer` with body `{ id, answer }` looks up the resolver,
resolves it with the answer string, and returns `200 { resolved: true, id }`
(or `404 { resolved: false }` for an unknown/already-settled id). The resolved
answer flows back through `ui.ask` → the ask tool (`ok("Answer: " + answer)`) →
the model, and the awaited Promise unblocks so the turn resumes naturally. No new
agent state machine: the pause **is** the awaited `ctx.ui.ask` in the tool body,
exactly as `confirm` already blocks a capability check.

`/answer` carries `{ id, answer }` in the body (chosen over a path param) so the
contract is symmetric with `/run`'s JSON body. It is behind the **same** bearer
auth as `/run` and `DELETE /sessions` (the route runs after the shared auth gate),
but it is deliberately **not** behind the single-flight `busy` lock — it must
succeed *while* a `/run` turn is parked on an ask. (Single-flight guarantees at
most one elicitation context is active, so an id is unambiguous.)

### B1-D3 — Bounded timeout + disconnect fallback (no hang)

Three independent guards ensure a turn never hangs on an unanswered question:
1. **Timeout.** Each pending ask arms a `setTimeout(askTimeoutMs)` (a `ServeOptions`
   field, default 120 s, test-overridable to milliseconds) that settles the
   resolver with `null` → the proceed-with-assumption fallback. The timer is
   `unref()`'d so it never keeps the event loop alive, and cleared on answer.
2. **Disconnect.** `res.on("close")` (the existing disconnect→`agent.stop()` path)
   also drains every outstanding resolver for the turn to `null`, so the agent
   loop unwinds instead of blocking on a dead socket's ask.
3. **Turn teardown.** `streamRun`'s `finally` drains any leftover resolvers and
   clears `elicit.ask`, so no resolver leaks past the turn and a later `/answer`
   for a stale id is a clean 404.

All settles are idempotent (guarded on `pending.has(id)`), so timeout / answer /
disconnect racing each other resolve the ask exactly once.

### B1 residual (still deferred, named so it is a known gap)

- **One pending ask at a time per turn.** Single-flight + the per-turn sink mean a
  turn can have multiple *sequential* asks (each gets a fresh id) but not multiple
  *concurrent* ones surfaced in parallel; concurrent multi-question forms remain
  the §3 "no multi-question / form batching" non-goal.
- **In-memory, single-process durability.** `elicit.pending` lives in the server
  process; a restart drops an in-flight question. A queue/store-backed registry
  for cross-process durability is out of scope (front a pool + sticky routing if
  needed — the same caveat the single-flight lock already carries).
