# Design + Impl (Light Mode) — Evals as a CI gate

**Slug:** `2026-06-29-evals-ci` · **Wave:** 7 (subsystem 4 of 4) · **Mode:** Light
**Source:** [`docs/ROADMAP.md`](../ROADMAP.md) · **Strategy:** [`2026-06-28-eagent-redesign-blueprint.md`](2026-06-28-eagent-redesign-blueprint.md) §3 P3.3 (evals-as-CI half)

> Light Mode: one combined doc + a single fresh-reviewer pass (+ confirming), then L3. Justified — the
> eval **runner already exists and is tested**; the gap is a thin non-REPL entrypoint + fixtures + one CI
> line. No new logic, no kernel change, no extension.

## 1. Background and the gap (code as truth)

The audit established P3.3's second half: the eval **runner is done but not CI-gated**.

- `evals.ts` ships a full offline runner: the `/eval <dir>` command (`evals.ts:346-419`) reads each
  `*.eval.json`, parses it via `parseEvalScenario` (exported, `:201`), scripts the agent's MockProvider
  with `scenario.mockScript`, `agent.clear()` + `agent.run(scenario.input)`, applies `checkExpect`
  (exported, `:130`), and prints a stable `eval: <passed>/<total> passed` scorecard + `  FAIL <file>: …`
  lines. `Trajectory`/`ExpectSpec`/`EvalScenario` are typed and exported.
- **But:** `.github/workflows/ci.yml` runs only `typecheck`/`test`/`build` (no `npm run eval`); there is
  **no `eval` npm script**; **no non-REPL entrypoint** that exits non-zero; and **zero `*.eval.json`
  fixtures** are committed. So the runner can only be invoked by hand in the REPL — it is not a gate.

This wave closes that: a thin headless **entrypoint** (`npm run eval`) that drives the existing, tested
`/eval` command and **exits non-zero on any failure**, a small committed **fixtures** dir, and one **CI
step**. No new eval logic, no kernel change, no extension.

## 2. Deliverables

- [ ] **D1** A headless entrypoint `src/eval-runner.ts`: build the host via
  `createAgentHost({ provider: "mock", storeRoot: mkdtempSync(...) })` — **pin the mock provider** (else an
  exported `*_API_KEY` selects a live provider with no `.script`, failing every scenario — review #5) and an
  **ephemeral storeRoot** (else it reads/writes the real `~/.eagent/state`, polluting state + risking
  non-determinism from persisted flags — review #6). Then call `runEvalDir` (D2) **directly** (NOT via a
  constructed `CommandContext`/`commands.get("eval")` — that would force stdout-parsing, KDD-2), print the
  scorecard, `await host.dispose()`, and `process.exit(failures.length ? 1 : 0)`.
- [ ] **D2** Structured result from the runner (avoids fragile stdout-parsing — KDD-2): extract the
  **readdir + scenario loop** (`evals.ts:359-414` — the loop is `:380-414` but the `readdirSync(dir).filter
  (…).sort()` is at `:359-367`, so `runEvalDir(dir, …)` must own the readdir to compute `total`/iterate —
  review #2) into an **exported** `runEvalDir(dir, agent, readTraj):
  Promise<{ passed: number; total: number; failures: string[] }>`. The `/eval` command **keeps its own
  guard outputs** (`usage`/`cannot read`/`no scenarios`/`disabled` — `:351/356/365/369`, pinned
  byte-identical by the existing T15 + kill-switch tests) and calls `runEvalDir` for the happy path, then
  prints exactly as today (behavior-identical — AC-5). `readTraj: () => Trajectory | undefined` is the
  trajectory accessor; **`runEvalDir` must treat `undefined` as a failed scenario** (the entrypoint's
  accessor is `Trajectory | undefined`, unlike the command's always-defined closure — review #3). The
  command passes `() => traj`; the entrypoint passes `() => getTrajectory({ store: host.storeFor("evals") })`
  (D3). The entrypoint sets the exit code from `failures.length`.
- [ ] **D3** Trajectory access for the entrypoint. Two coupled changes:
  (i) **Widen `getTrajectory`'s signature** to `getTrajectory(api: Pick<ExtensionAPI, "store">)` (it only
  touches `api.store`, `evals.ts:108-110`) — backward-compatible (every full `ExtensionAPI` still
  satisfies it) and removes the need for any cast (review #1: the `as Pick<…>` cast is the wrong direction
  and fails strict TS). (ii) Add a minimal public `ExtensionHost.storeFor(id: string): Store { return
  this.#store.open(id); }` — the namespace any extension already gets (`extension.ts:224`); `FileBackend`
  caches one store per namespace (`store.ts:53`), so `host.storeFor("evals")` returns the **same live
  instance** the evals extension mutates → the in-process trajectory read works. The entrypoint then calls
  `getTrajectory({ store: host.storeFor("evals") })` — **no cast**. This is **one ~2-line kernel touch**;
  `kernel-surface.test.ts` pins only top-level *export names* (not class method shapes — review #7), so
  adding a method to the already-exported `ExtensionHost` needs **no surface-test change** — only the line
  ceiling applies (kernel goes 2182 → ~2186, still under 2,200; review #8). The no-kernel alternative is
  weighed in KDD-3.
- [ ] **D4** An `npm run eval` script in `package.json`: `node --import tsx src/eval-runner.ts evals`
  (default dir `evals/`, overridable by `argv[2]`).
- [ ] **D5** Committed fixtures: an `evals/` dir with ≥2 `*.eval.json` scenarios exercising the runner
  (a tool-sequence assertion + a finish-reason/no-tool-error assertion), using `MockProvider` scripts so
  they are deterministic and offline.
- [ ] **D6** A CI step in `.github/workflows/ci.yml`: `- run: npm run eval` (after `npm test`).

## 3. Scope Boundary (NOT in scope)

- **No** new eval logic — reuse `parseEvalScenario`/`checkExpect`/the `/eval` loop verbatim (extracted, not
  rewritten). The only new code is the entrypoint + fixtures + the CI line + the `storeFor` accessor.
- **No** new extension, **no** new capability.
- **No** statistical pass@k / CI flake-retry / eval-awareness machinery (the `evals` design already
  deferred those — `DEFERRED-FOLLOWUPS` #5); this is the *gate*, not a framework.
- **No** live-model evals in CI — offline `MockProvider`-scripted scenarios only (deterministic, no keys).
- **No** change to `/eval`'s output or behavior — D2's extraction is behavior-identical.

## 4. Key Design Decisions

### KDD-1 — A thin entrypoint reusing the tested `/eval` runner, not a new runner
*Problem:* CI needs a non-REPL eval gate. *Options:* (a) write a fresh CI eval runner; (b) reuse the
existing, tested `/eval` loop. *Choice:* **(b)** — the runner is done and tested; duplicating it would
risk drift between the REPL and CI behavior. The entrypoint is glue. *Rejected:* (a) duplicates tested logic.

### KDD-2 — Structured `runEvalDir` return, not stdout-parsing
*Problem:* how does the entrypoint know pass/fail? *Options:* (a) run the `/eval` command and parse its
printed `eval: X/Y passed` line; (b) extract the loop into an exported `runEvalDir` returning
`{passed,total,failures}` that both the command and the entrypoint call. *Choice:* **(b)** — parsing your
own stdout is brittle (a format tweak silently breaks the gate); a structured return is robust and the
command's printed output stays byte-identical (existing evals tests unchanged). *Rejected:* (a) couples the
gate to a display string.

### KDD-3 — A 2-line `storeFor` accessor vs no-kernel-change alternatives
*Problem:* the entrypoint needs the evals trajectory, which lives in the evals extension's namespaced
store; the host doesn't expose per-extension stores. *Options:* (a) parse stdout (rejected, KDD-2);
(b) rebuild a slim agent+evals harness in the entrypoint (duplicates host wiring); (c) add a tiny public
`ExtensionHost.storeFor(id)` over the existing private `#store.open(id)`; (d, review #9) re-activate the
evals extension on the live host to capture its `ExtensionAPI` (`host.use("evals", e => …)` per
`test/evals.test.ts:47-54`) and read via the full handle — **zero kernel change**. *Choice:* **(c)** — (d)
avoids the kernel touch but tears down and **rebuilds a live builtin purely as a read side-channel**
(`activate()`'s "later wins" teardown *replaces* the instance — `extension.ts:212` — so it would not
double-fold, but it couples the entrypoint to evals' activation internals and `host.use` returns `void`,
forcing a closure-capture trick); (b) duplicates the BUILTIN_EXTENSIONS wiring (and the fixtures need the
full tool set). (c) is a **~2-line read-only accessor** exposing a namespace the kernel already hands every
extension — broadly useful (any host-level consumer reading an extension's published state), and per review
#7/#8 it needs **no `kernel-surface` export-pin change** (only the line ceiling: kernel 2182 → ~2186, ~14
lines under 2,200 — accurately *near* the cap, not "well under"). *Rejected:* (d) double-consumer risk +
unverified seam; (b) duplicated wiring; (a) fragile.

## 5. Acceptance Criteria (measurable, automatable)

- **AC-1** `npm run typecheck` 0 (incl. the widened `getTrajectory` signature — no cast). **AC-2**
  `npm test` 0 (existing 1039 + any new). **AC-3** `npm run eval` exists and, against the committed `evals/`
  fixtures (all designed to pass), prints the scorecard and **exits 0** — deterministically (the entrypoint
  pins `provider:"mock"` + a temp `storeRoot`, so it passes regardless of the developer's env keys / real
  store state).
- **AC-4 (gate actually fails)** A test (or a documented manual check) confirms that a *failing* scenario
  makes `runEvalDir` report it in `failures` and the entrypoint would exit non-zero — i.e. the gate is not
  vacuous. Pin via a `runEvalDir` unit test over a temp dir with one passing + one failing `*.eval.json`
  (assert `passed===1`, `total===2`, `failures.length===1`).
- **AC-5 (behavior-identical `/eval`)** After the D2 extraction, the existing `evals` tests pass
  **unchanged** (the `/eval` command's printed output + behavior are byte-identical).
- **AC-6 (storeFor)** `host.storeFor("evals")` returns the same namespaced `Store` the evals extension
  writes its trajectory to (a test reads back a value). `kernel-surface.test.ts` needs **no export-pin
  change** (it pins top-level export names, not class methods — review #7); it stays green, and the kernel
  line ceiling holds (`< 2,200`; ~2186).
- **AC-7** The CI workflow includes `npm run eval` (asserted by reading `.github/workflows/ci.yml`), and
  the committed fixtures parse via `parseEvalScenario` (no malformed fixture).

## 6. Impl tasks (TDD order)

1. **(test)** A `runEvalDir` test (in `test/evals.test.ts`): a temp dir with one passing + one failing
   `*.eval.json`; assert `{passed:1, total:2, failures:[…one…]}` (AC-4). + a `storeFor` round-trip test
   (in `test/host.test.ts` or `extension.test.ts`) (AC-6).
2. **(test)** Confirm the existing `evals` tests still pass after the extraction is wired (AC-5) — no new
   test needed; they are the net.
3. **(impl)** `evals.ts`: (a) widen `getTrajectory(api: Pick<ExtensionAPI,"store">)` (no behavior change);
   (b) extract the **readdir + loop** (`:359-414`) into `export async function runEvalDir(dir, agent,
   readTraj): Promise<{passed,total,failures}>`, treating `readTraj()===undefined` as a failed scenario;
   the `/eval` command **keeps its guards** (usage/cannot-read/no-scenarios/disabled) and calls
   `const { passed, total, failures } = await runEvalDir(dir, e.agent, () => traj); ctx.print(\`eval:
   ${passed}/${total} passed\`); failures.forEach(f => ctx.print(\`  FAIL ${f}\`));` — byte-identical output.
4. **(impl)** `extension.ts`: add `storeFor(id: string): Store { return this.#store.open(id); }` (public;
   `Store` already imported). No `kernel-surface` export-pin change.
5. **(impl)** `src/eval-runner.ts`: `const { agent, host } = await createAgentHost({ provider: "mock",
   storeRoot: mkdtempSync(join(tmpdir(), "eagent-eval-")), discoverDirs: [] });` (`discoverDirs: []` makes
   the gate **hermetic** — no user/cwd `.eagent/extensions` discovery, so a developer's local extension
   can't perturb the result; review optional-hardening) then `const { passed, total, failures } =
   await runEvalDir(process.argv[2] ?? "evals", agent, () => getTrajectory({ store: host.storeFor("evals")
   }));` (no cast — getTrajectory is widened), print the scorecard, `await host.dispose()`,
   `process.exit(failures.length ? 1 : 0)`. (Note: bypasses the command's `EAGENT_EVALS=off` guard, but the
   evals *consumer* is still gated, so with the kill switch the trajectory is empty → scenarios fail → exit
   1; CI doesn't set it.)
6. **(impl)** `package.json`: `"eval": "node --import tsx src/eval-runner.ts evals"`.
7. **(impl)** `evals/`: 2 deterministic `*.eval.json` fixtures (MockProvider scripts) designed to pass.
8. **(impl)** `.github/workflows/ci.yml`: add `- run: npm run eval` after `- run: npm test`.
9. **(verify)** `node --import tsx --test "test/evals.test.ts" "test/host.test.ts" "test/kernel-surface.test.ts"`;
   `npm run typecheck`; `npm run eval` (exit 0); `npm test`.

- **Accept:** `npm run eval` (exit 0) + `node --import tsx --test "test/evals.test.ts"`; `npm run typecheck`.
- **Exit:** AC-1..AC-7 pass; existing evals tests unchanged; `kernel-surface` green; `npm test` green.

## 7. Engineering Constraints

ESM NodeNext `.js` specifiers; strict TS (`noUncheckedIndexedAccess`); zero deps but jiti; offline
(entrypoint pins `provider:"mock"` — CI has no keys anyway). The **one kernel touch** is the ~2-line
`ExtensionHost.storeFor` accessor (`extension.ts`): no `kernel-surface` export-pin change (it pins export
names, not methods), only the line ceiling (kernel 2182 → ~2186, under 2,200). The `getTrajectory`
signature-widening + the `runEvalDir` extraction are in `evals.ts` (an **extension**, not kernel) and are
behavior-identical (existing evals tests are the net). No AI attribution in commits.

## 8. Risks and Rollback

- **R1 — `runEvalDir` extraction changes `/eval` behavior.** *Mitigation:* AC-5 (existing evals tests
  unchanged) + the command prints the same lines. *Rollback:* re-inline the loop.
- **R2 — Vacuous gate (always passes).** *Mitigation:* AC-4 pins that a failing scenario is detected and
  would exit non-zero. *Rollback:* n/a.
- **R3 — CI flake from a nondeterministic fixture.** *Mitigation:* fixtures are `MockProvider`-scripted →
  fully deterministic, offline, no keys. *Rollback:* remove the CI line.
- **R4 — `storeFor` widens the kernel surface.** *Mitigation:* a 2-line read-only accessor over the
  existing `#store.open`; pinned in `kernel-surface.test.ts`; broadly useful. *Rollback:* drop it + fall
  back to KDD-3(b) (slim harness) — but (c) is cleaner.
- **R5 — README/docs stale** (a new `npm run eval` + `evals/` dir). *Mitigation:* reconcile at F.

A thin entrypoint + a behavior-identical extraction + a 2-line accessor + fixtures + one CI line; reverting
the entrypoint/script/CI-line removes the gate, and re-inlining `runEvalDir` + dropping `storeFor` restores
the prior state exactly.
