# Design: a session todo list (`todo` extension)

## 1. Background and Purpose

EAgent has `planmode` (a plan-then-approve gate before acting) and `journal`
(an append-only narrative log), but **no structured task list** the agent
maintains and checks off *during* execution. For a long-horizon agentic run —
exactly the regime the models EAgent targets operate in — a live todo list is a
well-established coherence tool: it externalizes the plan, tracks which step is
in progress, surfaces remaining work, and stops the agent from dropping steps or
re-deriving the plan each turn.

The upstream project [opencode](https://github.com/anomalyco/opencode) ships a
`todowrite` tool (`packages/opencode/src/tool/todo.ts`): the model writes a list
of `{content, status, priority}` items, held in session-scoped state, and the
tool echoes the current list back. Its tool description spells out the discipline
("3+ distinct steps", "exactly one `in_progress` at a time", "mark `completed`
only after the work is actually done"). This is the same pattern Claude Code's
own todo tooling uses to keep long tasks on track.

This task digests that into EAgent as a small `todo` extension with one tool,
`todowrite(todos)`, that **replaces** the session's todo list and returns a
rendered view so the model sees current state, plus a `/todos` slash command so
the human can see it. State is session-scoped and in-memory (cleared on session
reset), needs **no capability** (it is pure bookkeeping — no filesystem, shell,
or network side effect), and is validated (status/priority enums) so a malformed
write fails with a correcting message instead of corrupting the list.

If we do not do this, multi-step work relies entirely on the model re-reading the
transcript each turn to remember what is left — which degrades on long runs and
gives the human no at-a-glance progress view.

## 2. Deliverables

- [x] `src/extensions/todo.ts` — a `todo` extension registering a `todowrite`
      tool (replace the session todo list; validate items; return a rendered

      clearing. No capability declared.
- [x] `test/todo.test.ts` — offline tests: `todowrite` stores and echoes the
      list; invalid status/priority fails with a correcting message; the list
      survives within a session and is rendered by `/todos`; `session_start`
      clears it; the tool needs no capability (runs under `fallback:"deny"`).
- [x] `src/host.ts` — register `todo` in `BUILTIN_EXTENSIONS`.
- [x] `CLAUDE.md` — add a one-line `todo` entry to the extension inventory.

## 3. Scope Boundary (NOT in scope)

- **No disk persistence.** The list lives in session-scoped memory and clears on
  reset; it is not written to a file. (opencode persists per session; EAgent's
  `session` extension already owns transcript persistence, and todo state riding
  the transcript is a separate, larger concern — out of scope.)
- **No change to `planmode` or `journal`.** `todo` is an additional, orthogonal
  surface; nothing about the plan-approve gate or the narrative log changes.
- **No automatic enforcement of agent discipline.** The tool validates *shape*
  (enums, non-empty content) but does **not** reject a list with two
  `in_progress` items — the "exactly one in_progress" rule is *guidance in the
  tool description*, not a hard constraint (matching opencode; over-enforcing
  shape rules the model is meant to self-apply is brittle). It does surface a
  count so the model/human can see it.
- **No second `todoread` tool.** The current list is returned by every
  `todowrite` and shown by `/todos`; a separate read tool is redundant
  (Simplicity First).
- **No priority-based sorting or scheduling.** `priority` is stored and rendered
  but the extension does not reorder or act on it.

## 4. Key Design Decisions

### D1. A new `todo` extension, not an addition to `planmode`

- **Problem:** Where does task-list state live?
- **Options:** (a) extend `planmode`; (b) a new `todo` extension.
- **Choice:** (b).
- **Rationale:** `planmode` is a *gate* (approve a plan before the agent may
  act); a todo list is *live progress tracking during* action. They are distinct
  concerns with distinct lifecycles, and a host may want one without the other.
  A separate extension keeps each small and independently disposable. Rejected
  (a) to avoid conflating an approval gate with a progress tracker. (No name
  collision either: `planmode` gates only tools whose name is *exactly* in its
  `MUTATING_NAMES` set `["write","edit","bash"]` — an exact `.has(name)` check, so
  `todowrite` is not gated despite containing the substring "write".)

### D2. No capability — pure in-memory bookkeeping

- **Problem:** What authority does `todowrite` need?
- **Choice:** Declare **no** `capabilities`. The tool only mutates an in-process
  list; it touches no filesystem, shell, or network.
- **Rationale:** Capabilities are EAgent's vocabulary for *side effects on the
  outside world* (`fs:*`, `shell:exec`, `net:fetch`). A todo write has none, so
  gating it behind a capability would be miscategorization and would needlessly
  prompt the human. An acceptance criterion proves it runs even under
  `fallback:"deny"`. (`executionMode` is left default; a todo write is cheap and
  has no ordering hazard.)

### D3. Session-scoped in-memory state, cleared on reset

- **Problem:** What is the lifetime of the list?
- **Choice:** A single in-extension array, cleared on `session_start` and
  `session_shutdown` (the idiom `flow-guard` uses for its taint set).
- **Rationale:** A todo list is meaningful only within the run that created it; a
  fresh session starts empty. In-memory + reset-on-session is the minimal correct
  lifetime and matches how other stateful extensions (`flow-guard`, `limits`
  counters) scope per-session state. Disk persistence is out of scope (§3).

### D4. One `todowrite` tool that replaces the list and echoes it

- **Problem:** What is the tool surface?
- **Choice:** `todowrite(todos: TodoItem[])` **replaces** the entire list
  (matching opencode — the model always sends the full updated list, avoiding
  per-item add/remove/patch ops), stores it, and returns the **rendered summary
  in the canonical D6 format** (the `Todos (C/M done):` header plus one line per
  item) so the model sees the authoritative current state in the tool result. A
  `/todos` command renders the same view for the human.
- **Rationale:** Whole-list replacement is the simplest coherent contract (no
  id-based patching, no partial-update races) and is what the upstream tool does.
  Echoing the rendered list back closes the loop so the model's next turn sees
  the canonical state without re-reading the transcript. Rejected an add/update/
  remove API as more surface for no benefit.

### D5. Validate shape (enums + non-empty content); fail with a correcting message

- **Problem:** A malformed write could corrupt the list or mislead.
- **Choice:** Each item must have non-empty `content`, a `status` in
  `{pending, in_progress, completed, cancelled}`, and a `priority` in
  `{high, medium, low}`. On any violation, the tool returns a `fail(...)` naming
  the offending field and the allowed values, and **does not** mutate the stored
  list (the prior list stands).
- **Rationale:** This follows the kernel's normal **error-feedback** convention —
  a tool returns `fail(...)` and the error result is fed back so the model
  corrects the input, rather than silently storing garbage. (This is the ordinary
  tool-error path, distinct from the kernel's `beforeToolCall` argument-rewrite
  seam.) Not mutating on error keeps the list consistent. The enums match
  opencode's documented states/priorities. Shape-only (not the "one in_progress"
  semantic rule, §3) keeps validation strict-where-mechanical and lenient-where-
  judgment.

### D6. Render format is model- and human-readable, with a done count

- **Problem:** How is the list presented?
- **Choice (the single canonical format — D4 and §7 defer to this):** a header
  line `Todos (C/M done):` where `C` = completed count, `M` = total, followed by
  one line per item `- [<glyph>] <content> (<priority>)` with glyph
  ` `/`~`/`x`/`-` for pending/in_progress/completed/cancelled. `/todos` prints
  exactly this; an **empty list prints `(no todos)`** (both from `todowrite` with
  an empty array and from `/todos` before any write).
- **Rationale:** A compact, stable text rendering is both what the model reads
  back and what `/todos` shows the human — one format, no divergence. The done
  count gives at-a-glance progress. Deterministic rendering makes the output
  assertable in tests.

## 5. Dependencies and Assumptions

- **`ExtensionAPI`**: `e.registerTool`, `e.registerCommand`, `e.on("session_start"
  / "session_shutdown")` — all already used by `flow-guard`/`limits`. The tool
  uses `defineTool`/`ok`/`fail` (`src/kernel/define.js`).
- **No capability, no kernel change, no npm dependency.** Pure in-memory state.
- **Tool dispatch**: the dispatcher runs a tool declaring no capabilities without
  any `require` call (`agent.ts:331-332` loops over an empty capability list), so
  `todowrite` executes regardless of capability policy — verified by an
  acceptance criterion under `fallback:"deny"`.
- **Test harness**: `makeHarness` + direct tool execute for the write/validate
  tests, and the agent loop for the no-capability test; `/todos` exercised via
  the command registry. Offline.

## 6. Relationship with Existing Designs

- Independent of the prior tasks; composes with none of them and supersedes
  nothing. It is orthogonal to `planmode` (approval gate) and `journal`
  (narrative log) — see D1.
- Mirrors the per-session-state idiom of `flow-guard` (`src/extensions/
  flow-guard.ts` — reset on `session_start`/`session_shutdown`) and the
  `defineTool`/`ok`/`fail` + slash-command shape of the other extensions.
- Terminology anchor: CLAUDE.md ("everything is an extension"; the seven
  primitives; capabilities are for side effects).

## 7. Acceptance Criteria

Verified by `npm test` (offline) and `npm run typecheck` (exit 0).

1. **Typecheck clean:** `npm run typecheck` exits 0.
2. **Write + echo (canonical D6 format):** `todowrite({todos:[{content:"a",
   status:"pending",priority:"high"},{content:"b",status:"completed",
   priority:"low"}]})` returns a non-error result whose content is the D6
   rendering — header `Todos (1/2 done):` and the two `- [<glyph>] <content>
   (<priority>)` lines (assert the exact D6 strings, not an approximation).
3. **Replace semantics:** a second `todowrite` with a different list returns the
   **new** list only (the first list's items are gone), proving whole-list
   replacement.
4. **Invalid status fails, list unchanged:** `todowrite` with an item
   `status:"bogus"` returns `isError` naming `status` and the allowed values, and
   a subsequent `/todos` still shows the **previous** valid list (no mutation on
   error).
5. **Invalid priority / empty content fail:** an item with `priority:"urgent"` or
   empty `content` returns `isError` naming the field.
6. **`/todos` renders the current list:** after a successful write, `/todos`
   prints the rendered list; with no writes it prints `(no todos)`.
7. **Session reset clears:** after a write, emitting `session_start` clears the
   list — `/todos` then prints `(no todos)`.
8. **No capability required (with a control):** under `makeHarness({fallback:
   "deny"})` (so any *declared* capability would be denied), a scripted
   `todowrite` call through the agent loop executes successfully (not
   capability-denied). **Control:** in the same harness, a tool that *does*
   declare a capability (e.g. a registered `shell:exec` stub) is blocked with a
   capability error — so the `todowrite` success is specifically attributable to
   its declaring no capability, not to the harness allowing everything.
9. **Regression:** `npm test` reports `# fail 0` (≥ 298 prior tests plus the new
   subtests); existing extensions and the host builtin-set test pass.

No latency budget: a todo write is an O(n) array store + render off the hot path;
excluded per the Scope Boundary.

## 8. Risks and Rollback

- **R1 — Unbounded list size.** A model could write a very large list, bloating
  the tool result. *Mitigation:* the `limits` extension's `afterToolCall` byte
  cap already backstops oversized tool output; a todo list is inherently small in
  practice, so no per-tool cap is added (Simplicity). Noted as a possible future
  cap.
- **R2 — Stale list across `/clear`-style resets.** Unlike `flow-guard`'s data
  taint (which rides messages and so clears with the transcript), this list is a
  plain extension-local array cleared only on `session_start`/`session_shutdown`;
  a host that wipes the transcript *without* firing `session_start` would leave
  the list in place. *Accepted risk* (not actively mitigated): the list is purely
  advisory state with no correctness impact if stale, and a stale list is
  immediately corrected by the next `todowrite`. Tying it to transcript-clear
  events is a possible future refinement, out of scope here.
- **R3 — Divergence between the model's mental list and the stored list.** The
  model might "forget" to call `todowrite`. *Mitigation:* this is inherent to any
  advisory todo tool and is addressed by the tool *description* (the discipline
  guidance), not by mechanism; out of scope to enforce.
- **Rollback:** remove the `todo` entry from `BUILTIN_EXTENSIONS` and the CLAUDE.md
  line; delete `todo.ts` + its test. The extension is inert when not loaded, holds
  only in-memory per-session state, and changes nothing in the kernel or other
  extensions.
