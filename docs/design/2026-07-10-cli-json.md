# Light-Mode brief — CLI `--json` stdout contract + first CLI test (Batch G1)

Slug: `2026-07-10-cli-json`
Tier: **Light** (two non-load-bearing files: `src/cli.ts` — a front end, not a contract/schema file —
and a new `test/cli.test.ts`). This *fixes* the existing `--json` JSONL contract (it does not add or
break an external contract); the routing rule below is a single resolved decision, no threshold. If a
reviewer judges the `--json` output a public contract requiring Full Mode, escalate.

## What / why

`--json` mode is documented as "emit one JSON object per lifecycle event to stdout"
(`cli.ts:325`). But several human-affordance/​diagnostic writes go to **stdout** un-gated on the mode,
so `echo … | eagent --json` interleaves non-JSON lines that break a consumer's per-line `JSON.parse`:

- `cli.ts:246` — `console.log(\`\n› ${line}\`)` echoes each batch input line (ANSI-bolded).
- `cli.ts:271` — `console.log(\`Unknown command: …\`)` (dispatch).
- `cli.ts:275` — command output via `print: (l) => console.log(l)`.
- `cli.ts:277` — `console.log(\`✗ /${name}: …\`)` (command error).
- `cli.ts:346` — `console.log(\`✗ ${err}\`)` in `runTurn` (a run throw, distinct from the `error`
  lifecycle event the JSON renderer already emits at `cli.ts:339`).

The human logger (`cli.ts:149`) already routes to stderr ("Diagnostics go to stderr so stdout stays
clean"); the batch/dispatch/runTurn paths simply don't follow it. And there is **no** `test/cli.test.ts`
at all — the primary programmatic surface is untested.

## Explicit non-goals

- **No** change to the JSONL event schema (`wireJsonRendering`, `cli.ts:326-340`), to human-mode
  rendering (`wireRendering`), to arg parsing, or to the REPL/banner UX in human mode.
- **No** change to what human mode prints to stdout (echo, command output stay on stdout in human mode).
- **No** new flags. **No** kernel/host change.

## The rule

In `--json` mode, **stdout carries only the JSONL lifecycle events**; every other write (input echo,
command output, dispatch/​run errors) goes to **stderr**. In human mode, behavior is unchanged. Thread
the existing `args.json` boolean into `batch`, `dispatchCommand`, `runTurn`, and `repl`, and select the
sink per line: `const diag = json ? console.error : console.log;` for the echo and command `print`; the
dispatch/run error writes likewise route to stderr when `json` (they may stay on stdout in human mode
to preserve current UX).

## >1-option decision surfaced

**Where non-JSONL output goes in `--json` mode.** Options: (A) route it to **stderr** [chosen];
(B) **suppress** it entirely; (C) wrap it as a synthetic JSON event on stdout. **Choice (A):** stderr
keeps the information available to an operator/CI log without polluting the machine-readable stdout
stream — the same split the code already uses for its logger. **Reject (B):** silently dropping a
command's output or an error is worse for debugging. **Reject (C):** inventing `{type:"echo"}`/
`{type:"diagnostic"}` events expands the JSONL schema (a real contract change) for content that isn't a
lifecycle event.

## Measurable acceptance command

`node --import tsx --test test/cli.test.ts` — a subprocess integration test (RED before fix, GREEN
after):
- Spawn `node --import tsx src/cli.ts -p mock --json` with piped stdin containing a normal turn line
  and a slash command (e.g. `"hi\n/help\n"`), no API key (mock provider runs offline).
- Assert **every non-empty line of stdout is valid JSON** (`JSON.parse` does not throw) — this fails
  before the fix (the `› hi` echo and `/help` output are not JSON) and passes after.
- Assert at least one JSONL event was emitted (e.g. a line with a `type` field), so the test proves
  events still flow, not merely that stdout is empty.
- (Optional) assert the human echo/command output appears on **stderr**.
