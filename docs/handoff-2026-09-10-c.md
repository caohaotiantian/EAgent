## 4 · Decisions taken without the user this wave

Five, each recorded because nobody was asked and each is reversible only at a cost.

1. **§A.55 — the barrier RELEASES rather than FAILS.** `#maybeFireJoin` decides WHEN a barrier
   releases; `#foldJoin` decides what the release MEANS, and it already holds the failure arm
   (`onBranchError === "fail" && skipped > 0` → `E_QUORUM_UNREACHABLE`). Failing from the predicate
   would compute that judgement a second time, compute it differently, and override an operator who
   wrote `onBranchError: "skip"` on purpose. It is also the engine's own convention on the two
   modes whose decision rests on absence: `all` is `quiescent && terminal >= expected` and
   `quorum`'s second disjunct IS the under-count case, and both release. **The alternative not
   taken** — failing in the predicate — is what §D.9 would revisit, and the two `TODAY` assertions
   in `join-all-branches-fail.test.ts` are the failing test whoever settles it flips.
2. **§A.59(1) — READABILITY is re-checked at the executor's door and the CEILING is not.**
   `rule007Fanout` refuses a width over `expansion.maxFanout`; `#assertBound` deliberately does
   not, and the test pins an over-ceiling width as ACCEPTED so the gap is a decision rather than an
   oversight. The ceiling is a policy number the compiler produces by merging graph policy over
   defaults; re-deriving it in the kernel would be a second implementation of a budget, and any
   drift would refuse graphs the compiler accepted — **including runs already in flight**, since
   `#assertBound` runs on every `advance`. An unreadable width is a correctness hole; a width over
   budget is the compiler's business.
3. **§A.58(2) — the gates cap stays PER VALUE.** A per-output budget makes what an operator sees
   depend on how many OTHER gates are parked and in what order channels are visited: the first gate
   in a fan-out prints whole and the last prints nothing, and the same gate shows different content
   as its neighbours resolve. This door's subject is one human deciding on one gate. Accepted with
   it: a worst case bounded by `gates × channels × maxBytes`, every cut of which is named on stderr
   and in the row's own `readsTruncated`. The answer to "too many gates in one document" is
   selecting or paging gates — a different feature, not a budget that silently decides which
   approver gets to read.
4. **§A.58(4) — SPLIT, rather than closed or left whole.** Whether a held write EXISTS on a printed
   channel is decidable from `p.tasks` alone and needs no engine seam; what the value IS needs
   `reduceState` inside `cli.ts`, which is a second copy of the engine's reducer in a second file —
   the exact drift `gatesWithReads` already refuses by calling `observedChannels` and not
   `node.reads`. So the silence closed and the value did not, and the open half is §A.60 rather
   than a caveat inside a struck row.
5. **§A.56 — the `fix:` names the INNERMOST fan-out's barrier, and names no candidate join.** Under
   double nesting "the fan-out X is inside" names two and only one works: a join two fan-outs deep
   collected by the OUTER barrier makes that barrier reachable at two depths and fails closed on
   `GRAPH008_JOIN_DEPTH`, while the inner one compiles. So the adjective decides whether following
   the line converges, and `heldFixEdits` parses it so dropping it breaks the test file rather than
   the next reader's compile. **It refers to the join rather than naming a candidate**, because
   naming candidates is what cost GRAPH021 four review rounds — and it does not claim the author's
   choice is checked downstream, because it is not (§A.64).

## 5 · Facts you would otherwise rediscover

- **A worktree branched from `init` and had to be reset before it committed.** The cli lane's
  worktree started on `086e47d` (the default branch), not on `loom`. Caught at dispatch by reading
  `git worktree list`; the fix is cheap before the first commit and expensive after. **Check every
  lane's base right after dispatch**, not at merge time.
- **The three tests that fail in a fresh worktree are an artifact of the worktree.**
  `guards-lane-surface-guard-decides` and the two `toolchain-gate` suites want `dist/` and
  `node_modules`, which a worktree does not have. `check-surface.mjs` reads `dist/`, so a lane that
  needs to run it must build first: `npx tsc -b packages/core/tsconfig.json` inside the worktree.
  In the main checkout, after `npm run check` builds, all three pass. Do not chase them from a lane.
- **`npm test` leaves `x/journal.db` in the repo root and `git status` does not say so.** It is
  §H.10; the reason it hid is that `.gitignore`'s `*.db` covers the only file in the directory, and
  git does not report a directory whose entire content is ignored. If you see a stray `x/`, that is
  what it is — read it before deleting it, but it is a journal from a flag test.
- **The differential evidence that made a validate change safe is a SHAPE, not a file.** Over
  183 graphs and 906 diagnostics, the (file, code, at) key set and every severity identical to
  baseline is what proves a message change moved no refusal; a mutation differential of the same
  kind — 72 of 159 mutants killed, with the survivors enumerated and argued rather than counted —
  is what proves the assertions bind. The harnesses lived in the lanes' gitignored `.agent/`
  directories and are gone with them. **The durable pins are the test files**:
  `fanout-branch-diagnostic.test.ts`'s 20 assertions, whose `namesIn`, `offeredJoins`,
  `heldFixEdits` and `countedIn` all THROW on a sentence they do not recognise.
- **`readsTruncated` and `readsMayBeStale` are new output vocabulary that landed under `fix:`.**
  The kernel guard cannot see that, and `check-surface.mjs` pins the exported NAME SET only, so
  neither would have flagged it. They are on the gate ROW rather than inside a channel value for a
  reason worth keeping: JSON keys are arbitrary strings, so every marker name a value might use is
  one a node can write, and what a channel value CANNOT do is add a key to the row that carries it.
  That is the general answer to "recognised by shape", and it is `payloadHandle`'s answer too.
- **A restart test that attaches to a run which is already terminal proves nothing.** Zero events
  are appended to a closed journal, so re-folding it cannot distinguish a verdict recomputed from
  rows from one that was never needed. The shape that works is a run PARKED on something a second
  process must decide — here, two open `human_gate`s, resolved by a fresh `Engine` over its own
  `SqliteStateStore` on the same file, with the barrier releasing on the journal alone.
- **THE WAVE'S OWN LESSON: two of three lanes needed a round for a FALSE JUSTIFICATION, not a wrong
  mechanism.** The engine lane's fix was correct and its claim was not — it said the row was closed
  when half of it was open, and the reviewer's finding was an OVER-CLAIM. The cli lane's §A.58(4)
  had been recorded as a closed decision on an argument that was false in both halves ("a SIBLING's
  committed write"; "shows LESS and never more") **and the false argument had been promoted into
  `cli.ts`**. The validate lane's first draft of a comment claimed a safety net that does not exist
  — which is how §A.64 was found. A mechanism you can test; a justification you have to read
  against the code it describes. **Ask what a claim would look like if it were false**, and run
  that.
- **A builder's own green suite is still not evidence, for the second wave running.** Every lane
  shipped green and every lane's reviewer then found something: the over-claim above, a gate
  printing a stale value in silence and then — one round later — a gate printing NOTHING in
  silence, which was the worse half and which the first fix's `view.visible` filter had missed
  precisely because it answered "is this worth warning about?" with "only if I already have
  something to show for it". That is this project's own recurring lens, one field over.
