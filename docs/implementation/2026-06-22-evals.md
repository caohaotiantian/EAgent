#### T3 — IMPL: the trajectory consumer
Create `src/extensions/evals.ts`. Mirror `trace`'s pure-consumer discipline
exactly (`trace.ts:88-173`):

- A `safe()` wrapper so a handler throw is logged, never escapes the bus.
- On `agent_start`: reset to a fresh empty `Trajectory` (keep only the last run,
  bounding memory — `trace.ts:99-108`).
- On `tool_start`: push a tool span `{ name: call.name, ok: undefined }` and the

- On `tool_end`: set the matching span's `ok = result.isError !== true`.
- On `usage`: mirror `p.cumulative` (idempotent), keep `totalTokens` (import as

`turn`-inclusive count is a noisier regression signal). Define
`interface Trajectory { tools: string[]; spans: { name: string; ok?: boolean }[];
finishReason?: StopReason; totalTokens: number }` (or equivalent). No kernel
change, no new event, no capability.

**Acceptance:** `node --import tsx --test test/evals.test.ts` (T2 green);

#### T4 — TEST: `checkExpect` — five predicates, each pass AND fail
**Invariant protected:** *each `/expect` predicate is a pure, deterministic
verdict over the trajectory; a passing spec yields `{pass:true, reasons:[]}` and
violating exactly one predicate flips `pass` to false with exactly that
predicate's reason.* (design D2; §7 AC2, AC3, AC4)

Import the exported pure `checkExpect`. Build a trajectory fixture (either via a
scripted run as in T2, or construct the `Trajectory` literal directly — no I/O).
Table-drive all five, **each in its passing and failing form**:

- `tools` `in_order`: `{tools:["A","B"], order:"in_order"}` passes on `[A,B]`;
  `{tools:["B","A"], order:"in_order"}` fails, `.reasons` names the order
  mismatch (subsequence match for `in_order`).
- `tools` `exact`: deep-equality of the full list passes; a differing list fails.
- `maxSpans`: `>=` the tool count passes; one below fails (counts
  `traj.spans.length === traj.tools.length`, the **tool-span count**, D2).
- `finishReason`: equal `StopReason` passes; a different one fails.
- `noToolErrors`: all spans `ok` passes; a trajectory with a span `ok:false`
  fails (the AC4 case).
- `maxTokens`: `>=` cumulative `totalTokens` passes; one below fails.

For AC4 also drive a **live** run whose tool genuinely returns `isError:true`
(register a stub that returns `fail("boom")`, as `recovery.test.ts:108` produces
a real failed call) and assert that span is `ok:false` and
`checkExpect(traj, {noToolErrors:true}).pass === false`.

**Acceptance:** `node --import tsx --test test/evals.test.ts` — red (no
`checkExpect`).

#### T5 — IMPL: `checkExpect`
Export `checkExpect(traj, spec): { pass: boolean; reasons: string[] }`. Pure,
zero I/O. One human-readable reason per failed predicate; absent spec fields are
not checked. `in_order` = subsequence test over `traj.tools`; `exact` = deep
equality. `maxSpans` compares `traj.spans.length`. Define the `ExpectSpec` type
(`{ tools?: string[]; order?: "in_order" | "exact"; maxSpans?: number;
finishReason?: StopReason; noToolErrors?: boolean; maxTokens?: number }`).

**Acceptance:** T4 green; `npm run typecheck`.

#### T8 — TEST: `parseJudgeReply` — pure, total, pinned grammar + sentinel
**Invariant protected:** *the classifier reply parses by the pinned one-line
grammar `SCORE <n>/10 <PASS|FAIL> <reason>`; an unrecognized or empty reply
returns `undefined` (never a throw, never a fabricated score).* (design D3; §7
AC5)

Table-driven, no I/O:

```
assert.deepEqual(parseJudgeReply("SCORE 8/10 PASS clear and correct"),
  { score: 8, verdict: "pass", reason: "clear and correct" });
assert.deepEqual(parseJudgeReply("score 3/10 fail wrong answer"),
  { score: 3, verdict: "fail", reason: "wrong answer" });        // case-insensitive
assert.equal(parseJudgeReply(""), undefined);                     // empty
assert.equal(parseJudgeReply("hello world"), undefined);          // garbled
```

Cover: reads the **first non-empty line**; clamps `<n>` to `0..10`; `reason` is
the trimmed remainder (possibly empty); missing `SCORE`/`<n>/10`/verdict → sentinel.

#### T9 — IMPL: `parseJudgeReply`
Export `parseJudgeReply(reply: string): { score: number; verdict: "pass" |
"fail"; reason: string } | undefined`. Model it on `parseVerdict`
(`risk-guard.ts:57-67`): same total, exception-free shape. Read the first
non-empty line; require a leading `SCORE` token, then an `<n>/10` fraction
(clamp `0..10`), then a `PASS`/`FAIL` token (case-insensitive); the rest is
`reason`. Anything else → `undefined`. **Never throws, never fabricates.**

**Acceptance:** T8 green; `npm run typecheck`.

#### T10 — TEST: `judge` tool against a scripted classifier (and fail-closed)
**Invariant protected:** *`judge` grades a candidate against a rubric via a
recursion-safe tool-less sub-call and returns `{score, verdict, reason}`; an
unparseable/absent verdict becomes an **error** `ToolResult`, never a silent
pass.* (design D3, §5; §7 AC6, AC7)

This is the determinism-sensitive test. Per design D3/§5, the `judge` sub-call
and the outer loop draw turns from the **same** `MockProvider` queue, so `judge`
must be `sequential` for the queue to be consumed in a fixed order. Script the
queue so the turn that **invokes `judge`** is immediately followed by the
**judge-shaped reply turn** (`{ text: "SCORE 8/10 PASS clear and correct" }`):

```
responder: [
  { toolCalls: [{ name: "judge", arguments: { rubric: "...", candidate: "..." } }] },
  { text: "SCORE 8/10 PASS clear and correct" },  // consumed by the judge sub-call
  { text: "done" },                                // outer loop's final turn
]
```

Run `agent.run("grade it")`. Find the `judge` tool's `ToolResult` (inspect the
tool message, or call `e.agent.tools.get("judge").execute(...)` directly with a
seeded queue — either is offline). Assert its parsed `details`/`content` carry
`{ score: 8, verdict: "pass", reason: "clear and correct" }` (AC6).

Then a second case (AC7): script the reply turn as `{ text: "garbled" }` so
`parseJudgeReply` returns `undefined`; assert the `judge` `ToolResult` has
`isError: true` (the wrapper maps the sentinel to a `fail(...)`). Also note the
no-provider path fails closed (returns an error result, never throws) — design §5.

#### T11 — IMPL: `judge` tool
`e.registerTool(defineTool({ name: "judge", executionMode: "sequential", ...
}))` — **`sequential` is load-bearing** (design D3/§5: forces the in-order
`for…of…await` dispatch path so the shared `MockProvider` queue is read
deterministically; `agent.ts:285-290`). Inside `execute`: build a tool-less
sub-call exactly like `risk-guard.classify` (`risk-guard.ts:95-121`) —
`e.agent.providers.get()`, then `provider.stream({ systemPrompt: <rubric
prompt>, messages: [candidate], tools: [], model: e.agent.model, signal })`;
collect the `done` message text; `parseJudgeReply` it. On a parsed verdict return
`ok(<text>, { score, verdict, reason })`; on `undefined` or no provider return
`fail(...)` (design D3: the *tool wrapper*, not the parser, maps the sentinel to
an error result). Default cheap effort (`thinking` omitted/`"off"`). **No new
capability** (provider sub-call is already exposed, design §5). Never throws into
the loop (catch → `fail`).

**Acceptance:** T10 green; `npm run typecheck`.

## 3. Engineering Constraints Index (house rules + commit conventions)

**House rules (CLAUDE.md + design §5):**

- **ESM + NodeNext.** Use `.js` import specifiers even for `.ts` files
  (`import … from "../kernel/define.js"`). Required by `module: NodeNext` +
  `verbatimModuleSyntax`.
- **Strict TS.** `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`,
  `noFallthroughCasesInSwitch` all on. **No `any`** — model the types
  (`ExpectSpec`, `Trajectory`, the judge reply, the scenario).
- **Zero runtime deps except `jiti`.** Pure Node only — `readFileSync` /
  `readdirSync` for the runner, global `fetch`/`provider.stream` for the judge.
  No SDK, no new npm dependency.
- **Capability-gate side effects.** The consumer, `/expect`, `/eval`, and
  `judge` have **no privileged side effect** (in-memory reads, a provider
  sub-call the kernel already exposes, reading a caller-named dir), so **no
  `grantCapability`** is called (design §5). Do not invent a capability.
- **Offline `node:test` via `makeHarness`.** Every test runs with no network and
  no `ANTHROPIC_API_KEY`, against the scriptable `MockProvider`. Load the
  extension with `host.use("evals", evals)` — never depend on `BUILTIN_EXTENSIONS`.
- **Kill switch.** `EAGENT_EVALS=off` makes the consumer + commands + tool
  no-ops (design §2).
- **Dispose loop that never throws.** Return one teardown function that
  `dispose()`s every registration inside `try/catch` (`trace.ts:252-260`,
  `risk-guard.ts:170-178`).
- **Pure-consumer discipline.** Wrap every bus handler in `safe()`; out-of-order
  / missing events degrade the trajectory, never the run (`trace.ts:88-96`,
  design D1, §8).
- **No kernel change, no new event/filter/capability vocabulary** (design §3).

**Commit conventions:**

- Prefix: `feat(phase1)` for production tasks; `fix(phase1-roundR)` for
  review-round fixes.
- Trailers: include `npm test` and `npm run typecheck` results.
- **No mention of AI/model/tooling** in commit messages.
- Branch off the default branch before committing; commit/push **only when the
  user asks**.

## 4. Data / Fixture Dependencies

- **`test/helpers.ts` — reuse, do not reinvent.** `makeHarness(opts)` gives
  `{ agent, host, commands, provider }` with a `MockProvider` registered as
  default. `host.use(id, activate)` loads the extension; `autoUI(answer)` /
  `silentLogger` / `lastText` are available. (`test/helpers.ts:16-55`.)
- **`MockProvider` scripting.** `responder: MockTurn[]` scripts the queue;
  `provider.script(turns)` resets and re-scripts between scenarios
  (`mock.ts:53`). One `MockTurn` per `stream` call — **central to the `judge`
  determinism** (design D3/§5): the judge sub-call dequeues the turn **after**
  the one that invoked it, which is why `judge` is `sequential`.
- **Stub tools** via `defineTool` / `ok` / `fail` (`src/kernel/define.js`),
  registered inline as `flow-guard.test.ts:16-33` does. For the AC4 error case,
  a tool returning `fail("boom")` produces a genuine `isError:true` span
  (`recovery.test.ts:108`).
- **`*.eval.json` fixtures** are written into a `mkdtempSync` temp dir inside the
  test (inline, per design §7 AC8 "tiny inline fixture") and removed in
  `finally` — no committed fixture files needed, no network.
- **Security attack shapes** are reused verbatim from each guard's existing
  suite (T19–T23 above); do not author new attack vectors.

## 5. Regression Protection (which prior tests must stay green)

The change is **purely additive** (no kernel edit, no built-in registration), so
the entire existing suite must stay green — `npm test` exit 0 is the bar. In
particular, watch these as the highest-signal regressions:

- **`test/trace.test.ts`** — `evals` is a *second* consumer of the same bus;
  loading both must not perturb trace's spans/metrics. `/expect`/`/eval` must not
  shadow `/trace`/`/usage` (disjoint names, design §6).
- **`test/risk-guard.test.ts`** — `judge` reuses the tool-less sub-call pattern;
  confirm it does not alter risk-guard's classifier behavior (separate tool,
  separate command).
- **`test/recovery.test.ts`** — the canonical kill-switch / dispose / `host.use`
  shape T16/T18 mirror; if it breaks, your env save/restore or dispose loop is
  wrong.
- **`test/content-guard.test.ts`, `test/secret-guard.test.ts`,
  `test/flow-guard.test.ts`, `test/bash-policy.test.ts`,
  `test/write-guard.test.ts`** — the guards your `test/security/` set exercises;
  the regression files must **assert the same defining action** those suites
  already prove, never weaken or contradict them.
- **`test/agent.test.ts`, `test/extension.test.ts`, `test/host.test.ts`** — the
  loop/dispatch/host invariants the consumer, the `sequential` judge, and the
  dispose loop ride on; any breakage here means an unintended kernel/host coupling.

If any prior test goes red, you have crossed the additive boundary — back out and
re-derive from the design.
