## 6 · The transferable lessons, each with the lane it came from

- **A round-3 prose fix reopened the mechanism the lane existed to close, and round 4's right
  answer was to DELETE.** `engine-cross-run`. `76f0d3d` added `isCancellation`, which decided "this
  run was cancelled" from the thrown value's NAME — so any fetch- or deadline-backed `StateStore`
  rejecting with an `AbortError` ended the parent run, which is exactly the input class the lane
  had closed two rounds earlier. The lane first replaced the shape test with a signal test, then
  drove the guard's true arm and found it protected nothing: *"substituting `if (false) throw e` for
  the guard leaves all fourteen tests green, including that one… `cancel` decides a run's status by
  journaling `run.cancelled`, so a task re-classed as "come back later" defers into a run that is
  already over. The loosening four rounds argued about cannot happen."* The confirming reviewer
  tried to refute the deletion and could not. **Driving a guard's true arm is a different act from
  testing around it**, and it is what turns four rounds of argument into a deletion.
- **The diff reviewer's blocking finding was the author's own bound claim, not the code.**
  `plane-inputs`: *"the refusal was bounded in two dimensions and needed four, and it asserts no
  consequence at all"* — and the lane's own note, *"Three successive readers found a false clause in
  this one sentence, which is the signal that the sentence's shape was wrong rather than its
  wording."* Same shape in `usage-floor`, where round 1 *"found no defect in the code, only an
  overclaim about what it achieves and two undocumented residues. All round-1 changes are docstring
  corrections plus two new pinned tests."*
- **The real mechanism was not the one the row named.** `node-id`. §A0.19 said *"`plans` is a plain
  object, so `plans['valueOf']` is a function"*; `plans` turned out to be unreachable, because every
  read of it is `?.field ?? default`. The reachable defect was one object over —
  `ctx.baselinePostures?.[n.id]` fabricating `GRAPH014_OVERSIGHT_LOOSENED`, escalated by
  `compile.ts` to a policy-class `E_OVERSIGHT_LOOSENED` on a graph that never reached policy. The
  fix was unchanged and every justification around it was rewritten. **A row's stated mechanism is a
  hypothesis; reproduce it before you cite it in the fix.**
- **The mock, not the console.** `flake`. A flake in a test that drives a product file is evidence
  about the harness first: the DOM mock's `innerHTML` had no setter clearing `children`, and
  `console.ts` — the file everyone would have edited — was correct throughout. The diagnosis
  reproduced the exact failing string *"with zero timing dependency — confirming hypothesis 1 and
  refuting 2–5"*, which is what a diagnosis is for; a fix chosen without it would have been a sleep.
- **The exclusion reason was wrong even though the number was right.** `seam-ledger`, round 1: the
  lane claimed `2a9eda8` stayed out of the census because of the final-paragraph rule. It stays out
  because it touches only `TODO.md`. Same round: a new test *"passed against the mutant"* — it would
  have been green with the mechanism removed. **A right number reached by a wrong argument is a
  claim nobody has checked**, and the test that cannot fail is how it survives.
- **A guard that runs once is not a guard.** `mcp-seal`: *"a scan that ran once and moved on"* had
  no way to catch a registration created afterward, *"because nothing re-ran it"* — measured, a
  squatter registered from a `setTimeout` sailed past it. The fix is not a bigger scan, it is asking
  the question at the one place every registration must pass through. The companion lesson from the
  same lane: **a value read from a caller-supplied object more than once can answer differently each
  time**, so read it into one binding and decide everything from that.
- **The adversary's optimum is not where the first test pinned it.** `usage-floor`: *"The
  adversary's true optimum is not `cacheCredit = 2500` (the sum-floor value the original test
  pinned) — it is `cacheCredit` close to `estimated`, which is indistinguishable from a genuine full
  cache hit."* The behaviour agent measured ~8× on the fixture it happened to choose, not the ~10×
  adversarial optimum — and the report says so rather than rounding them together.
- **Ask what an outcome-shaped `STATUS: CLOSED` actually closed.** `usage-floor` returned CLOSED
  with 0 confirmed blocking and its `TODO.md` row is still open, because the lane closed its own
  Goal and the row asks for more. **A lane's STATUS is about the lane, never about the row.**

New today:

- **`isolation: "worktree"` branches from the repository's DEFAULT branch, not from `HEAD`.** Four
  of this wave's seven worktrees came up at `086e47d` (`init`) instead of `c54b0c2` (`loom`). The
  symptom is a worktree with a pre-rewrite tree — `src/`, `tui/` — and no `packages/core/`. **Every
  lane brief must say "verify your merge-base before you commit", and every merge must re-verify
  `git merge-base <target> <branch>` rather than trust the lane.**
- **`git worktree remove` needs `git worktree unlock` first when a live `claude` pid holds the
  lock.** Seven of nine refused `--force` alone with *"cannot remove a locked working tree, lock
  reason: claude agent … (pid 49101)"*. That pid is the `claude` process that spawned the lane
  agents, not a running build, so unlocking is safe **once the lane is merged and verified** — and
  that ordering is the whole safety argument.
- **SIGTERM is deferred while `zsh` sits in `sleep`, so `kill` looks like it did nothing.** Use
  `kill -9` for a shell parked in a sleep loop. This is why the process-hygiene rule forbids the
  `until … sleep` idiom rather than merely asking that it be cleaned up: a loop you cannot reliably
  signal is a loop you cannot reliably stop.
- **Copy a lane's `.agent/<lane>/` out before removing its worktree** — `git worktree remove`
  deletes it, and for two lanes this wave the harness refused the in-worktree write entirely, so the
  final message was the only copy.
- **A clean merge shows no files.** `git show --name-only --format='' <clean-merge>` prints nothing;
  the same command on a conflict-resolving merge prints the files the resolution touched. Any tool
  that filters commits by "did it touch path P" is blind to clean merges, which is `TODO.md`
  §A0.26 and is worth remembering the next time a guard is given a path filter.
