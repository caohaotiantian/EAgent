## The cause, in one sentence

`Engine.#uncompensatedIrreversible` asks **"does the TOOL declare a compensation?"**;
`planCompensation` / `RewindPlan.dispatch` ask **"is there a step that will actually dispatch
one?"** — and a rewind is permitted on the first answer while nothing is undone according to the
second.

## Four shapes, and the split that round 1 forced

|---|---|---|---|---|---|
| 1 | `not_attempted`, no `details` recorded | absent (**correct**) | 0 steps | accepted | **REFUSE** (`planRewind` too) |
| 2 | nothing settled; no `details` recorded | n/a | 1 step, `dispatch 0` | accepted | **REFUSE** (`rewind` only) |

## Change 1 — the seam: write `retryable` where `compensation.ts` already promises it is written

`run/compensation.ts:170-173` says:

**It is not written.** `compensationRecord` (engine.ts:989-1013) only FORWARDS

Every exit of `#compensateOne`, with the answer each should carry:

differ is the projection folded for a different `atSeq`. `retryable: true` is still the right
answer — the row must not settle the seq — but the advice its reason gives an operator is "rewind
to another boundary", not "deploy the missing thing".

**Arm f is two different facts wearing one outcome**, and this is shape 3:

- **A policy GATE refusal.** `#compensateOne` dispatches with `nodeApproved: trigger === "rewind"`
  (engine.ts:2559). `#invokeTool`'s gate arm (engine.ts ~9568-9592) refuses when `!nodeApproved`,
  returning `{content, isError: true}` — **and no `error`**, unlike the `deny` arm one screen up,

  the class"*. The undo NEVER RAN. So: **record it `not_attempted`, `retryable: true`** — which is
  also more honest than today's `failed`, since `failed` means *the undo tool ran and did not work*.
- **A policy DENY, or a genuine tool error.** The undo ran, or was refused by a decision a rewind

To tell them apart without parsing the reason string — which is the thing `compensation.ts:170`
exists to avoid — **give `#invokeTool`'s gate-refusal return the typed error the deny arm already

consumer and found none that depends on that arm having no `error` — the agent-turn path reads
`content` only, the tool-node path reaches the arm with `nodeApproved: true` and never returns from
it, and `ToolResult.error` is optional and documented. **There is no `refusedForApproval` fallback;
revision 2's mention of one is withdrawn.**

**The two edits, and the reason string, verbatim.** `#invokeTool`'s gate arm (engine.ts ~9590)
keeps its `content` byte-identical, so nothing an agent sees changes:


where nothing could be named."*

**Cost of change 1, stated:** a retryable row is re-planned on every later pass, so a blocker that
never clears now appends one row per rollback instead of one ever. That is bounded (one per pass),
it is the shape `#dispatchRollback`'s context-less arm already lives with, and it is the price of

## Change 2 — arm 1 of the refusal, in `#uncompensatedIrreversible`

## Why the existing `no_compensation` wall is not a precedent for a journal-derived one

Revision 1 justified refusing on settled rows as *"symmetry with `no_compensation`"*. It is not
symmetric. The `no_compensation` wall reads the **live registry** (engine.ts:1995,
`this.tools.get(called.name)?.compensation`), i.e. the top of the `ToolRegistry` stack — so
registering a version that declares a compensation **clears it**, and the operator has a move. A
wall derived from a journal row is permanent by construction: the row is durable, `settled` is
sticky, and nothing an operator can deploy changes it. That is exactly why change 2's condition (4)
is about the ARGUMENTS — the one input that genuinely cannot change — and not about which blocker
happened to be recorded.
