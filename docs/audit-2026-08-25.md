### F27 · Violation six: run spend is not reconstructible from the journal, so a restart refunds the budget

### F33 · `ctx.now()` does not reproduce on replay — the replay clock is the wall clock, and the README states the opposite

`confirmed` · *Determinism and replay — the "control the realm" thesis*

The one sanctioned clock accessor for a node body diverges on every replay. `replayRun` fixes only the SHADOW STORE's clock (`replay.ts:439`, `new MemoryStateStore({now: opts.engine.now ?? (() => original.startedAt)})`), but that clock never reaches an event: `RunLog` passes `now: this.#now()` on every append (`run/log.ts:66` and `:101`) and `prepare` gives the caller priority (`journal/store.ts:236`, `const ts = input.now ?? now`). The replay Engine is constructed with no `now` (`cli.ts:2534-2545` passes only tools/functions/models/policy), so it defaults to `Date.now` (`run/engine.ts:775`). `#bodyClock` reads `p.tasks[taskId].lease.at`, which the fold takes from `e.ts` (`run/projection.ts:720`) — so the body's clock on replay is the wall clock at replay time. Further: even injecting a fixed clock cannot fix it, because the recorded `task.leased.ts` is never served; the shadow writes its own. The mechanism the code claims ("replay folds the same event and computes the same number", `engine.ts:3047`) does not exist.

**Evidence.** Ran a one-node graph whose body returns `ctx.now()` (`function/rnd@stable`) through `node packages/core/src/cli.ts run`. Journal dump: `run.submitted ts 1787639493451`, `task.leased ts 1787639493453`, run output `now: 1787639493453` — recording is correct. Then two `loom replay` invocations one second apart against the SAME runId:
  `✗ state.reduced : expected {..."now":1787639493453...}, got {..."now":1787639585181...}`
  `✗ state.reduced : expected {..."now":1787639493453...}, got {..."now":1787639586342...}`
The two replays differ by 1161 ms — exactly the `sleep 1` between them — proving the value tracks the wall clock and not `original.startedAt` (which is constant). Note `r1`/`r2` from `Math.random()` were bit-identical in both, so the seeded-PRNG half genuinely works and only the clock half does not.

**Why it matters.** This violates the non-negotiable "every nondeterministic call is recorded under a derived key, and replay serves the record" for the one clock the runtime sanctions, and it is asserted as fact in three places a user or maintainer would trust: README.md:94 ("**Reproducible.** `ctx.now()` is the task's journaled lease timestamp, so replay computes the same number with nothing new written"), TODO.md:274 ("~~**Clock bound to the journal (D3).**~~ **DONE for `ctx.now`** — ... so it reproduces on replay with nothing new written"), and DESIGN.md D3. Any graph whose body reads the time can never replay green, and an auditor re-deriving such a run gets `match: false` for a run that was faithfully recorded — the "harness that answers a different question than the one asked" failure that cli.ts:2538 itself warns about, one field over.

### F34 · Hook bodies get the real, unseeded `Math.random()` — the extension surface is exempt from the determinism built-ins get

### F18 · The score's cost and latency terms both reward FAILING — **PARTLY FIXED 2026-08-25**: cost is triple-counted on success, double on failure, and wallMs is 0 for every failed run

`understated` · claim rewritten by the verifier · *P3 — Endless self-improvement*

Reproduced exactly, and the defect is broader than the cost/latency terms. `readSignals` (score.ts:131-173) never reads `t.outcome.runStatus` at all — run failure contributes nothing to the outcome term either. So the two effects compound: on identical real spend (0.01) and wall (100ms), a FAILED run scores 0.267 and a SUCCEEDED run scores 0.100 — the failure outscores the success by 2.67x, not by a marginal nudge. One mitigation the finding does not name: `measureCohort` (score.ts:323) computes p50Cost from the same inflated trajectory field, so the 3x factor cancels inside an all-successful cohort; the bias is purely the success/failure asymmetry (3x + real wallMs vs 2x + wallMs 0) plus the missing runStatus signal.

**Evidence.** Ran `agent()` with MockModelAdapter against the real engine: projection usage `{"costUsd":0.000019,...}` vs trajectory usage `{"costUsd":0.000057,...}` — exactly 3×. Hand-built journals with identical real spend 0.01 and wall 100ms: `completed -> {"costUsd":0.03,...,"wallMs":100}` / `failed -> {"costUsd":0.02,...,"wallMs":0}`. Code: trajectory.ts:212-215 (`run.completed` arm), :273-275 (`model.called`), :301-303 (`task.committed`); score.ts:211-215.

**Why it matters.** Against a cohort p50 drawn from mostly-successful runs, an identical failed run collects roughly +0.067 on the cost term and the full +0.10 on the latency term — ~0.167 of the 0.4 of score that is not `outcome`. `isGolden` condition 2 is `score >= cohort.p90Score`, a p90 of exactly these numbers. ### F19 · **CONFIRMED AND FIXED 2026-08-26** — reproduced on a live engine, not a hand-built journal · A retry erases the human gate decision (S2) from the trajectory — the highest-value label, deleted by the normalization rule that claims to preserve strategy identity

`unverified` · *P3 — Endless self-improvement*

**Evidence.** Two hand-built journals identical except for one `task.retry_scheduled` row on the gated task `act@root#0`: `retry=false → humanDecisions [{approve,5000ms}], signals ["S2"], outcome 1, ceiling {"channel":"stable"}`; `retry=true → humanDecisions [], signals [], outcome 0, ceiling {"channel":"draft","requiresHumanSignOff":true}`. `policy.gatesRaised` stays 1 in both, so the fold knows a gate happened and has lost only the decision.

### F35 · `loom replay` runs with the hook registry disabled, so it never re-derives the extension chain

`confirmed` · *Determinism and replay — the "control the realm" thesis*
